# Bindless residency cost on Metal and wgpu: state of the art

Researched 2026-11-05 for ticket #599, before M4's residency work. It feeds ADR 0017's amendment and #183 (texture-wall's 10,005 bound Textures).

**Summary.** On the M4 Pro the cost is Metal's per-Texture residency declaration, and it grows with the square of the count. A probe outside wgpu reproduces texture-wall's stretch: 10,005 `useResource` calls on one render encoder take 12.8 to 13.5 ms of kernel scheduling, 20,000 take 52 ms and 40,000 202 ms. Declaring the same Textures in bulk, through one `useHeap` or a residency set, schedules the command buffer in 12 to 39 µs at every count measured, up to 40,000. A residency set does nothing while the per-Texture calls remain: the kernel pays for the calls, not for missing residency. So Metal's half of the cost goes only if wgpu-hal stops calling `useResource` for read-only binding-array Textures, or if the Textures become a few resources (texture arrays per size class). wgpu-core's per-Texture tracking, 17% of the main thread's samples in two profiles (28% of `Renderer::render`'s), goes only with the second, or with upstream's planned read-only usages. The note ends in four options and chooses none.

Sources: Apple's Metal documentation and WWDC sessions of 2023 and 2025; the ARB bindless texture extension; the GDC 2014 AZDO talk (through a web.archive.org snapshot); Microsoft's D3D12 residency documentation and Residency Starter Library; Vulkan-Docs; source at the commits linked: wgpu 30.0.1, Bevy 0.16.0, MoltenVK 1.4.2, Dawn, Godot, The Forge and Wicked Engine; wgpu, MoltenVK and gpuweb issues and pull requests; and a Swift probe measured on the M4 Pro (Measured on the M4 Pro). Each claim the note relies on is in `docs/references.toml`, cited by key. Boundaries: sparse textures, virtual texturing and mip streaming policy are #46's note and ADR 0017's; this note covers what binding a resident set of Textures costs each frame.

## Comparison

Costs are at texture-wall's 10,005 Textures on the M4 Pro unless stated. "Kernel" is a command buffer's `kernelEndTime − kernelStartTime`, the time the GPU driver spends on the CPU scheduling it [ref:apple-metal-command-buffer-kernel-time]; "encode" is the probe's CPU time from creating the command buffer to its commit.

## Techniques

**1. Per-Texture residency (today).** A bindless shader reads Textures through an argument buffer, and "Metal doesn’t determine what resource’s memory to make accessible to the GPU by inspecting the argument buffer"; the app declares each one [ref:apple-metal-argument-buffer-residency]. wgpu-hal 30 records each binding-array view in the bind group's `resources_to_use` [ref:wgpu-hal-30-metal-resources-to-use-by-view] and calls `useResource` for every entry on every `set_bind_group` [ref:wgpu-hal-30-metal-use-resource]; Dawn's new Metal resource table does the same once per pass [ref:dawn-metal-resource-table-use-resource]. Apple: the encoder methods "Require CPU overhead for each resource or heap, which scale up with each one you add" and apply to one encoder [ref:apple-metal-residency-set-aggregation]; Metal makes the resources resident after the commit, "which can delay when the GPU starts working on it", and "This overhead adds up as the number of resources increases" [ref:apple-metal-encoder-residency-at-commit]; `useResource` "is an expensive call when used in excess" [ref:apple-wwdc23-10124-use-resource-expensive]. No source gives a figure. The probe gives one: the kernel time grows as the square of the count, 3.4 to 4.1 times per doubling, and at 10,005 reads 12.8 to 13.5 ms against #565's 13.8 to 14.3 ms gate (`docs/performance.md`). The foundation is OpenGL's bindless handles, which "must first be made resident", and can be made non-resident again [ref:arb-bindless-texture-residency].

**2. Batched `useResources`.** Apple suggests the plural call [ref:apple-wwdc23-10124-use-resource-expensive]. It does not touch the kernel's cost and costs more CPU on the encoder than the single calls (1.06 to 1.43 against 0.54 to 0.93 ms at 10,005).

**3. Heaps and `useHeap`.** One `useHeap` covers every sampled Texture in a heap; it ignores Textures with `renderTarget` or `shaderWrite` usage, which still need `useResource` [ref:apple-metal-use-heap-sampled-textures]. Heaps are untracked by default, and their resources inherit it [ref:apple-metal-heap-untracked-default], so an upload copy and a later sample need a fence. Godot, when it does not use Metal's hazard tracking, calls `useHeaps` with its allocator's heaps on every render encoder [ref:godot-metal-use-heaps]; The Forge backs each device memory block with an `MTLHeap` and does the same [ref:the-forge-metal-use-heaps]. In wgpu, Textures from a native heap can only come in through `create_texture_from_hal`, whose tracking of heap resources #46 could not confirm, and wgpu-hal would still call `useResource` for each of them.

**4. Residency sets on the queue.** A residency set (macOS 15) aggregates allocations "at little to no cost for each resource or heap" and attaches to a queue in one call [ref:apple-metal-residency-set-aggregation]; the encoder methods are then unneeded for its allocations, up to 32 sets per queue or command buffer [ref:apple-metal-residency-set-limits]. The work moves to the set's first use, which `requestResidency` brings forward [ref:apple-metal-residency-set-request-residency]; a heap allocation in a set makes the whole heap resident [ref:apple-metal-residency-set-whole-heap]. Sets track no hazards and are not thread-safe [ref:apple-metal-residency-set]. Apple's guidance: queue for sets that change little, command buffer for sets that change often, few large sets [ref:apple-wwdc25-254-residency-set-guidance]; Metal 4's encoders have no `useResource` at all and treat every resource as untracked [ref:apple-metal4-residency-sets-only]. MoltenVK 1.3 put every allocation in one queue-wide set "to avoid having to useResource all resources in bound argument buffers" [ref:moltenvk-2402-residency-set] [ref:moltenvk-1.4.2-residency-set-queue]; Wicked Engine attaches one set to its queues as well [ref:wicked-metal-residency-set-queue]. The cost appears above the kernel's wired limit: on a 24 GB M4 Pro a game with 11.6 GiB of allocations in one queue-wide set re-wires memory every submission and runs at 2.3 to 2.9 fps against 8.7 to 8.8 without the set [ref:moltenvk-2890-residency-set-wired-limit]; ADR 0013's 8 GB Budget sits below the 11.6 GiB that hit the cliff, near the report's 8.1 GiB game that did not. wgpu-hal 30 already builds a set per submission for TLAS dependencies [ref:wgpu-hal-30-metal-residency-per-submit], and a wgpu maintainer expects sets to keep bindless resources resident [ref:wgpu-3637-read-only-usages]; no wgpu change after 30.0.1 moves bind groups to them. The probe's deciding row: a queue set holding all 10,005 Textures, with the per-Texture `useResource` still issued as wgpu-hal does, schedules in 12.9 to 13.5 ms, as without the set.

**5. Residency sets per command buffer.** The same set attached by `useResidencySet` each frame measured as row 4 (probe); Apple recommends it only for sets that change often [ref:apple-wwdc25-254-residency-set-guidance].

**6. Texture arrays per size class.** AZDO's portable alternative to bindless: an array "groups textures with same shape", "Dimensions, format, mips, MSAA", up to 2048 per container, and a texture array had "~5x Less Overhead" than a bind per object [ref:everitt-2014-azdo-texture-arrays]. In wgpu each class is one Texture, so wgpu-hal's `useResource`, wgpu-core's merge [ref:wgpu-core-30-merge-bind-group] and the kernel see one resource per class; a Layer becomes a class and a slice. Hardware filtering stays, as each slice keeps its own mips. The costs are ADR 0017's: a Texture whose resident mips change moves to another class by copy, as a new texture plus `copy_texture_to_texture` does today; each class's capacity is fixed at creation, and an empty slice still holds memory. wgpu's default limits allow 256 layers per array [ref:wgpu-types-30-max-texture-array-layers-default], and the Capability floor keeps the defaults; Metal and DX12 report 2048 ([capability matrix](wgpu-capability-matrix.md)).

**7. Binding only the frame's Textures.** Binding the 105 Textures texture-wall samples cost 38 to 42 µs of CPU where 10,005 cost 2.1 to 2.2 ms (#153); a rebuild costs 0.25 to 0.30 µs per Texture (`docs/performance.md`, M2). Bevy splits bindless materials into slabs of 64 resources on macOS and iOS and 2048 elsewhere, "to work around `wgpu` performance problems involving large numbers of bindless resources" [ref:bevy-0.16-bindless-slab-limit]. Shadow rays and M4's probe rays read Materials off screen (the map's residency line), so the frame's set is the visible and the ray-reachable Materials, not the rasterized ones alone.

**8. Capping the count.** The probe's first row: 2,500 Textures schedule in 0.9 to 1.1 ms, 5,000 in 3.5 to 3.7 ms. A cap bounds the cost and the world's distinct Textures together.

**9. Read-only usages.** wgpu-core merges each bind group view into the pass's usage scope on `set_bind_group` [ref:wgpu-core-30-merge-bind-group]. wgpu's bindless tracking issue plans `set_usages` so that "Those resources with only read only usages can be ignored and just bound indirectly" [ref:wgpu-3637-read-only-usages]; WebGPU's proposal names `useResource`, `useHeap` and `useResidencySet` as the Metal ways to manage residency [ref:gpuweb-bindless-residency]. Nothing of it is in a release.

**Other APIs.** D3D12 makes memory resident when an object is created and evicts it at destruction, per heap [ref:ms-d3d12-residency-object-lifetime]; its Residency Starter Library tracks the heaps each command list uses [ref:d3dx12-residency-set-per-command-list]. Vulkan's descriptor indexing lets one set hold "substantially all of their resources" [ref:vulkan-descriptor-indexing-large-sets]. Neither has a per-bind residency call, which fits the RTX 2070 SUPER's 0.5 ms gate on texture-wall under Vulkan (#565).

## Measured on the M4 Pro

A Swift probe outside the repo (Metal through Swift, no wgpu) created N private 4×4 RGBA8 Textures with three mips, as texture-wall's, uploaded them with blit copies, wrote their `gpuResourceID`s into an untracked shared argument buffer, and drew one full-screen triangle into a 256×256 target, sampling eight of them, in one render encoder per command buffer. Each variant ran 60 warm-up and 200 to 300 measured frames, each frame waited for before the next. The table gives the range of the runs' medians of `kernelEndTime − kernelStartTime`, in µs, over three interleaved rounds (one round at 20,000 and 40,000). Apple M4 Pro, macOS 27.0.1, AC power, one-minute load average 2.1 to 3.0, no praxis process benching.

| Residency declared by | 1 | 105 | 2,500 | 5,000 | 10,005 | 20,000 | 40,000 |
|---|---|---|---|---|---|---|---|
| `useResource` per Texture | 13–33 | 18–20 | 860–1,051 | 3,503–3,708 | 12,847–13,539 | 52,063 | 202,259 |
| `useResources`, one call | 13–14 | 19–20 | 974–1,040 | 3,422–3,592 | 12,761–13,360 | 51,869 | 202,606 |
| `useHeap`, Textures in one heap | 13–14 | 13 | 30–35 | 35–37 | 34–37 | 37 | 35 |
| Residency set on the queue | 13–14 | 13 | 12–14 | 32–35 | 32–39 | 33 | 36 |
| The heap in a residency set on the queue | 13–14 | 13–14 | 12–13 | 12–13 | 30–38 | 36 | 37 |
| Residency set per command buffer | 13–14 | 13–14 | 12–13 | 12–18 | 34–36 | 36 | 38 |
| Queue set, 128 changes and a `commit` a frame | 13–14 | 12–14 | 26–33 | 33–35 | 34–37 | 32 | 35 |

Every bulk declaration stays within 12 to 39 µs at every count. Encode at 10,005 is 0.54 to 0.93 ms with `useResource` per Texture, 1.06 to 1.43 ms with `useResources` and 6 to 13 µs with a heap or a set; the churn row's 128 changes and `commit` a frame add about 5 µs. Committing a set of 10,005 Textures and requesting residency took 0.48 to 2.7 ms once, at start (a heap in a set: 14 to 23 µs). From 2,500 up each doubling of the count multiplies the per-Texture rows' kernel time by 3.4 to 4.1. The last row decides fit: the set is in place and the kernel time is unchanged.

## Options for ADR 0017's amendment (no recommendation)

- **A. Residency set through wgpu-hal.** Rows 4 and 9 in part. wgpu-hal adds each read-only binding-array Texture to one queue residency set when its bind group is created, skips its `useResource`, and removes it when the Texture goes; Textures written in the frame keep `useResource` or get a fence, since sets track no hazards. Cuts the kernel's 13 ms and the encoder's per-Texture calls; leaves wgpu-core's tracking (17% of the main thread's samples in #153 and the M2 exit profile, 28% of `Renderer::render`'s; `docs/performance.md`). Needs a patched wgpu-hal or an upstream change: ADR 0007's exception covers using wgpu-hal, not forking it, so a patch is a dependency decision. Image: unchanged. Risk: the wired limit above (8 GB Budget against the 11.6 GiB that hit it on a 24 GB machine).
- **B. Texture arrays per size class.** Row 6. The Channels become binding arrays of texture arrays, one per shape (size, mip count, format); residency and tracking cost follow the class count. Safe wgpu, every backend. Costs: per-class capacities in the 8 GB split, a copy when a Texture changes class (what mip streaming already does), sources padded or grouped to shared shapes at cook, 256 layers per array unless the floor rises to 2048 (ADR 0021). Image: unchanged where shapes are kept; any padding or resampling at cook is a cook change to judge.
- **C. Bind only the frame's Textures.** Row 7. Each frame's bind group holds the Textures of the Materials visible or within ray reach, rebuilt when that set changes (ADR 0017 already batches rebuilds to one per frame); the other slots repeat Layer 0's view, as #565's probe did, so a Layer keeps its index. Safe wgpu; cost follows the set size at the square law above (5,000 distinct Textures already cost 3.5 to 3.7 ms of kernel). Image: unchanged if the set is complete; a Material outside it samples Layer 0's neutral default.
- **D. Wait for upstream, capped meanwhile.** Rows 8 and 9. Cap bound Textures by the texture pool's Budget so the kernel time stays under a chosen share of 6 ms, and adopt wgpu's read-only usages and Metal residency when they ship. No date: wgpu's bindless tracking issue is open.


## Not verified

- How texture-wall's lit pass alone pays: #565 found the depth passes' encoders, which bind the same group, schedule in 13 to 16 µs; the probe has one encoder and does not explain it.
- Hazards when a residency set replaces `useResource` for a Texture written by an upload copy earlier in the frame: Apple says sets track no hazards; the probe wrote its Textures once, before measuring.
- The wired-limit cliff with a set of Praxis's size: the probe's Textures total under 1 MB.
- That a 4×4 RGBA8 Texture stands for a BC7 one: format was not varied.
- AZDO's slides were read in a SlideShare transcript snapshot, not the original deck.
- Research since 2019: no paper on bindless residency or descriptor management was found; only vendor documentation, talks, issues and code.
