# wgpu 29 capability matrix: Metal, Vulkan, DX12

Researched 2026-10-12 against wgpu 29.0.1 at tag [`v29.0.1`](https://github.com/gfx-rs/wgpu/tree/v29.0.1) (commit `923b896`; every cited file in the cargo registry is byte-identical to the tag), Apple's [Metal Feature Set Tables](https://developer.apple.com/metal/Metal-Feature-Set-Tables.pdf) dated 2026-05-21 (cited as MFST pN), the Vulkan spec source at Vulkan-Docs `193ebe1`, DirectX-Specs `a610933`, Microsoft Learn, and vulkan.gpuinfo.org extension coverage for [Windows](https://vulkan.gpuinfo.org/listextensions.php?platform=windows) and [Linux](https://vulkan.gpuinfo.org/listextensions.php?platform=linux) (default "Recent (1y)" filter, share of device reports, cited as gpuinfo W/L; every figure re-read 2026-10-13, [#95](https://github.com/gariasf/praxis/issues/95)). Ticket #19. What the reference machine actually does is under Measured on the M4 Pro. Audited 2026-10-13 ([#95](https://github.com/gariasf/praxis/issues/95)): the rows ADR 0021's Capability floor rests on (binding arrays, `INDIRECT_FIRST_INSTANCE`, ray queries, timestamps, BC, MSAA, `max_buffer_size`, probing and requesting, backend and compiler choice) were checked against the wgpu 30.0.1 crate source, and their links point at `v30.0.1`; every other wgpu link stays at `v29.0.1`.

Cells follow the wgpu-hal adapter code; where the `Features` docs disagree, the code wins and Surprises names the gap. Link labels: `mtl`, `vk`, `dx` are wgpu-hal `{metal,vulkan,dx12}/adapter.rs`; a `-cmd`, `-dev`, `-mod` suffix is that backend's `command.rs`, `device.rs`, `mod.rs`; `feat`, `lim`, `inst` are wgpu-types `features.rs`, `limits.rs`, `instance.rs`; `core-*` are wgpu-core files.

"Experimental" means the bit is in `Features::all_experimental_mask()` ([feat 1853](https://github.com/gfx-rs/wgpu/blob/v30.0.1/wgpu-types/src/features.rs#L1853-L1866)): the device request needs `experimental_features: unsafe { ExperimentalFeatures::enabled() }` ([tokens 37](https://github.com/gfx-rs/wgpu/blob/v30.0.1/wgpu-types/src/tokens.rs#L37)) or fails with `RequestDeviceError::ExperimentalFeaturesNotEnabled` ([core-inst 907](https://github.com/gfx-rs/wgpu/blob/v30.0.1/wgpu-core/src/instance.rs#L907-L917)). DX12 conditions written "SM 6.x" hold only with the DXC compiler; with FXC the adapter is SM 5.1 ([dx 435](https://github.com/gfx-rs/wgpu/blob/v30.0.1/wgpu-hal/src/dx12/adapter.rs#L435-L437)).

## Probing and requesting

- Probe before a device exists: `Adapter::features()`, `limits()` (the best the adapter offers), `get_info()` (`backend`, `device_type`, `subgroup_*`, `transient_saves_memory`), `get_downlevel_capabilities()` (`INDIRECT_EXECUTION`), `get_texture_format_features(format)` (MSAA counts, storage, filtering) ([wgpu adapter 159](https://github.com/gfx-rs/wgpu/blob/v29.0.1/wgpu/src/api/adapter.rs#L159-L184)). After: `Queue::get_timestamp_period()`, `Device::generate_allocator_report()`, `Device::get_internal_counters()`.
- Request through `DeviceDescriptor { required_features, required_limits, experimental_features, .. }` ([wgpu-types device 12](https://github.com/gfx-rs/wgpu/blob/v30.0.1/wgpu-types/src/device.rs#L12-L35)). `Limits::default()` is the WebGPU set; anything better must be requested; helpers: `using_minimum_supported_acceleration_structure_values()` (on 30.0.1: 2^24 − 1 BLAS geometries and TLAS instances, 2^28 BLAS primitives, one acceleration structure and 29 buffers plus acceleration structures per stage), `using_recommended_minimum_mesh_shader_values()` ([lim 774](https://github.com/gfx-rs/wgpu/blob/v30.0.1/wgpu-types/src/limits.rs#L774-L853)).
- Request failures: `RequestDeviceError::UnsupportedFeature`, `ExperimentalFeaturesNotEnabled`, `LimitsExceeded` ([core-inst 900](https://github.com/gfx-rs/wgpu/blob/v30.0.1/wgpu-core/src/instance.rs#L900-L941)), returned as `Err` on native ([wgpu_core 933](https://github.com/gfx-rs/wgpu/blob/v30.0.1/wgpu/src/backend/wgpu_core.rs#L933-L948)) although the `request_device` doc lists panics ([wgpu adapter 49](https://github.com/gfx-rs/wgpu/blob/v30.0.1/wgpu/src/api/adapter.rs#L49-L54)). 29.0.1's limit check omitted `max_binding_array_sampler_elements_per_shader_stage` and `max_acceleration_structures_per_shader_stage`; 30.0.1's checks both ([lim 18](https://github.com/gfx-rs/wgpu/blob/v30.0.1/wgpu-types/src/limits.rs#L18-L100)).
- Use without request: an API call raises `MissingFeatures` ([core-dev 342](https://github.com/gfx-rs/wgpu/blob/v29.0.1/wgpu-core/src/device/resource.rs#L342-L348)) and an uncaptured error panics by default ([wgpu_core 685](https://github.com/gfx-rs/wgpu/blob/v29.0.1/wgpu/src/backend/wgpu_core.rs#L685-L688)) unless an error scope catches it; WGSL using an unrequested capability fails shader-module validation, since naga's capabilities come from the device features ([bridge 9](https://github.com/gfx-rs/wgpu/blob/v29.0.1/wgpu-naga-bridge/src/lib.rs#L9-L100)).
- Backend choice: wgpu-core registers Vulkan, then Metal, then DX12 ([core-inst 83](https://github.com/gfx-rs/wgpu/blob/v30.0.1/wgpu-core/src/instance.rs#L83-L88)); `request_adapter` takes the first match, `PowerPreference::None` does not sort, and the other values sort stably by device type ([core-inst 571](https://github.com/gfx-rs/wgpu/blob/v30.0.1/wgpu-core/src/instance.rs#L571-L619)). With `Backends::PRIMARY` on Windows the Vulkan adapter wins whenever a Vulkan driver exists.
- DX12 compiler: `Dx12Compiler::Auto`, the default, uses static DXC only with the `static-dxc` cargo feature (not in wgpu's defaults, [wgpu Cargo.toml 37](https://github.com/gfx-rs/wgpu/blob/v30.0.1/wgpu/Cargo.toml#L37-L46)), else `dxcompiler.dll`, else FXC ([dx-inst 64](https://github.com/gfx-rs/wgpu/blob/v30.0.1/wgpu-hal/src/dx12/instance.rs#L64-L95)); the `Fxc` variant's doc still says "(default)" ([wgpu-types backend 780](https://github.com/gfx-rs/wgpu/blob/v30.0.1/wgpu-types/src/backend.rs#L780-L803)).
- `praxis capabilities` ([src/gpu/mod.rs](../../src/gpu/mod.rs)) reads `Adapter::features()`, `limits()`, `get_info()` and `get_texture_format_features()` without requesting a device, so it also runs below the Capability floor (ADR 0021), which every `GpuContext` device requests exactly. It prints the floor's four items #93 found missing: `INDIRECT_FIRST_INSTANCE`, `max_buffer_size`, `max_acceleration_structures_per_shader_stage`, and 4x MSAA on the main pass's formats, `Depth32Float` and, since #200, the HDR target's `Rgba16Float` (`Rgba8UnormSrgb` before; the window's surface takes only the tonemapping pass's single-sample output). It does not print: `BUFFER_BINDING_ARRAY`, `STORAGE_RESOURCE_BINDING_ARRAY`, `STORAGE_TEXTURE_ARRAY_NON_UNIFORM_INDEXING`, `ACCELERATION_STRUCTURE_BINDING_ARRAY`, the sampler and acceleration-structure binding-array limits; `MULTI_DRAW_INDIRECT_COUNT`, `DownlevelFlags::INDIRECT_EXECUTION`; mesh limits beyond output vertices and primitives; BLAS limits; `Queue::get_timestamp_period`; `_BC_SLICED_3D`, ASTC, ETC2; `SUBGROUP_VERTEX`; every short row. Its Metal subgroup line prints the constants 4 and 64.

## Surprises (what a session trusting the docs or the ticket would get wrong)

1. ADR 0013 as first accepted counted GPU memory "as wgpu's allocator report states them" (since #50 the engine sums what it creates); on Metal, the reference backend, that report is `None`, the byte counters stay at zero, and budget thresholds do nothing.
2. The docs list `EXPERIMENTAL_RAY_QUERY` as Vulkan-only and `PARTIALLY_BOUND_BINDING_ARRAY` as Vulkan and DX12; the Metal adapter sets both. The docs' Metal condition for texture arrays (MSL 2.0, macOS 10.13) is older than the code's (MSL 3.0 plus argument buffers Tier 2).
3. Vulkan `MULTI_DRAW_INDIRECT_COUNT` depends on the extension string, not on Vulkan 1.2; the spec makes the count commands optional on 1.2 without the extension ([VK_KHR_draw_indirect_count.adoc 37](https://github.com/KhronosGroup/Vulkan-Docs/blob/193ebe195f47ffc5004683d1659e71c725658c4d/appendices/VK_KHR_draw_indirect_count.adoc#L37-L39)).
4. `multi_draw_indirect` runs on Metal as a CPU loop; per the changelog, `MULTI_DRAW_INDIRECT_COUNT` being present is how to know multi-draw is not emulated ([changelog 966](https://github.com/gfx-rs/wgpu/blob/v29.0.1/CHANGELOG.md#L966-L970)).
5. ADR 0005 reads per-draw data through `instance_index`; on DX12 that includes `first_instance` for indirect draws only through indirect validation, and never for `multi_draw_indirect_count`.
6. A Windows build without DXC loses every SM 6 feature on DX12 (subgroups, f16, int64, int64 atomics, ray query); wgpu's defaults do not link DXC.
7. On Windows, `Backends::PRIMARY` selects Vulkan over DX12; the DX12 column applies only when the engine restricts `backends` to `Backends::DX12` or no Vulkan adapter exists.
8. `SHADER_PRIMITIVE_INDEX` no longer exists: it is `Features::PRIMITIVE_INDEX` with `enable primitive_index;`, and on Vulkan it switches on `geometryShader`.
9. The Metal subgroup sizes (4, 64) and timestamp period (1.0) are constants, so a probe printing them measures nothing. Measured on the M4 Pro: subgroups are 32 wide, and the 1.0 period is right.
10. Mesh shaders on Metal and DX12 need passthrough shaders; WGSL mesh shaders compile only for Vulkan. On Metal the feature bit is set, yet a WGSL mesh pipeline panics the process (measured). v30.0.0 adds WGSL mesh shaders on both (After 29.0.1).
11. Metal exposes `TIMESTAMP_QUERY_INSIDE_ENCODERS` on Apple GPUs, but the sample can land at the next encoder boundary instead of the call site. From v30.0.0 the bit needs blit-encoder sampling, so Apple GPUs no longer report it (After 29.0.1).
12. DX12 and Linux non-NVIDIA Vulkan cap `max_buffer_size` at 2^31-1, and Vulkan and DX12 cap storage bindings at 2^31-1, so a shared vertex or index buffer (ADR 0002) above 2 GiB cannot be one buffer there.
13. Only 4x MSAA is valid until `TEXTURE_ADAPTER_SPECIFIC_FORMAT_FEATURES` is requested; Apple lists 4 as the render-pass maximum on Apple9.
14. Reported limits that diverge from the vendor: DX12 sampler binding-array elements 2^20 against a 2048 heap (fixed in 29.0.2); Metal 1024 sampler elements on Apple7 and Apple8 against Apple's 996; Metal mesh grid 1024 on Apple9 against Apple's 1,048,575; Metal ray-tracing limits are constants.
15. On Metal, pass timestamps resolved before their pass's submission completes read 0, or repeat the previous values, for passes of a few milliseconds (measured), whether the resolve is in the same submission or the next one. Resolved after the submission completed, every reading was valid.
16. WGSL's `enable subgroups;` fails to parse in naga 29.0.1; subgroup builtins work without it.

Options for the blocked decisions (no recommendation):

- A. Require Tier 1 only. Indirect draw counts are then fixed on the CPU side, and ray-traced shadows and mesh shading are out.
- B. Require Tier 1; probe Tier 2 at runtime and enable it behind `ExperimentalFeatures::enabled()`, keeping a Tier 1 path for each use.
- C. Require Tier 1; use Tier 3 on Windows and Linux where present, with a Metal path that uses neither count draws nor in-pass timestamps.
- D. Require Tiers 1 and 2; hardware without ray queries or mesh shaders is out of scope.
- For the ADR 0013 metric on Metal: an engine-side ledger of the buffer and texture sizes it creates (same on every backend); per-backend native figures (Metal `currentAllocatedSize` through `as_hal`, wgpu's allocator report on Vulkan and DX12); or a restated metric.

- Why early timestamp resolves read 0 or stale values (the Metal hal documents sampling quirks at [mtl-cmd 157](https://github.com/gfx-rs/wgpu/blob/v29.0.1/wgpu-hal/src/metal/command.rs#L157-L180)), and whether 30.0.x changes them.
