# State of the art: job systems and frame threading

Researched 2026-10-12 for ticket #47; it blocks #20 (threading and job model). Pinned crates were read in the cargo registry, and every cited registry file is byte-identical to its tag: wgpu 29.0.1 with wgpu-core, wgpu-hal and wgpu-types at [`v29.0.1`](https://github.com/gfx-rs/wgpu/tree/v29.0.1); bevy_ecs and bevy_tasks 0.18.1 at [`v0.18.1`](https://github.com/bevyengine/bevy/tree/v0.18.1); async-executor 1.14.0 at [`v1.14.0`](https://github.com/smol-rs/async-executor/tree/v1.14.0); winit 0.30.13 at [`v0.30.13`](https://github.com/rust-windowing/winit/tree/v0.30.13); raw-window-metal 1.1.0, through which wgpu-hal makes its Metal layer, at [`1.1.0`](https://github.com/rust-windowing/raw-window-metal/tree/1.1.0). bevy_render and bevy_app are cited as shipped practice only (Praxis uses bevy_ecs alone, ADR 0009) and were read at the same Bevy tag on GitHub.

Link labels: `wgpu-`, `core-`, `hal-`, `types-` name a file of the wgpu, wgpu-core, wgpu-hal and wgpu-types crates (`hal-mtl` is the Metal backend); `ecs-`, `tasks-`, `render-` name a bevy_ecs, bevy_tasks or bevy_render file; `exec` is async-executor's `src/lib.rs`; the number is the first cited line, and `pN` is a PDF page. Reference machine (ADR 0013): Apple M4 Pro, 12 cores without SMT, 8 performance cores in two clusters of 4 with 16 MiB L2 each and 4 efficiency cores sharing 4 MiB L2 (`sysctl hw.perflevel0`, `hw.perflevel1`), macOS 27.0.1. ADR 0008 is not engaged: no technique here accumulates across frames.

## Techniques

**Thread per subsystem.** Halo: Reach gave rendering, audio and simulation their own hardware threads; simulation computed tick N while rendering drew tick N-1 from a copied game state ([Tatarchuk p13-p15](https://advances.realtimerendering.com/destiny/gdc_2015/Tatarchuk_GDC_2015__Destiny_Renderer_web.pdf#page=13)). Unreal's render thread runs one frame behind the game thread and records platform-agnostic commands that an RHI thread translates, keeping single-threaded submission order ([UE](https://dev.epicgames.com/documentation/en-us/unreal-engine/parallel-rendering-overview-for-unreal-engine)). Unity's Native, Legacy and Split graphics-job modes vary who writes and who translates commands ([Native](https://docs.unity3d.com/ScriptReference/GraphicsJobMode.Native.html), [Legacy](https://docs.unity3d.com/ScriptReference/GraphicsJobMode.Legacy.html), [Split](https://docs.unity3d.com/ScriptReference/GraphicsJobMode.Split.html)). Caveat: Halo's static per-thread balance left the smaller threads idle and did not carry over to other core layouts ([p17-p18](https://advances.realtimerendering.com/destiny/gdc_2015/Tatarchuk_GDC_2015__Destiny_Renderer_web.pdf#page=17)).

**Work stealing.** Blumofe and Leiserson proved the time and space bounds of randomized stealing ([JACM 1999](https://doi.org/10.1145/324133.324234)); Cilk-5's work-first principle moves overhead from the work onto the critical path ([PLDI 1998](https://doi.org/10.1145/277650.277725)); crossbeam-deque cites Chase and Lev's circular deque ([SPAA 2005](https://doi.org/10.1145/1073970.1073974)) and its weak-memory proof ([PPoPP 2013](https://doi.org/10.1145/2442516.2442524)). Since 2019, BWoS splits each queue into blocks so owner and thieves rarely meet ([OSDI 2023](https://www.usenix.org/system/files/osdi23-wang-jiawei.pdf#page=2)). Caveat: async-executor, under bevy_tasks, is not deque-based: spawned and woken tasks enter one global queue, and each runner refills a bounded local queue by taking half of another ([exec 357](https://github.com/smol-rs/async-executor/blob/v1.14.0/src/lib.rs#L357-L363), [exec 963](https://github.com/smol-rs/async-executor/blob/v1.14.0/src/lib.rs#L963-L983)).

**Fibers.** Gyrling's job system for The Last of Us Remastered runs 6 core-locked workers over 3 priority queues, without stealing, and 160 fibers; a waiting job parks its fiber and the worker takes another ([Gyrling p7-p18](https://media.gdcvault.com/gdc2015/presentations/Gyrling_Christian_Parallelizing_The_Naughty.pdf#page=7)). The cost is a separate synchronization regime: OS mutexes break because fibers migrate, and compilers may cache a thread-local address across a switch ([p36-p38](https://media.gdcvault.com/gdc2015/presentations/Gyrling_Christian_Parallelizing_The_Naughty.pdf#page=36)). Nishanov's P1364R0 cites that hazard and stack memory to judge fibers unsuited to scalable software ([p1](https://www.open-std.org/jtc1/sc22/wg21/docs/papers/2018/p1364r0.pdf#page=1), [p5](https://www.open-std.org/jtc1/sc22/wg21/docs/papers/2018/p1364r0.pdf#page=5)). Rust futures are stackless coroutines ([RFC 2033](https://rust-lang.github.io/rfcs/2033-experimental-coroutines.html)); stackful ones need a crate such as corosensei.

**Explicit task graphs.** Destiny builds a job chain per view only when the view exists, and finishing extract unblocks the next simulation tick ([Tatarchuk p70](https://advances.realtimerendering.com/destiny/gdc_2015/Tatarchuk_GDC_2015__Destiny_Renderer_web.pdf#page=70), [p73](https://advances.realtimerendering.com/destiny/gdc_2015/Tatarchuk_GDC_2015__Destiny_Renderer_web.pdf#page=73), [p91](https://advances.realtimerendering.com/destiny/gdc_2015/Tatarchuk_GDC_2015__Destiny_Renderer_web.pdf#page=91)). Unreal's Tasks System adds prerequisites, nested tasks and pipes on the TaskGraph workers ([UE Tasks](https://dev.epicgames.com/documentation/en-us/unreal-engine/tasks-systems-in-unreal-engine)). Since 2019: Taskflow schedules graphs with in-graph control flow by work stealing ([TPDS 2022](https://doi.org/10.1109/TPDS.2021.3104255)); a Euro-Par 2022 simulation of a Ubisoft frame graph found sorting subtasks, then splitting long tasks, gained more than swapping schedulers ([Regragui p11](https://hal.science/hal-03580775v1/document#page=11)). Caveat: Jolt's pool is an example; it expects the engine's job system ([JobSystemThreadPool.h 20](https://github.com/jrouwe/JoltPhysics/blob/v5.6.0/Jolt/Core/JobSystemThreadPool.h#L20-L24)).

**Heartbeat scheduling.** Acar et al. keep parallelism latent and promote a task only when a periodic heartbeat fires, bounding task-creation overhead for any nested-parallel program ([PLDI 2018](https://doi.org/10.1145/3192366.3192391)); TPAL implements the beat with kernel and hardware interrupts ([PLDI 2021](https://doi.org/10.1145/3453483.3460969)). The Rust crate chili ports Spice, which states it uses heartbeat scheduling ([Spice README 5](https://github.com/judofyr/spice/blob/39186ac9da2b851f558a33926836e605e238694d/README.md#L5)), and runs a thread that sets per-worker heartbeat flags ([chili lib.rs 147](https://github.com/dragostis/chili/blob/6c49338d25f1656ba1cdd0b9b21479cd4207652f/src/lib.rs#L147-L181)). Caveat: its published wins are on cheap tree recursion; at 1023 nodes chili is slower than serial ([README 55](https://github.com/dragostis/chili/blob/6c49338d25f1656ba1cdd0b9b21479cd4207652f/README.md#L55)).

**ECS-scheduled parallel systems.** bevy_ecs builds a pairwise conflict matrix from system access, starts a ready system only when no running system conflicts, and runs an exclusive system only when nothing else runs ([ecs-mt 186](https://github.com/bevyengine/bevy/blob/v0.18.1/crates/bevy_ecs/src/schedule/executor/multi_threaded.rs#L186-L202), [ecs-mt 539](https://github.com/bevyengine/bevy/blob/v0.18.1/crates/bevy_ecs/src/schedule/executor/multi_threaded.rs#L539-L576)). Unity Entities runs systems on the main thread ([systems](https://docs.unity3d.com/Packages/com.unity.entities@1.3/manual/concepts-systems.html)) and chains their jobs by component access ([dependencies](https://docs.unity3d.com/Packages/com.unity.entities@1.3/manual/scheduling-jobs-dependencies.html)); Flecs runs each multi-threaded system on every worker, with sync points between ([Systems.md 1437](https://github.com/SanderMertens/flecs/blob/v4.1.6/docs/Systems.md#L1437-L1439)). Caveat: Bevy's only published overhead predates the current executor ([#6503](https://github.com/bevyengine/bevy/pull/6503)); Measured below has 0.18.1's. Flecs' static slices are the split Apple says finishes late on efficiency cores.

**Frame pipelining.** Gyrling measured a 25 ms critical path inside about 100 ms of CPU work on 6 cores; overlapping game logic, render logic and GPU work on consecutive frames brought the frame to 15.5 ms ([p50-p64](https://media.gdcvault.com/gdc2015/presentations/Gyrling_Christian_Parallelizing_The_Naughty.pdf#page=50)). Destiny's extract window blocks the next tick while every output system reads game state ([Tatarchuk p92-p93](https://advances.realtimerendering.com/destiny/gdc_2015/Tatarchuk_GDC_2015__Destiny_Renderer_web.pdf#page=92)). Bevy ping-pongs its render sub-app between threads through two `bounded(1)` channels ([render-pipelined 131](https://github.com/bevyengine/bevy/blob/v0.18.1/crates/bevy_render/src/pipelined_rendering.rs#L131-L132)). Caveat: wgpu calls a latency of 3 or more very noticeable at 60 Hz ([types-surface 197](https://github.com/gfx-rs/wgpu/blob/v29.0.1/wgpu-types/src/surface.rs#L197-L231)); no source read measures input-to-photon cost per stage.

**Render graphs.** O'Donnell's FrameGraph compiles declared passes into reference counts, lifetimes, barriers and async wait points and culls unreferenced passes ([p26](https://media.gdcvault.com/gdc2017/Presentations/ODonnell_Yuriy_FrameGraph.pdf#page=26)); Unreal RDG ships transient aliasing, split barriers and parallel command-list recording ([UE RDG](https://dev.epicgames.com/documentation/en-us/unreal-engine/render-dependency-graph-in-unreal-engine)). Halcyon builds its graph serially and records it in parallel ([p46](https://media.contentapi.ea.com/content/dam/ea/seed/presentations/wihlidal-halcyonarchitecture-notes.pdf#page=46)); Granite reorders passes and reuses images instead of aliasing memory ([Arntzen](https://themaister.net/blog/2017/08/15/render-graphs-and-vulkan-a-deep-dive/)). Caveat for wgpu 29: barriers are automatic, and there is neither an aliasing API nor a second queue, so culling, ordering and per-pass recording remain.

**Parallel command recording.** Vulkan makes command pools externally synchronized, so each thread records its own buffers ([fundamentals 690](https://github.com/KhronosGroup/Vulkan-Docs/blob/193ebe195f47ffc5004683d1659e71c725658c4d/chapters/fundamentals.adoc#L690-L731)); D3D12 command allocators are not free-threaded and bundles are pre-processed by the driver ([D3D12](https://learn.microsoft.com/en-us/windows/win32/direct3d12/recording-command-lists-and-bundles)); Metal's parallel encoder splits one pass across threads ([Metal](https://developer.apple.com/documentation/metal/mtlparallelrendercommandencoder)). Since wgpu v27, recorded commands are stored and encoded to the hal only at `finish` ([CHANGELOG 1027](https://github.com/gfx-rs/wgpu/blob/v29.0.1/CHANGELOG.md#L1027)). Caveat: wgpu has no API that splits one render pass, and the Metal hal makes no use of `MTLParallelRenderCommandEncoder`.

**Asynchronous upload and streaming.** D3D12 exposes copy queues beside 3D and compute ([D3D12](https://learn.microsoft.com/en-us/windows/win32/direct3d12/user-mode-heap-synchronization)); DirectStorage batches small NVMe reads with GPU decompression ([README 3](https://github.com/microsoft/DirectStorage/blob/c53f1499d5f67a61b69a1a348d22dcd2b4cb4ede/README.md#L3)); `MTLIOCommandQueue` loads files into resources used by the same device's queues ([Metal](https://developer.apple.com/documentation/metal/mtliocommandqueue)). wgpu 29's `write_buffer` and `write_texture` copy into a new staging allocation and run before the next submit's command buffers ([wgpu-queue 118](https://github.com/gfx-rs/wgpu/blob/v29.0.1/wgpu/src/api/queue.rs#L118-L156)); `StagingBelt` records copies into a caller's encoder ([belt 132](https://github.com/gfx-rs/wgpu/blob/v29.0.1/wgpu/src/util/belt.rs#L132-L138)). Caveat: wgpu's tracking issue lists asynchronous upload as unsolved ([#8824](https://github.com/gfx-rs/wgpu/issues/8824)).

**Core-type aware scheduling.** Apple tells custom pools to steal work, to make tasks more numerous than cores, to use QoS classes, and to replace spin locks with blocking locks ([Apple](https://developer.apple.com/documentation/apple-silicon/tuning-your-code-s-performance-for-apple-silicon)). Intel tells games to avoid hard affinity, prefer CPU sets and power-throttling hints, and balance dynamically ([Intel](https://www.intel.com/content/www/us/en/developer/articles/guide/12th-gen-intel-core-processor-gamedev-guide.html)). On the reference machine 4 of 12 cores are efficiency cores. Caveat: Naughty Dog locked each worker to a core ([Gyrling p18](https://media.gdcvault.com/gdc2015/presentations/Gyrling_Christian_Parallelizing_The_Naughty.pdf#page=18)); XNU reports no affinity sets on ARM, so macOS offers no such pinning ([affinity.c 96](https://github.com/apple-oss-distributions/xnu/blob/xnu-12377.121.6/osfmk/kern/affinity.c#L96-L99)).

## What the pinned stack imposes

bevy_ecs 0.18.1 and bevy_tasks 0.18.1:

- `ExecutorKind` defaults to `SingleThreaded` unless the `multi_threaded` feature is on, though its doc comment still says `MultiThreaded` is the default off wasm ([ecs-exec 45](https://github.com/bevyengine/bevy/blob/v0.18.1/crates/bevy_ecs/src/schedule/executor/mod.rs#L45-L67)). bevy_ecs's defaults are `std`, `bevy_reflect`, `async_executor`, `backtrace` ([ecs Cargo.toml 14](https://github.com/bevyengine/bevy/blob/v0.18.1/crates/bevy_ecs/Cargo.toml#L14-L20)); Praxis adds only `trace` ([Cargo.toml](../../Cargo.toml)) and nothing else in `Cargo.lock` depends on bevy_ecs or bevy_tasks, so `Schedule::default()` in [src/state.rs](../../src/state.rs) runs single-threaded.
- Without `multi_threaded`, bevy_tasks runs every task on one thread: `thread_num()` is 1 and builder settings are no-ops ([tasks Cargo.toml 12](https://github.com/bevyengine/bevy/blob/v0.18.1/crates/bevy_tasks/Cargo.toml#L12-L21), [tasks-single 50](https://github.com/bevyengine/bevy/blob/v0.18.1/crates/bevy_tasks/src/single_threaded_task_pool.rs#L50-L73), [tasks-single 101](https://github.com/bevyengine/bevy/blob/v0.18.1/crates/bevy_tasks/src/single_threaded_task_pool.rs#L101-L104)), and `Query::par_iter` iterates serially ([ecs-par 86](https://github.com/bevyengine/bevy/blob/v0.18.1/crates/bevy_ecs/src/query/par_iter.rs#L86-L101)).
- With it, `MultiThreadedExecutor` runs `Send` systems on the global `ComputeTaskPool`, non-`Send` systems on the thread of a `MainThreadExecutor` resource if present, else on the thread calling `Schedule::run`, and exclusive systems on the calling thread ([ecs-mt 706](https://github.com/bevyengine/bevy/blob/v0.18.1/crates/bevy_ecs/src/schedule/executor/multi_threaded.rs#L706-L711), [ecs-mt 716](https://github.com/bevyengine/bevy/blob/v0.18.1/crates/bevy_ecs/src/schedule/executor/multi_threaded.rs#L716-L762), [tasks-pool 320](https://github.com/bevyengine/bevy/blob/v0.18.1/crates/bevy_tasks/src/task_pool.rs#L320-L328)).
- If the application has not created the pool, the executor creates it with `TaskPool::default` ([ecs-mt 279](https://github.com/bevyengine/bevy/blob/v0.18.1/crates/bevy_ecs/src/schedule/executor/multi_threaded.rs#L279)), which spawns `available_parallelism()` threads ([tasks-pool 156](https://github.com/bevyengine/bevy/blob/v0.18.1/crates/bevy_tasks/src/task_pool.rs#L156-L167)) on top of the calling thread; `sysctl hw.logicalcpu` reports 12 here. A standalone user calls `ComputeTaskPool::get_or_init` first ([tasks-usages 13](https://github.com/bevyengine/bevy/blob/v0.18.1/crates/bevy_tasks/src/usages.rs#L13-L17)) with a `TaskPoolBuilder` that sets `num_threads` and an `on_thread_spawn` hook ([tasks-pool 52](https://github.com/bevyengine/bevy/blob/v0.18.1/crates/bevy_tasks/src/task_pool.rs#L52-L76)); the Bevy engine instead gives 25% of cores to IO and 25% to async compute, at most 4 each ([task_pool_plugin 112](https://github.com/bevyengine/bevy/blob/v0.18.1/crates/bevy_app/src/task_pool_plugin.rs#L112-L146)).
- `par_iter` sizes a batch as the largest matched table's length divided by threads times `batches_per_thread`, which defaults to 1 ([ecs-par 133](https://github.com/bevyengine/bevy/blob/v0.18.1/crates/bevy_ecs/src/query/par_iter.rs#L133-L155), [ecs-batching 94](https://github.com/bevyengine/bevy/blob/v0.18.1/crates/bevy_ecs/src/batching.rs#L94-L106)).
- `World` is `Send + Sync`; a non-`Send` resource panics when touched from a thread other than its inserter ([ecs-world 3777](https://github.com/bevyengine/bevy/blob/v0.18.1/crates/bevy_ecs/src/world/mod.rs#L3777-L3780), [ecs-resource 66](https://github.com/bevyengine/bevy/blob/v0.18.1/crates/bevy_ecs/src/storage/resource.rs#L66-L82)). Praxis inserts none today.

wgpu 29.0.1:

- On every native target `Device`, `Queue`, `CommandEncoder`, `RenderPass`, `RenderBundle`, `Surface` and `SurfaceTexture` are `Send + Sync` ([wgpu build.rs 7](https://github.com/gfx-rs/wgpu/blob/v29.0.1/wgpu/build.rs#L7-L10), [wgpu-device 23](https://github.com/gfx-rs/wgpu/blob/v29.0.1/wgpu/src/api/device.rs#L23-L24), [wgpu-queue 17](https://github.com/gfx-rs/wgpu/blob/v29.0.1/wgpu/src/api/queue.rs#L17-L18), [wgpu-encoder 26](https://github.com/gfx-rs/wgpu/blob/v29.0.1/wgpu/src/api/command_encoder.rs#L26-L27), [wgpu-pass 38](https://github.com/gfx-rs/wgpu/blob/v29.0.1/wgpu/src/api/render_pass.rs#L38-L39), [wgpu-bundle 16](https://github.com/gfx-rs/wgpu/blob/v29.0.1/wgpu/src/api/render_bundle.rs#L16-L17), [wgpu-surface 239](https://github.com/gfx-rs/wgpu/blob/v29.0.1/wgpu/src/api/surface.rs#L239-L240), [wgpu-surface-texture 16](https://github.com/gfx-rs/wgpu/blob/v29.0.1/wgpu/src/api/surface_texture.rs#L16-L17)); `RenderBundleEncoder` is never `Send` ([wgpu-bundle-encoder 17](https://github.com/gfx-rs/wgpu/blob/v29.0.1/wgpu/src/api/render_bundle_encoder.rs#L17-L24)). Command buffers run in submission order, and within one submit in the order passed ([hal-lib 1179](https://github.com/gfx-rs/wgpu/blob/v29.0.1/wgpu-hal/src/lib.rs#L1179-L1192)).

- Error scopes are a per-thread stack since v28, and `ErrorScopeGuard` is `!Send` ([CHANGELOG 629](https://github.com/gfx-rs/wgpu/blob/v29.0.1/CHANGELOG.md#L629-L642), [wgpu-device 422](https://github.com/gfx-rs/wgpu/blob/v29.0.1/wgpu/src/api/device.rs#L422-L436)).
- Map and work-done callbacks run on whichever thread next calls `Queue::submit`, `Device::poll` or `Instance::poll_all` after the GPU finishes, and that call waits for them ([wgpu-buffer 361](https://github.com/gfx-rs/wgpu/blob/v29.0.1/wgpu/src/api/buffer.rs#L361-L368)).
- One queue: `request_device` returns one `(Device, Queue)` ([wgpu-adapter 40](https://github.com/gfx-rs/wgpu/blob/v29.0.1/wgpu/src/api/adapter.rs#L40-L66)); the hal opens one `MTLCommandQueue` ([hal-mtl 64](https://github.com/gfx-rs/wgpu/blob/v29.0.1/wgpu-hal/src/metal/adapter.rs#L64-L68)), one Vulkan queue of family 0 ([hal-vk 2821](https://github.com/gfx-rs/wgpu/blob/v29.0.1/wgpu-hal/src/vulkan/adapter.rs#L2821-L2824)), one DX12 direct queue ([hal-dx 1035](https://github.com/gfx-rs/wgpu/blob/v29.0.1/wgpu-hal/src/dx12/adapter.rs#L1035-L1047)). The Metal adapter always offers `MAPPABLE_PRIMARY_BUFFERS` ([hal-mtl 1038](https://github.com/gfx-rs/wgpu/blob/v29.0.1/wgpu-hal/src/metal/adapter.rs#L1038-L1039)).
- Metal surfaces: creation panics off the main thread ([wgpu-surface 273](https://github.com/gfx-rs/wgpu/blob/v29.0.1/wgpu/src/api/surface.rs#L273-L275), [raw-window-metal 402](https://github.com/rust-windowing/raw-window-metal/blob/1.1.0/src/lib.rs#L402-L403), [hal-mtl-mod 152](https://github.com/gfx-rs/wgpu/blob/v29.0.1/wgpu-hal/src/metal/mod.rs#L152-L161)). Acquire and present have no main-thread check; acquire reads the hosting window's `occlusionState` on the calling thread ([hal-mtl-surface 123](https://github.com/gfx-rs/wgpu/blob/v29.0.1/wgpu-hal/src/metal/surface.rs#L123-L158)), present commits a command buffer on the device queue ([hal-mtl-mod 599](https://github.com/gfx-rs/wgpu/blob/v29.0.1/wgpu-hal/src/metal/mod.rs#L599-L620)).

## Options for #20 (no recommendation)

### A. One thread plus the task pool

- Threads and owners: the main thread runs winit, the simulation schedule, prepare, command recording and submit; the compute pool runs systems, `par_iter` and per-pass encoders; an IO thread or pool reads and decodes assets.
- Frames in flight: 1 on the CPU; up to 2 on the GPU (`desired_maximum_frame_latency` 2, as today).
- Executor: `MultiThreaded`, which needs bevy_ecs's `multi_threaded` feature.
- wgpu queue: main thread only; workers return `CommandBuffer`s; decoded assets reach the queue through the main thread (`write_texture` or a `StagingBelt` copy).
- Frame data: built and consumed on the main thread; workers borrow it inside pool scopes; no channel.
- ADRs: 0004 keeps the ECS World out of the renderer without a thread crossing; 0009 gains a feature flag; 0013's 6 ms is one thread's frame plus its waits on the pool.

### B. Render thread one frame behind

- Threads and owners: the main thread runs winit, input, the simulation schedule and prepare; a render thread owns the `Surface` after its main-thread creation, records with the pool, acquires (off the main thread; see Not verified), submits and presents; an IO thread decodes assets and sends upload requests to the render thread.
- Frames in flight: 2 on the CPU (simulate N+1 while rendering N); up to 2 on the GPU.
- Executor: either kind; the ECS World never leaves the main thread.
- wgpu queue: render thread only, including uploads and error scopes.
- Frame data: moved through a bounded channel of capacity 1, the way Bevy passes its render sub-app, or a double buffer.
- ADRs: 0004 as written (a channel send); 0009 unchanged; 0013 does not say whether 6 ms bounds each thread or their sum, and has no latency budget for the extra frame (16.7 ms at 60 fps).

### C. Main thread for the OS only

- Threads and owners: the main thread runs winit, window calls and surface creation and forwards input over a channel; a simulation thread owns the ECS World; a render thread as in B; a streaming thread decodes and uploads.
- Frames in flight: 2 on the CPU plus input queued for the simulation thread; up to 2 on the GPU.
- Executor: either kind on the simulation thread; any future non-`Send` resource must be inserted and used there.
- wgpu queue: render thread for submit and present; the streaming thread may call `write_texture` itself (the queue is `Sync`), contending on the pending-writes mutex and landing at the render thread's next submit, or record its own encoder and send the `CommandBuffer` for ordered submission.
- Frame data: simulation to render through a channel, as in B; input from main to simulation through another.
- ADRs: 0004 as in B; 0009's ECS World leaves the main thread, which bevy_ecs allows (`World: Send`); 0013 as in B.

### D. Job graph without a render thread

- Threads and owners: the main thread runs winit and takes part in the pool; one worker per remaining core with a QoS class set in `on_thread_spawn`; IO threads outside the pool; no thread owns a stage, stages are job chains.
- Frames in flight: 2 or 3 overlapping stages on the CPU, each frame's data in a ring of per-frame packets; up to 2 on the GPU.
- Executor: `MultiThreaded` for the simulation schedule as one node of the graph; other stages run as bevy_tasks scopes or under a new task library.
- wgpu queue: a submit job at the end of each frame's chain, on whichever worker runs it; error scopes stay on the thread that pushed them.
- Frame data: the per-frame packet passed between stage jobs, released when its GPU work completes.
- ADRs: 0004 holds with Frame data as the packet; 0009's ECS becomes one stage of a larger graph and may need a dependency beyond bevy_tasks; 0013 needs critical path and summed CPU time stated separately.
