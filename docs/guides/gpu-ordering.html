Praxis · M3 · ticket #244 · PR #267

How a ray missed a triangle that was there

In brief

A Praxis test sometimes traced a ray at a triangle and hit nothing. On Metal with wgpu 30.0.1, the TLAS that rays search could be built from the triangle's BLAS before the GPU had finished compacting it: a GPU queue orders when work starts, not when it finishes, and nothing told Metal the build reads that BLAS. PR #267 makes the CPU wait for the compaction, only in frames that load Meshes. The idea to keep: when GPU work reads what other GPU work writes, something must order the two.

You'll learn

  • Why a queue orders when work starts, not when it finishes
  • How Vulkan, Direct3D 12 and Metal order a read after a write
  • Why Metal's hazard tracking misses a TLAS build's BLASes
  • How a stress loop and one-step cuts found the race
  • What the CPU wait costs, and how the GPU could order the work instead

Read first: Acceleration Structures Explained, Dynamic TLAS Explained

A test of the Mesh pool traced a ray straight down onto a triangle and, now and then, found nothing. The triangle was there. The TLAS that the ray searched had been built before the GPU finished writing the triangle's BLAS, and on Metal nothing in wgpu 30.0.1 told the GPU to wait. This guide follows that race from the symptom to the fix: why a GPU queue promises the order in which work starts but not the order in which it finishes, how graphics APIs order work that reads what other work wrote, why Metal's automatic tracking cannot see a TLAS build read its BLASes, how the work on #244 found the race by changing one step at a time, and what the fix costs. Two live demos model the race and replay the measured cuts.

PR #270 then corrected two of its comments, as main 3b07d5f. Praxis's code is quoted from 3b07d5f, and from 5a5f075 where it shows the code before the fix. Chapter 1 · ticket #244

A ray that sometimes misses

The test loads a Mesh of one triangle into the Mesh pool, which builds the Mesh's BLAS and compacts it. It then builds a TLAS with one entry for that BLAS, tagged 7, and traces three rays straight down: one onto the triangle and two beside it. It expects [Some(7), None, None]. On the M4 Pro it sometimes got [None, None, None]: the ray aimed at the triangle hit nothing.

The test is a_meshs_blas_holds_its_triangle_from_its_arena_ranges_and_is_compacted, in src/assets/pools.rs. Before the triangle it loads a Mesh whose only triangle is degenerate, so that the real triangle's ranges of the vertex and index Arenas start past their first elements. The TLAS places the BLAS with the identity transform and tags the entry with custom data 7, which a hit reports. Each ray starts 1 m above its point and looks 2 m down.

#244 records how often. The test first failed on 2026-10-22, during scripts/verify.sh on a branch that changed only a shader and its oracle tests, and passed when rerun alone. That day #244 counted 5 failures in about 16 runs of cargo test --lib and scripts/verify.sh, on branches that touched no BLAS code, and then recorded three more; the next day it failed once in 4 runs. Some failures came while another process was loading the same GPU, and at least one while nothing else was. That left the library's own tests, 115 to 120 of them, which cargo test runs in parallel, as many at a time as the machine has hardware threads, all on one adapter.

On 2026-10-23 the project's owner placed the ticket in milestone M3, blocking #211, the milestone's exit, for two reasons recorded on it. Verify runs are not reliable evidence while a test is flaky. And the BLAS the test traces comes from MeshPool::compact_blases, the engine's own load path, so "the race may be the engine's and not the test's; then shadow rays could miss a Mesh in real scenes." Chapter 5 shows that it was the engine's. The ticket closed the same day, when PR #267 merged.

Chapter 2 · Metal's command queue

A queue is an order, not a timeline

The CPU records GPU work into command buffers and submits them to a queue. The queue keeps them in the order they were submitted, and that order is its whole promise: the GPU starts each command buffer after the ones ahead of it have started. It does not wait for them to finish. Work that does not depend on earlier work, as far as the GPU knows, can run alongside it.

Apple's documentation says it in two places. A command queue "maintains an ordered list of command buffers", and of commit(), which submits one: "The GPU starts the command buffer after it starts any command buffers that are ahead of it in the same command queue." Starts, not finishes. Apple's overview of resource synchronization opens with "By design, GPUs can run multiple commands in parallel." And wgpu's Metal backend says it as plainly in a doc comment: "Metal allows independent command buffers in a queue to overlap on the GPU" (wgpu-hal 30.0.1, metal/mod.rs).

In wgpu, a command buffer is what CommandEncoder::finish returns, and Queue::submit sends a batch of them as one submission. wgpu-core adds command buffers of its own, among them one of resource transitions ahead of each of yours and one of copies that need no encoder of yours, such as those of Queue::write_buffer. That one is its pending writes, which it puts ahead of them all in the next submission (device/queue.rs). On Metal, wgpu-hal then commits the batch's command buffers one after another, so their order holds, and only their order.

The CPU learns that work has finished by asking. Device::poll with PollType::wait_indefinitely() blocks the calling thread until the most recent submission has finished (wgpu-types 30.0.1). That is a CPU wait: it is correct, and the thread does nothing else meanwhile.

The test's submissions

The flaky test makes three submissions. The first sends the load staging, with the copies of the Meshes' data and the BLAS builds that read them. compact_blases then polls until the builds have finished and records each compaction copy, which wgpu-core keeps in its pending writes. The second submission is the TLAS build's command buffer, with the pending writes just ahead of it. The third traces the rays. Nothing in the second submission says that the TLAS build reads what the copy writes.

Chapter 3 · hazards and barriers

Read after write

When one piece of GPU work writes memory that a later piece reads, the reader has to wait until the writer is done, or it may read old or half-written data. That is a read-after-write hazard. Vulkan and Direct3D 12 leave it to the application, which records a barrier between the two. Metal can handle it for you: for the resources it tracks, it holds back work that reads what earlier work is still writing. Either way, something has to know that the second piece reads what the first one writes.

Hazards are named by the order of two accesses to the same memory. Read after write is the one here. Write after read is a write that must wait until earlier reads are done, and write after write is two writes that must land in order. Two reads never conflict. In Apple's words: "It's okay for multiple commands to load data from the same resource memory at the same time because they all read from memory without modifying it." Without synchronization, the same page warns, "a load operation from one command can run before, during, or after a store operation."

Metal's hazard tracking

Every Metal resource is tracked or untracked. Resources made from the device are tracked by default and resources made from a heap are not, and an acceleration structure is a resource like any other; wgpu-hal makes its acceleration structures from the device (metal/device.rs, create_acceleration_structure). When a command writes a tracked resource, Apple writes, Metal will "Delay write operations until all previous read operations finish" and "Prevent subsequent commands from running until write operations finish".

Hazard tracking has an edge, and this whole race sits on it. Before Metal 4, Metal synchronizes access conflicts "only for the resources that" are tracked and that the application binds directly: "You directly bind that resource to an encoder type that adopts the MTLCommandEncoder protocol". A resource that the work reaches any other way, such as through an ID stored in a buffer, is outside it, unless a render or compute pass declares it with useResource; wgpu-hal declares no BLAS that way. Metal 4's own queues track nothing at all; wgpu-hal 30.0.1 still uses the older MTLCommandQueue, where tracking applies.

Barriers, fences and events

Where tracking does not reach, the application orders the work itself. Vulkan and Direct3D 12 do this with barriers recorded between commands. Metal has three tools. A barrier makes later work wait for earlier work: within a render or compute pass, and, since Metal's 26 releases, between passes on one queue, acceleration-structure passes included. A fence orders passes: one pass updates it after its stores, and a later pass waits for it before running. An event orders command buffers: one signals a value once its earlier work is done, and another, on the same queue or a different one, waits for that value before its next pass. A shared event also reaches the CPU and other devices.

Chapter 4 · wgpu-hal 30.0.1, Metal

What Metal cannot see

A TLAS is built from its BLASes, so its build has to come after whatever writes them. On Metal, wgpu builds every TLAS from a buffer of entries that name their BLASes by resource ID. The build's descriptor names the buffer, not the BLASes, so Metal's tracking never learns that the build reads them. wgpu-core does know, and asks the backend for a barrier at that point. On Metal, the function it calls is empty.

Apple's page on the build command shows the ordering it expects: "you can use a single encoder to build multiple geometry acceleration structures and then build the instanced structure that uses them", because "By default, Metal automatically synchronizes GPU access to the acceleration structure and any resources contained in the acceleration descriptor." The words that matter are the last ones: contained in the descriptor.

Two ways to name a BLAS

Metal's descriptor for a TLAS, an instance acceleration structure, takes its entries in one of several layouts. In the default layout, the descriptor carries the BLASes themselves, in instancedAccelerationStructures, and "Each instance in the instance descriptor buffer has an index into this array". In the indirect layout, "An option that enables an instance descriptor memory layout the GPU can populate", each entry holds its BLAS's accelerationStructureID, a resource ID, and the descriptor lists no BLAS at all.

Where wgpu-core asks for a barrier

wgpu is built in layers. Your calls go to wgpu-core, which validates them, tracks resources and decides where ordering is needed, the same way for every backend. wgpu-hal turns each of its requests into one backend's commands. For acceleration structures, wgpu-core calls the hal's place_acceleration_structure_barrier before it builds BLASes, after the BLAS builds of a call and before its TLAS builds, and after a TLAS build, before shaders read the TLAS (wgpu-core 30.0.1, command/ray_tracing.rs). So on Metal, nothing orders a TLAS build after the work that writes its BLASes, beyond whatever the GPU happens to do. At submit, wgpu-hal does one more thing for TLAS users: set_acceleration_structure_dependencies puts the BLASes that each command buffer's TLASes refer to into a residency set (metal/command.rs). That keeps them in GPU memory and orders nothing. Apple's page on residency sets says so: "residency sets don't track hazards, so you need to account for hazards with fences and events."

The issue upstream, gfx-rs/wgpu#9215, "Metal BLAS -> TLAS builds need synchronisation", was opened in March 2026 and is still open. It says the same from wgpu's side: "On metal, acceleration structure barriers are not inserted (due to metal not having barriers during development of this) however it appears that metal does not serialize them as I would expect an API with little synchronisation to have." Its repro sometimes reads zero where it should read one; #244's test read nothing where it should read 7.

The newer of its two fixes, PR #10292, still an open draft, adds regression tests, and a comment in them puts the mechanism in one sentence: "On Metal, acceleration structure builds are not ordered against each other within an encoder, nor across command buffers committed back to back, so a TLAS build could consume a BLAS that is still building." One of those tests, COMPACTED_BLAS_IN_PENDING_WRITES, is #244's case exactly: a BLAS compacted through the pending writes, which are "committed ahead of the command buffers of the next submission", and a TLAS built in that next submission, which "must be ordered after the copy".

Chapter 5 · Renderer::upload

The same race at load

The test did not invent the race; it follows the engine's own order. In a frame that follows new loads, Renderer::upload submits the load staging, which builds the new Meshes' BLASes; compacts them; and records the static TLAS's build into the frame's encoder. compact_blases waited on the CPU for the builds, but not for the compaction copies. wgpu-core held those in its pending writes until the next submission, and sent them in a command buffer at its head. That submission held the dynamic TLAS's build when the frame built one, or else the frame's own command buffer, and nothing ordered either TLAS build after the copies.

A model of the race

The demo below models the submission that carried the race in a frame that builds no dynamic TLAS: the pending writes, holding one compaction copy, and the frame's command buffer, whose TLAS build reads the copy's BLAS. The slider adds other devices' work to the same GPU, and the two switches are the two ways to order the pair. It is a model to watch the mechanism in, not a measurement.

What it would have cost

The static TLAS is built from the first Frame data and rebuilt only in a frame that changes a static Instance or frees one's slot (StaticTlas, src/render/acceleration_structures.rs). A Mesh whose BLAS lost the race would have cast no ray-traced shadow until the static TLAS's next rebuild, which, in a scene where nothing static changes, never comes. The dynamic TLAS, built in render in that same frame, had the same exposure for a Moving Instance whose Mesh had just loaded. It is rebuilt in every frame (#204), though, so its next build would have read the BLAS again. The fix covers both.

The fix changes no Golden: no Reference scene renders differently with it, by PR #267's verify run. The race needed the GPU busy with other work to show, as in #244's failing runs, where that work came from other processes or from the library's own parallel tests.

Chapter 6 · the work on #244

Make it fail, then cut

A race that shows once in a few runs is hard to study, since every experiment needs dozens of runs to say anything. So the work on #244 first made it fail often, by running the test's GPU steps on eight threads at once, each with its own device. Then it changed one step at a time and counted the misses. The change that stopped them named the race; the change that did not showed where a wait comes too late.

A loop that fails every run

The loop was a temporary test, ignored by default and never committed. It ran the flaky test's GPU steps, from loading the two Meshes to the trace, on 8 threads, 10 times each, so 80 traces a run, in about 0.7 s. Each iteration made its own headless context, so each thread drove its own wgpu device on the one GPU. Every run of it missed:

So the race needs other devices loading the GPU at the same moment, and the more of them, the more often it loses. The loop was also a test that turned red within a second, every time, which the next step needs.

One step at a time

With a red loop in hand, each variant below changed one thing about the test's steps and ran three times, 80 traces each, on 8 threads. Choose one to see its steps, where the CPU waits, and which write is left unordered with the TLAS build.

Read together, the cuts name the race. The TLAS build reads its BLAS before the last GPU write to that BLAS has finished: the BLAS build itself when nothing waits after it, the compaction copy when the build is waited for. A CPU wait after that last write ends the misses. A wait after the TLAS build, just before the trace, changes nothing, because by then the TLAS is already built. And the degenerate first Mesh played no part.

The regression test

The loop became a test that stays, a_tlas_built_after_compaction_holds_its_blas_while_other_devices_load_the_gpu, in src/assets/pools.rs. Eight threads, each with its own device and a Mesh pool whose Arenas hold 4 KiB each, load a triangle Mesh, compact its BLAS and trace it, 25 times over. Without the fix it failed every run: 20 of 20 with full-size Arenas, then 10 of 10 once the review had shrunk them, since eight pools of full Arenas took 660 MiB. With the fix it passed 20 of 20 both times, and it takes 0.18 s on the M4 Pro. The ticket asked for a reproducer that fails at least one run in four before the fix and passes 20 consecutive runs after it. The stress loop, after the fix, missed 0 of 1,600 traces in 20 runs.

The review also made both tests read the BLAS through MeshPool::blas, as the renderer does, rather than from the pool's own list. On CI's lavapipe the library's tests now take 38.4 s against main's 24.3 s, about 14 s more. PR #267 first read the new test as a guard for Metal alone, saying Vulkan places the barrier. That holds after a BLAS build, where wgpu-core asks for a barrier (chapter 4), but not after the compaction copy. wgpu-core 30.0.1 records no barrier after it, and the barrier before a TLAS-only build has shader reads as its source. The barriers wgpu-core records around a TLAS's buffer of entries cover only that buffer. So on hardware Vulkan no barrier makes the copy's writes visible to a TLAS build either, and the wait does that on every backend. The PR's text was corrected after merge, and PR #270 corrected the code comment.

What it does not show

The original scenario did not come back on the day of the fix. With the fix reverted and the new test skipped, 12 runs of cargo test --lib all passed, as did 12 with the fix in. So the evidence that the fix ends #244's flaky failures is the mechanism, the cuts and the stress loop. The loop stands in for the flaky run because it matches it twice over: the same path, in which Meshes load, the loads are submitted, the BLASes compacted, and a TLAS built in the submission that flushes the pending writes; and the same symptom, [None, None, None]. It is not a before and after of the original failure.

Chapter 7 · PR #267

Wait for the copies, for now

compact_blases already waited for the BLAS builds. Now it also submits the pending writes, where the copies are, and waits for those. It is a CPU wait, so the thread that loads stops until the GPU has finished the copies. It runs only in frames that load Meshes; in three runs of 80 calls on one thread, it added about 0.3 ms to the median call's time. Work that has to be ordered in every frame could not pay that way, and #209 brought such work, which it orders on the GPU instead (below).

The empty submit is what makes the poll useful. The copies sit in wgpu-core's pending writes until something submits, and a poll waits only for work already submitted, so a poll alone would return without waiting for them. queue.submit(std::iter::empty()) sends the pending writes as a submission of their own, and the poll then waits for it.

What it costs

Timed on one thread, 80 calls a run and three runs, compact_blases took a median of 4.0 to 4.6 ms before the fix and 4.5 to 4.7 ms after, about 0.3 ms more; other work on the machine was loading the GPU at the time. It runs only in frames that load Meshes, which today means frame 0, and on every backend. No bench measures such a frame: every run counts its counters from frame 8, and the runs that record Baselines time their frames after 248 warm-up frames. So no Baseline moves, and every counter matches.

Other ways to order the pair

A CPU wait is the bluntest tool. It suits work that happens once, at load, and it does not suit work in every frame. The pair can also be ordered on the GPU, which lets the CPU go on:

Why the event route is delicate

wgpu-hal 30.0.1's Metal queue can stage a wait or a signal on an MTLSharedEvent for the next submit. Its doc comments carry two warnings. Staging is queue-wide: "any add_wait_event call is consumed by whichever Queue::submit runs next on this queue". And by default the wait is encoded on a command buffer of its own, which "does not strictly gate subsequent user command buffers when those CBs share no Metal-tracked resources with it": this race exactly. Strict ordering needs enable_strict_event_sync, at "one extra encodeWaitForEvent per command buffer plus one extra internal command buffer per submit".

#9215's last comment, from 2026-10-13, reports another application's experience. It had built this event workaround and then removed it: a worker thread could submit between staging the signal and submitting the BLAS's command buffer, take the signal, and leave the TLAS waiting for unrelated work. A lock around its own submits could not cover the submits that wgpu-core makes by itself, for example when mapping a buffer with pending writes. It fell back to a CPU poll on Metal after each frame that rebuilds a BLAS, and accepted that the wait "stalls the render thread through the producer and earlier queued GPU work".

What #209 has to solve

#209 refits each crowd Mesh's BLAS in every frame through wgpu-hal on Metal, and the dynamic TLAS, rebuilt in every frame, is then built from those BLASes. A refit writes the BLAS and the TLAS build reads it by ID: the same unordered pair, in every frame instead of at load. A CPU wait there would stall the main thread, which records and submits every frame (ADR 0016), in every frame. So ordering on the GPU is the likely route: the upstream fence fix, if a wgpu release ships it in time, or events through wgpu-hal.

For events, Praxis starts with one thing in its favour: only the main thread submits, presents or polls (ADR 0016), so no worker can take a staged signal. The submits that wgpu-core makes by itself remain, so #209 would have to stage and submit with nothing in between that could submit, and choose whether it needs strict mode. (It took events, in strict mode. Since PR #289, merged on 2026-10-26 as 66b5b57, the submission that holds the refits signals a Metal shared event as it completes, and the dynamic TLAS's build waits for that event on the GPU; the frame waits on the CPU only where no shared event can be made. The owner then chose the crowd's per-bone shadow proxies for milestone M7, so the refit stays behind its Render switch. BLAS Refit Explained tells that story.)

The project's roadmap issue, #17, keeps the rest as a one-line note for later work, "Metal BLAS-to-TLAS ordering": drop the wait only when a wgpu release orders a TLAS build after compaction copies on every backend. #9215 is Metal's alone, and wgpu-core 30.0.1 records no barrier after the copy on any backend. That is a version bump and so the owner's call. Revisit when milestone M4 streams Meshes during play, "where each load frame stalls on the GPU twice". It ends where this chapter does: #209's per-frame refit "needs an order of its own", which PR #289 has since given it.

Glossary

Queue
Where command buffers are submitted; it keeps their order of submission and does not wait for one to finish before the next starts.
Command buffer
A batch of GPU commands recorded on the CPU and submitted in one piece.
Submission
One call to Queue::submit, with wgpu-core's pending writes ahead of its command buffers.
Pass
A run of commands of one kind, recorded through one encoder.
Pending writes
wgpu-core's own command buffer of copies, sent ahead of yours in the next submission.
Poll
Device::poll; with a wait, it blocks the CPU until the most recent submission has finished.
Hazard
Two accesses to the same memory, at least one a write, with nothing to order them.
Read after write
The hazard in which a read must wait for an earlier write to finish.
Barrier
A recorded command that makes later GPU work wait for earlier work's writes.
Hazard tracking
Metal's automatic ordering, for tracked resources that work binds directly.
Tracked resource
A Metal resource whose hazards Metal tracks; device-made resources are tracked by default.
Fence
MTLFence: one pass updates it after its stores, a later pass waits for it.
Event
MTLEvent: a counter one command buffer signals and another waits for; a shared event also reaches the CPU.
Residency set
Metal's list of resources a command buffer may touch; it tracks no hazards.
Resource ID
A number naming a Metal resource from inside a buffer, out of tracking's sight.
Indirect instance descriptor
Metal's TLAS entry layout that names its BLAS by resource ID; wgpu-hal uses it for every TLAS.
wgpu-core
wgpu's layer that validates calls, tracks resources and asks for barriers, for every backend alike.
wgpu-hal
wgpu's layer that turns wgpu-core's requests into one backend's commands.
BLAS
Bottom-level acceleration structure: the GPU's search structure over one Mesh's triangles.
TLAS
Top-level acceleration structure: the GPU's search structure over Instances, each placing a BLAS with its transform.
Static TLAS
The TLAS of every static Instance whose Mesh rays trace, built at load and rebuilt only in a frame that changes one (#202).
Dynamic TLAS
The TLAS of at most 10,000 Moving Instances, rebuilt every frame (#204).
Compaction
Copying a built BLAS into a smaller one that replaces it; wgpu-core records the copy into its pending writes.
Refit
Recomputing an acceleration structure's bounds in place, keeping its tree; not in wgpu-core 30.
Load staging
Praxis's encoder of load-time copies and BLAS builds, submitted ahead of the next frame's work.
Custom data
A number a TLAS entry carries and a hit reports; Praxis stores the Instance's slot.
Device
A wgpu connection to one GPU, with its own queue.
Flaky test
A test that passes on some runs and fails on others, with the same code.
Stress loop
A test run many times at once to raise a race's rate until every run fails.
Cut
One step of the test changed or removed, to see whether the failures stop.
Mesh
An ordered list of Primitives that are rendered together.
Instance
One Renderable's data on the GPU, in a slot of the Instance buffer that the Renderable keeps while it is one.
Golden
A committed image that a Reference scene must reproduce within tolerance.
Baseline
The recorded measurements of a Reference scene on one adapter.
