The HDR target

The single-sample Rgba16Float target that the lit pass's 4x MSAA colour resolves into, holding each pixel's exposed colour, clamped to fp16's range and weighted by 1 / (1 + its luminance) so that the hardware's plain average of the samples comes out as an average weighted the way a display shows them; the tonemapping pass reads it and undoes the weighting.

Describes main at fbae12f4 (2026-11-04). A change to the target rewrites this page and moves the commit; nothing is appended. Read first: Lit Pass for the shading whose colour the target stores, HDR Pipeline Explained for the light units and the EV100 exposure, MSAA Fragment Merging Explained for a pixel's samples and its fragments.

Interface

Created
By RenderTargets::new with every other size-dependent target, at the frame's size, and again on every resize; the tonemapping pass then rebuilds the bind group that reads it.
Written
By the lit pass, as the resolve target of the multisampled colour: a transient 4x HDR_FORMAT attachment, cleared to the scene's background exposed and weighted, drawn into by the lit pass's fragment shaders, resolved into the HDR target when the pass ends, and its samples discarded.
Read
By the tonemapping pass, one texel per pixel with textureLoad, through group 3, tonemapping input.
Format
HDR_FORMAT, Rgba16Float, for both the target and the multisampled colour, which the Capability floor checks renders and resolves at 4x.
Shader
src/render/shaders/hdr.wgsl, a part of the main pass's module and the tonemapping pass's: LARGEST_HALF, relative_luminance, resolve_weighted and resolve_unweighted.
Counted
In the render targets' GPU memory: 8 bytes a pixel for the target, and 32 for the multisampled colour where a transient attachment takes memory, none where the adapter reports that it saves it.

1 · fs_main, src/render/shaders/main.wgsl

Exposed, then clamped

Light is shaded in f32 in photometric units, whose range fp16 cannot hold. The lit pass multiplies by the camera's exposure before anything is stored, then clamps to fp16's largest finite value, so every backend stores the same number.

Luminance leaves the shading in cd/m². Under the Reference scenes' sun of 100,000 lx, a dielectric's sun glint at roughness 0.04 peaks at 1.24×108 cd/m², 10.9 stops past fp16's 65504. The exposure, camera.exposure, is 1 / (1.2 · 2EV100); every Reference scene sets its EV100 so that the sun's illuminance exposes to 1, which makes the exposure 10−5. The glint then stores as 1,240 and a white surface in full sun as about 0.32.

    // Pre-exposed in f32 and clamped to fp16's range before the HDR target
    // stores it (ADR 0023), weighted for the resolve.
    let exposed = min(luminance * camera.exposure, vec3<f32>(LARGEST_HALF));
    return vec4<f32>(resolve_weighted(exposed), surface.opacity);

The tail of the lit pass's shading, main.wgsl.

The clamp is the same for every path that writes the attachment. A shader that overflows fp16 on write gets infinity on Vulkan, which may store it, while the Apple M4 Pro saturates to 65504; and an infinite sample can turn into black patches. The background is exposed on the CPU, in prepare, from the Environment's background luminance, and RenderTargets::color_attachment clamps it to the same 65504 before it weights it as the shaders do.

2 · resolve_weighted

Weighted for the resolve

The hardware resolves 4x MSAA by a plain average. Over exposed colour, one bright sample swamps an edge pixel and it tone maps to white. Each sample is stored divided by one plus its luminance instead, so the hardware's plain average, undone, is an average that weights each sample by 1 / (1 + Y).

fn relative_luminance(color: vec3<f32>) -> f32 {
    return dot(color, LUMINANCE_COEFFICIENTS);
}

fn resolve_weighted(color: vec3<f32>) -> vec3<f32> {
    return color / (1.0 + relative_luminance(color));
}

hdr.wgsl. LUMINANCE_COEFFICIENTS, ITU-R BT.709-6's 0.2126, 0.7152 and 0.0722, is declared into the WGSL from targets.rs.

Y is linear in the colour, so the plain average of c / (1 + Y) has luminance equal to the average of Y / (1 + Y), and one minus that is the average of 1 / (1 + Y). Dividing the stored average by it leaves the weighted mean:

stored = c / (1 + Y(c)) resolved = average(stored) / (1 − Y(average(stored))) = Σ wᵢ cᵢ / Σ wᵢ, wᵢ = 1 / (1 + Yᵢ)

A thin wire of exposed 100 that covers one of a pixel's four samples, over a background of 0.05, averages to 25.04 by the box, past white once tone mapped; weighted, the same four samples resolve to 0.395, close to what the background around the wire shows. A stored luminance, Y / (1 + Y), stays below 1, but the stored colour still needs fp16: a saturated colour's channels can pass 1, and every bright sample's luminance is stored just under 1, where only fine steps tell one from another.

3 · RenderTargets::new · color_attachment

The attachment and the target

The four samples live only inside the lit pass: the multisampled colour is a transient attachment whose samples are discarded once the pass has resolved them, so on a tile-based GPU they need never reach memory. Only the resolved target, one texel per pixel, outlives the pass.

color: target(
    "Multisampled Colour Texture",
    HDR_FORMAT,
    SAMPLE_COUNT,
    wgpu::TextureUsages::RENDER_ATTACHMENT | wgpu::TextureUsages::TRANSIENT_ATTACHMENT,
),
hdr: target(
    "HDR Texture",
    HDR_FORMAT,
    1,
    wgpu::TextureUsages::RENDER_ATTACHMENT | wgpu::TextureUsages::TEXTURE_BINDING,
),

RenderTargets::new, targets.rs.

The lit pass takes the multisampled colour as its one colour attachment from color_attachment, which clears it to the background, clamped and weighted, names the HDR target as its resolve target and discards its samples, as a transient attachment's must be.

let [red, green, blue] =
    [clear.r, clear.g, clear.b].map(|channel| channel.min(largest_half));
let coefficients = LUMINANCE_COEFFICIENTS.map(f64::from);
let luminance = coefficients[0] * red + coefficients[1] * green + coefficients[2] * blue;
let weight = 1.0 / (1.0 + luminance);
wgpu::RenderPassColorAttachment {
    view: &self.color,
    resolve_target: Some(&self.hdr),
    depth_slice: None,
    ops: wgpu::Operations {
        load: wgpu::LoadOp::Clear(wgpu::Color {
            r: red * weight,
            g: green * weight,
            b: blue * weight,
            a: clear.a,
        }),
        store: wgpu::StoreOp::Discard,
    },
}

RenderTargets::color_attachment, targets.rs.

Both are created at the frame's size by RenderTargets::new, which a resize calls again. A bind group is a snapshot of the views it was built with, so the tonemapping pass builds the group that reads the target in one function, at creation and again after every resize.

4 · resolve_unweighted · fs_tonemap

Undone in the tonemapping pass

The tonemapping pass loads each pixel's resolved texel and divides by one minus its luminance, which turns the hardware's plain average back into exposed colour averaged by weight.

fn resolve_unweighted(weighted: vec3<f32>) -> vec3<f32> {
    let complement = max(1.0 - relative_luminance(weighted), 1.0 / LARGEST_HALF);
    return min(weighted / complement, vec3<f32>(LARGEST_HALF));
}

hdr.wgsl.

Rounding can bring a resolved luminance to 1 or past it, where the division would give infinity or a negative colour, so the complement is held at 1 / 65504 at least and the result clamped to 65504 again. From here the colour is exposed colour, as the lit pass computed it, and the tonemapping pass maps it for display (The tonemapping pass).

6 · gpu_memory_bytes

What it costs

The target is memory, not a pass: 8 bytes a pixel, and four times that again for the samples wherever a transient attachment takes memory. Its time is spread over the passes around it, too small to see in their Baselines: the weighting is a division in the lit pass and its inverse one in the tonemapping pass.

7 · ADRs 0008, 0019, 0021, 0023

Why this way

Pre-exposure, then fp16. ADR 0023 makes light photometric, so values span more stops than fp16 holds. Shading in f32 and storing only the exposed result is the practice of engines with physical light units; it keeps an 8-byte target where storing luminance itself would need f32 and twice the memory.

The clamp on every path. Overflow is where the backends disagree: Vulkan's conversion rules allow infinity, the M4 Pro saturates, and Metal's specification leaves it open. Unreal traces black patches on reflective surfaces to an overflowing colour buffer. A clamp to 65504 before every write makes every adapter store the same number.

Rgba16Float over a packed float format. A format of three small unsigned floats in 32 bits halves the memory, but its 5- and 6-bit mantissas shift hue, and the weighting needs precision just under 1: there, the inverse of the largest stored luminance caps near 2,000 in fp16 and near 127 in 11-bit floats.

The weighted resolve over the box. A plain box resolve of exposed colour is physically an average of light, but tone mapped it turns bright sub-pixel detail into white stair steps. Karis's reversible weighting makes the hardware's own resolve behave like an average after tone mapping, at a division per sample, and keeps ADR 0019's 4x MSAA memoryless.

The hardware resolve over a shader resolve. Storing the samples and resolving them in a shader would allow any filter, at 117,964,800 bytes more at 1440p and with the samples reaching memory, which ADR 0019's memoryless 4x rules out.

A fixed EV100 per scene. ADR 0023 has each Reference scene set its exposure by hand, which keeps Goldens exact; histogram adaptation waits for a scene that needs it. ADR 0008 keeps screen-space history out of the frame, so nothing about the target carries from one frame to the next.

8

Limits

Sub-pixel highlights lose energy. A glint that covers one sample counts for less than its quarter of the pixel, since its weight is the smallest of the four.

Blending happens in the weighted space. A fragment that blends over another blends their weighted colours, which darkens a 50% blend; no Reference scene blends yet, and transparency will have to blend before weighting or in a pass of its own.

Three channels, Rec. 709 primaries. The target holds colour in the scene's primaries and the luminance weights are Rec. 709's; a wider-gamut working space would change both.

SDR only downstream. The target holds values past display white, but nothing reads it for an HDR display: the tonemapping pass maps it to SDR.

History

The target came with the move to photometric light in the third milestone: first an fp16 target behind a clamp-only pass, then the weighted resolve, after a plain one whitened bright edges, then the tonemapping pass it feeds. The development narrative, with each step's measurements and the operator survey, is in the notebook's volumes until the pages absorb them: Tonemapping Pass Explained and HDR Pipeline Explained. This page describes the target as it is; the volumes describe how it got here.
