Praxis · after the frame · src/bench/mod.rs

The bench

The command that renders a Reference scene along its camera path twice, with shadow rays on and off, and reduces every frame's Frame stats to one record of medians, p95s and counters; its two companions judge such a record against the scene's committed Baseline and the Budgets, and print it as the markdown tables a PR quotes.

Describes main at 7b8009ee (2026-11-05). A change to the bench, to what it compares or to how a record is kept rewrites this page and moves the commit; nothing is appended. Read first: The Reference scenes for the camera paths and injected time a run follows, Frame stats for the per-frame figures it reduces, Waiting on the GPU Explained for why the bench's main thread spins rather than blocks.

Interface

Runs
praxis bench <output directory> [--ci | --counters | --ci-counters] [--skip-aliasing] [--no-publish | --experiment <name>] [<scene>...], on a headless GPU context, every scene whose assets are present when none is named; then praxis compare <bench directory> [--ci] and praxis report <bench directory>, which run no GPU. The verify command runs the first two with --counters, --no-publish and --ci; CI runs them with --ci-counters.
Reads
The scene through render_frames: its camera path and injected time at a 60 Hz frame delta, with the default Render switches and again with shadow_rays off; every frame's Frame stats, GPU stats included; the checkout through git and the machine's load through preflight, once before the first scene; bench/budgets.json; the Baseline at bench/baselines/<adapter key>/<scene>.json.
Writes
One <scene>.json per scene into the output directory, a Measurements in pretty JSON, and one line of its figures to standard output; a crowd form other than the default writes crowd-<form>.json. compare prints a line per scene and per finding and exits non-zero when any metric failed; report prints markdown tables.
Compared
Times by their median against the Baseline's, warning past 5% and failing past 10% and a noise floor, and against the Budgets; counters exactly, any increase failing; the two aliasing counters by the same ratios with no floor. With --ci, counters alone.
Published
Unless given --no-publish, the results join the Bench history as Bench records, under an Experiment's name with --experiment; a failed publish warns and fails no bench.
Where in the code
src/bench/mod.rs: Configuration, run, measure, Measurements, Counters, Aliasing, compare and its checks, baseline_directory. src/bench/provenance.rs: BenchStart, Provenance, Checkout, source_hash, HARNESS_VERSION. src/bench/report.rs: report. src/capture/mod.rs: render_frames and FrameWait. src/bin/praxis.rs: the three commands' arguments. scripts/verify.sh: the bench step.

1 · Configuration · run · src/bench/mod.rs

A run: two passes along the camera path

A run renders the scene along its camera path with injected time, so every frame is the frame the Baseline measured, for a warm-up and a measured stretch whose lengths and size a Configuration fixes. It renders the whole stretch twice, with shadow rays on and then off, because two of its lines, the gate and shadow-ray time, need the frame without rays.

Four configurations exist, each with the size, the warm-up and the measured frames, and whether the run measures aliasing. The reference one is what praxis bench runs by default and what every Baseline on a hardware adapter holds.

src/bench/mod.rs

The wait on the oldest frame

render_frames keeps up to FRAMES_IN_FLIGHT frames, two, in flight, as a window's swapchain allows, so the GPU stays busy and the CPU never runs further ahead than a window would. Before it records a third, it waits for the oldest. How it waits is the FrameWait its caller passes: the Goldens' captures block, as a window does in get_current_texture; the bench polls the device with a zero timeout and spins until the frame is done.

/// How `render_frames` waits for the oldest frame in flight.
#[derive(Clone, Copy)]
pub(crate) enum FrameWait {
    /// Blocks, as a window does in `get_current_texture`.
    Block,
    /// Polls until the frame is done. Behind a GPU-bound frame, the M4 Pro
    /// runs a main thread that blocks markedly slower for the whole next
    /// frame (measured: `docs/performance.md`, Measurements behind the
    /// code), so its CPU times would measure the clock, not the work. Apple
    /// asks games not to busy-wait, which holds a P-core and spends thermal
    /// headroom [ref:apple-tech-talk-110147-busy-waits], so only the bench
    /// spins, on a hardware adapter.
    Spin,
}

The bench spins because the CPU Budgets price the main thread's work when it is on the critical path. Behind a GPU-bound frame it is not, and on the Apple M4 Pro a main thread that blocks there runs the whole next frame on a slower clock, so a blocked bench reads the clock rather than the work. Spinning holds a performance core for the minutes a bench lasts and spends the thermal headroom a game's GPU would want, which is why only the bench spins, and only on a hardware adapter: lavapipe rasterises on the CPU, where a spinning thread would take a core from it. The window keeps blocking. Waiting on the GPU tells how the clock was found.

The counter frames

Every run, whatever its length, also records the counters of one fixed window of frames, so a run of 72 frames compares its counters with a Baseline of 2,048.

src/bench/mod.rs
/// The frames whose counters every run also records, whatever its length:
/// counters repeat exactly on every run, so runs of different lengths
/// compare on these. By the eighth frame the Scene's uploads and the first
/// frames' allocations are over. Baselines record the frames, so
/// moving them refuses every Baseline until it is re-recorded.
const COUNTER_FRAMES: std::ops::Range<u32> = 8..72;

The window is absolute: frames 8 to 71 of the run, which in the reference configuration lie inside the warm-up. The counters-only configurations are exactly that window, with a warm-up of 8 and 64 measured frames, so their measured frames and their counter frames are the same frames.

2 · measure · Measurements · Spread

What is measured

A record holds, for each time, its median and p95 over the measured frames, and for each counter one value: the median over the measured frames and again over the counter frames. Nothing is a mean, and nothing reads the wall clock.

measure takes the two runs' Frame stats and fails unless every frame of both read back its GPU stats. It drops the warm-up and reduces the rest. The lines, as a Measurements holds them and as the Baselines spell them:

Counters

The eight counters are draw_calls, instances_drawn, triangles_drawn, instances_overflowed, uploaded_bytes, gpu_memory_bytes, arena_bytes_in_use and heap_allocations, in the order Counters::NAMES gives and a test holds the JSON to. Each is the median of its frames but one: Instances overflowed is the most of any frame, so a single frame whose draw had no room for an Instance counts.

Median and p95

A Spread is a median and a p95, both by nearest rank: the values sorted, and the smallest one with at least the fraction at or below it. Over 1,800 measured frames the median is the 900th smallest value and the p95 the 1,710th; over the 64 counter frames the median is the 32nd. The rank is a frame that was measured, never a value between two.

src/bench/mod.rs
/// The nearest-rank percentile: the smallest value with at least `fraction`
/// of `values` at or below it.
fn percentile(mut values: Vec<f64>, fraction: f64) -> f64 {
    values.sort_by(f64::total_cmp);
    let rank = (fraction * values.len() as f64).ceil() as usize;
    values[rank.clamp(1, values.len()) - 1]
}
3 · Aliasing::between · measure_aliasing

The aliasing counters

Two counters measure how far one frame of the scene lies from the same frame rendered at three times its size and box-filtered down in linear light. The reference is the engine's own render, so they measure aliasing, not bias; they are integers in millionths, so they compare as counters do.

A configuration that measures aliasing captures the scene twice more after its two runs, through capture, which renders 60 frames and reads the last back: once at the Goldens' size, 640×360, and once at 1920×1080, both with the run's switches. The frame captured, the 60th, lies inside the counter frames. Each pixel of the small image is set against the mean of the 3×3 block of the large one that covers it, every value decoded from sRGB to linear light first, through the EOTF the Khronos data format specification gives.

A pixel's error is the mean of its three channels' squared differences; alpha is no channel of it. aliasing_rmse is the root of the mean of every pixel's error, the whole image's distance; aliasing_p99 is the root of the 99th-percentile pixel's error, the worst hundredth of the image: a few sparkling highlights move it where they barely move the first. Both are rounded to millionths of the unit range. The two counters are written into the record only when measured, so a record from a run that skipped them has no such keys, and a Baseline without them is distinguishable from one that measured zero.

4 · BenchStart · Provenance · src/bench/provenance.rs

Provenance: what was measured, where, and how quietly

A record names the source it measured, as one git tree hash over the paths that can change a measurement, the adapter, backend and driver, the Harness version, the Cooked cache's hash of the Blobs the scene loaded, and whether the machine was quiet. compare reads one field of it, the load average, to print beside a CPU line it fails; the rest is for the Bench history.

BenchStart::read runs once before the first scene: it reads the checkout, and the GPU utilisation, the one-minute load average, the other praxis processes and preflight's power and display warnings while no scene runs, since a reading taken right after a scene would include that scene's load. Since 2026-11-08 each scene also lists the busy processes at its start and end, which leaves praxis's own processes out by name and process ID and so reads none of the scene's load. A checkout git cannot read, such as a run outside a repository, warns and leaves the results without Provenance; such a result is skipped at publish.

src/bench/provenance.rs
/// Names what the bench's metrics mean: raised by any change to how a
/// metric is measured, so that two Bench records compare only when they
/// share it. The lower versions name the eras before the Bench history,
/// numbered by its import of the Baselines from 1.
pub const HARNESS_VERSION: u32 = 10;

/// The top-level paths whose changes can change a measurement, which the
/// source hash covers. Every other tracked top-level path is in the tests'
/// `UNMEASURED_PATHS`.
const MEASURED_PATHS: [&str; 5] = ["src", "assets", "Cargo.toml", "Cargo.lock", ".cargo"];

/// A scene's GPU frame p95 over its median at or above which its run was
/// not quiet, whatever preflight saw at its start.
pub(super) const QUIET_P95_OVER_MEDIAN: f64 = 1.06;

The source hash

The Checkout holds the commit, the branch, whether a measured path differed from the commit, untracked files included, and the source hash. source_hash asks git for the tree entries of the measured paths at a revision and has git mktree hash them as one tree, so a commit that changes none of those paths has the hash of the commit before it, and a docs-only commit measures as its parent. A dirty checkout hashes its working tree instead: the measured paths are staged as git add --all would stage them, through a temporary index under GIT_INDEX_FILE, so the checkout's own index stays as it is.

source_hash, src/bench/provenance.rs
pub fn source_hash(repository: &Path, revision: &str) -> anyhow::Result<String> {
    let listing = git(
        repository,
        &[
            &["ls-tree", "--full-tree", revision, "--"][..],
            &MEASURED_PATHS[..],
        ]
        .concat(),
        None,
    )?;
    // An empty tree is no input at all: mktree refuses a blank line.
    let entries = if listing.is_empty() {
        listing
    } else {
        listing + "\n"
    };
    git(repository, &["mktree"], Some(&entries))
}

A run was quiet when preflight would have warned of nothing at its start, the scene's GPU frames held steady and, since 2026-11-08, no process outside praxis held half a core or more at the scene's start or end. 5 · compare · check_regression · check_budget

Compare: medians against the Baseline, every line against its Budget

A time regresses by its median: past 5% of its Baseline it warns, past 10% it fails, but only when it also grew by more than a noise floor, since a short time moves by more than the ratios between runs. A counter fails on any increase, because it is the same on every run. A Budget fails whatever the Baseline says.

praxis compare reads every result in the directory, finds each one's Baseline by its adapter and backend, and runs compare in one of two modes: Local, every metric, and Ci, with --ci, the deterministic counters only, since times depend on the machine and its load. It prints ok for a clean scene, else one line per Finding, warn or FAIL with the metric and its detail, and exits non-zero when any failed.

What refuses a Baseline

ensure_comparable runs first in both modes and in report: the Baseline must be of the same scene, profile (debug or release, whose allocations differ) and size, and must have counted the same counter frames. A Baseline in another form, from a version of the bench that spelled its records differently, is refused earlier, by Measurements::from_baseline_json, with a message to re-record it. In Local mode two more checks follow the counters: the run and the Baseline must have measured as many frames, since their times cover other frames otherwise, and must have run on the same adapter through the same backend; and before the passes are compared, the run's timed passes must be the Baseline's, else the Baseline is re-recorded.

compare, src/bench/mod.rs
    ensure_comparable(current, baseline)?;
    let (counters, baseline_counters) = compared_counters(current, baseline);
    let mut findings = Vec::new();
    for ((metric, current), (_, baseline)) in
        counters.named().into_iter().zip(baseline_counters.named())
    {
        if current > baseline {
            findings.push(Finding {
                metric,
                verdict: Verdict::Fail,
                detail: format!("{current} against Baseline {baseline}"),
            });
        }
    }
    check_budget(
        &mut findings,
        "gpu_memory_bytes",
        current.counters.gpu_memory_bytes as f64,
        budgets.gpu_memory_bytes as f64,
    );
    check_aliasing(&mut findings, current.aliasing, baseline.aliasing);
    if mode == CompareMode::Ci {
        return Ok(findings);
    }

Which counters compare depends on the lengths: runs that measured as many frames compare their measured frames' counters; runs of other lengths compare their counter frames', the window of section 1. That is how the verify command's 72-frame run and CI's judge their counters against Baselines of 2,048 frames.

Ratios and floors

/// `docs/performance.md`, Measurements behind the code).

A time that did not grow passes whatever its sign. From a Baseline at or below zero any growth is past every ratio, so it is the floor alone that judges it: this is the rule for shadow-ray time, whose median can read below zero where the rays cost little, so that a frame's worth of noise in either direction neither fails a scene nor hides a real rise. A growth past 10% that stays within the floor only warns.

What compare judges in Local mode, in its order; in Ci mode the first two rows alone. The GPU frame answers to its Baseline as well as each pass, so a frame that grew within every pass's tolerance still fails; the CPU frame's p95 answers to the Budget because that Budget bounds the frame's p95 as well as its median.

Aliasing has no floor: on the M4 Pro two runs of every Reference scene measured equal aliasing counters, so a rise past the ratios is a change of the image. A run that skipped them passes; a run that measured them against a Baseline without them fails both, with a message to re-record the Baseline, since the Baseline cannot say whether the image changed.

Last, a failed CPU line gains the one-minute load average both runs started under, unknown for a record without Provenance, because CPU times move with the machine's load where GPU times hold: a reader of the line sees at once whether the run or the machine was slower.

Publishing

After the scenes are written, praxis bench publishes them as Bench records on the bench-history branch, unless given --no-publish; with --experiment they publish under that name, on no Series. A publish that fails warns, names the praxis publish command that retries it, and fails no bench; the verify command and CI's pull-request runs never publish. The history observes and never gates: The Bench history says what a record becomes there.

6 · report · src/bench/report.rs · scripts/verify.sh

Report, and the verify command's bench step

praxis report prints each result as markdown tables against its Baseline and the Budgets, so no figure a PR quotes is retyped by hand. The verify command benches the counter frames alone and compares counters only, since counters repeat exactly and times do not.

A report opens with one line naming the scene, adapter, profile, size and measured frames, then three tables: the times, with each line's median and p95, the Baseline's, the delta and ratio of the medians and the Budget where one applies; the gate's passes with the lit pass's wait, their medians' sum and the gate itself, when the record carries them; and the counters, with the aliasing counters after them when measured. Times compare only with a Baseline of as many frames on the same adapter; a Baseline of another scene, profile, size or counter frames is refused as compare refuses it, and a result with no Baseline gets a line saying why and tables of its own figures.

The verify command's bench step

scripts/verify.sh runs after formatting, lint, build and the tests. It lists every scene that has a Baseline on any adapter, so a fetched helmet does not fail for lack of one, benches them with --counters and --no-publish into target/verify/bench, and compares with --ci. Aliasing renders each scene twice more, so it is measured only when the branch's diff against main, or an untracked file, touches what can change the image: src/render, src/cook, src/scenes or assets. 7 · BASELINE_DIRECTORY · baseline_directory · bench/baselines

Baselines

A Baseline is a bench result committed under its adapter and backend's directory, and a run compares only with the Baseline of its own adapter and backend, so no machine's times judge another's and no API's judge another's. Re-recording one is running the bench with that directory as its output.

The directory is the adapter's name in lowercase with each run of other characters a hyphen, then the backend's name unless it is Vulkan or Metal: those lead the engine's backend order, so an adapter runs on one of them unless WGPU_BACKEND asks for another, and the suffix marks the ones that were asked for.

src/bench/mod.rs
pub fn baseline_directory(adapter: &str, backend: &str) -> PathBuf {
    let default_backend = [wgpu::Backend::Vulkan, wgpu::Backend::Metal]
        .iter()
        .any(|default| default.to_str() == backend);
    PathBuf::from(BASELINE_DIRECTORY)
        .join(adapter_key(adapter, (!default_backend).then_some(backend)))
}

/// `adapter`'s name in lowercase, each run of other characters a hyphen,
/// then `backend` when given.
fn adapter_key(adapter: &str, backend: Option<&str>) -> String {
    adapter
        .to_lowercase()
        .split(|character: char| !character.is_ascii_alphanumeric())
        .chain(backend)
        .filter(|word| !word.is_empty())
        .collect::<Vec<_>>()
        .join("-")
}

10 · ADRs 0013, 0019, 0020, 0022, 0024

Why this way

Medians over a fixed camera path, not frames per second. ADR 0013 sets the Budgets as per-frame times at 1440p on the reference machine, and ADR 0019 phrases its gate as the median over the scene's camera path. A Reference scene's injected time means frame 700 is the same frame on every run and on every machine, so a median over it is a property of the code, where a frame rate over wall-clock seconds is a property of the run. The p95 is kept beside the median for the tail, and judged only where ADR 0013 bounds the tail, the CPU frame.

Counters exactly, times by ratio and floor. Counters repeat exactly from run to run, so any increase is a change in the code and fails; there is nothing to tolerate. Times move with the machine, so a time is judged by its ratio to the Baseline, with the 5% and 10% set above the noise of GPU medians over repeated runs on the M4 Pro under the owner's usual load. CPU medians of tens of microseconds and short passes move by more than those ratios between runs, so a time fails only when it also grew past a floor in microseconds; within it, it warns.

Two runs, so that the gate reads the main pass. ADR 0019's gate is timed with shadow rays off, since every main-pass design it weighs traces the same rays; with them in, the gate would measure the rays as much as the pass. No pass is only the rays, so their cost is read as the difference of the two runs' frames, and the second run is the price of two lines the first cannot give.

A spin wait in the bench alone. The CPU Budgets price the main thread's work when the frame waits on it. Behind a GPU-bound frame on the M4 Pro a blocked main thread runs the whole next frame on a slower clock, so blocking measures the clock. Spinning measures the work, at the cost of a performance core and the thermal headroom Apple asks games not to spend, which is why the window keeps blocking and lavapipe, which rasterises on the CPU the spin would take a core from, blocks too. Reading the CPU lines from a run with one frame in flight was weighed and set aside: the clock's ramp after each wait stays in the lines, and every scene would run a third time.

Aliasing against the engine's own render, in linear light. A reference from another renderer would measure bias, every place the shading differs, as much as aliasing. The same frame at three times the size, box-filtered down, differs from the frame only where one sample per pixel missed what nine resolve: specular sparkle, shimmering edges, terminator steps. The filter runs on decoded values because the average of two sRGB-encoded bytes is not the encoding of their average light; a test holds the block of three white and six black pixels to a third, not to the 0.0908 the encoded mean would decode to. The counters are integers in millionths so that they compare as the other counters do, and the p99 is kept beside the root mean square because a few sparkling pixels move the one and barely the other.

Baselines gate, the history observes. ADR 0024 keeps every run as a Bench record keyed by source hash, adapter, backend and scene, and draws the quiet ones on a Series, but changes nothing about what fails: Baselines stay on main under bench/baselines, chosen by hand, and compare judges against them as ADR 0013 set. The source hash covers only the paths that can change a measurement, so a docs commit inherits its parent's record rather than earning a run; the Harness version rises with any change to what a metric means, so a redefinition never reads as a regression.

The reference machine judges, the floor compares, CI counts. ADR 0013 judges Budgets on the Apple M4 Pro, benches the RTX 2070 SUPER for comparison on Vulkan and on DX12, and gives no ADR to the floor. CI has no GPU: lavapipe's times mean nothing, but its counters repeat exactly, so CI benches the counter frames alone at the Goldens' size and compares counters only, and its records join a Series whether or not the runner was quiet, since the quiet test judges GPU times it never read.

60 Hz. ADR 0022 keeps the Budgets judged at 60 Hz, the display the measurements ran on, so the bench's frame delta is the window's 60 Hz frame whatever the machine would reach.

11

Limits

A Baseline without the aliasing counters. A run that measured them against a Baseline that lacks them fails both until the Baseline is re-recorded. Only the lavapipe Baselines lack them, and CI's configuration skips them, so the gap fails no run; the DX12 Baselines alone hold Provenance, the lit pass's wait and the gate's passes.

Budgets on every adapter. compare does not know which machine is the reference one, so the RTX 2070 SUPER's town fails the CPU frame's Budget and the dynamic TLAS's CPU ceiling there, lines ADR 0013 judges on the M4 Pro alone.

Harness version unchecked. A Baseline is refused for its form, its scene, profile, size, counter frames, frame count, adapter, backend and passes, not for its Harness version; a Baseline recorded under an earlier version whose records still parse compares as if it were current.

One frame of aliasing, at the Goldens' size. The counters judge the 60th frame at 640×360, not the bench's size or its camera path; aliasing that appears elsewhere along the path, or only at 1440p, is not measured.

Times across backends. report compares times with a Baseline of the same adapter whatever its backend, where compare requires the backend as well.

The dynamic TLAS's CPU line answers to no Baseline. It answers to its Budget alone, so a growth of its cost short of its ceiling is reported, not judged.

The spin wait changes the machine it measures. A busy performance core may take power the GPU would otherwise have; in the town runs behind the choice the GPU frame moved by at most 1.4% across every form of wait, within the ratios but not nothing, so a GPU line compared across the two waits is read with that in mind.

Input latency has no Budget yet. ADR 0013 names one; nothing measures it.

One number per run. The bench records no per-frame series, only the reductions; a frame that was slow once is in the p95 and nowhere else.

History

The bench began beside the Instance buffer's fixed capacity, as a way to prove a change had not moved the counters or the medians: one run per scene, counters held exactly, times by the 5% and 10% ratios with a floor for the short CPU frames, and a scene-order trap found while recording the first Baselines. The dense scene's Baselines brought the second run, with ADR 0019's gate and shadow-ray time read as a difference, the dynamic TLAS build timed from the frame before, and the ceilings on that build. The spin wait came when town's CPU lines on the M4 Pro were found to read a slowed clock behind its GPU-bound frames, told in Waiting on the GPU.
