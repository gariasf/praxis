Praxis · concept · docs/performance.md

Metal quirks

Metal on the Apple M4 Pro, through wgpu 30.0.1, behaves in nine measured ways no specification promises, from merging two triangles' fragments in a pixel to running a whole frame's passes one after another once frames queue, and Praxis's code carries one answer to each: a flat input read to no effect, a scan in place of atomics, a Taylor series in place of a sine, a shared event in place of a barrier, an indirect dispatch at the head of a pass.

Describes main at 7b8009ee (2026-11-05). A concept the pages lean on: what the reference machine's Metal backend does that the specifications do not promise, each measured on the Apple M4 Pro and each with the code that answers it; a new measurement or a change to that code rewrites this page and moves the commit. Pages that use it: The depth pre-pass, MSAA, The lit pass, The culling pass, The bend pass, The BLAS refit, The static TLAS, The shadow mask pass, The depth pyramid pass. Read first: MSAA, for samples and fragments.

1 · fs_surface_normals · coverage_tests.rs

Index-sharing fragments merge unless a flat input is read

Under 2x or 4x MSAA, when a fragment stage reads no flat-interpolated input, the M4 Pro can merge the fragments of nearby triangles of one draw that share vertex indices in a pixel both cover: one fragment, with one triangle's interpolated inputs, writes the samples of both. The samples covered stay exact; which triangle's inputs they receive does not. Reading any flat input stops it.

A fragment's inputs come from its triangle's vertices. Most are interpolated across the triangle; a flat input, declared @interpolate(flat), is not, and every fragment of a triangle reads the value one vertex wrote. A Meshlet's triangles share vertices, and two that meet along an edge name the same two vertex indices; Praxis's packed indices carry the Meshlet record in their high bits, so triangles of different Meshlets or Instances never share an index.

How it was measured

coverage_tests.rs draws quads with sides of 0.3 to 1.5 px into a 256×256 multisampled ID target. The fragment stage writes each sample's triangle ID, and a compute pass reads the target back per sample. The flat scene's 4,096 quads do not overlap, so an analytic oracle knows every sample's owner; it leaves out samples within 0.01 px of an edge, where rounding could go either way. Each quad is drawn as the cooker draws one, 0 1 2 then 0 2 3, so its two triangles, partners, share two indices, and each carries a weight that only its first triangle interpolates and one that only its partner does, so a fragment's smooth inputs alone say which triangle they were interpolated over.

Fragments, not just the index. IDs built from smooth inputs alone depart exactly where primitive_index does, so a merged fragment carries one triangle's interpolated inputs onto the other's samples. A flat input stops it. Every row that reads one departs nowhere, even where the flat value is the same for both triangles: what matters is that the stage reads one, not what it holds. What triggers it. No flat input, shared vertex indices, nearness in the draw and more than one sample per pixel; one triangle between partners still merges most, a partner thousands of triangles later or in another draw call never, and sample-rate shading does not stop it. Coverage is exact. The samples the two triangles cover together do not change; only their attribution moves, and how it moves depends on what else the draw holds, so removing every other quad turns 1,421 into 760.

Fatahalian and colleagues proposed something like it in 2010, as a way to cut the shading cost of small triangles: gather the fragments of adjacent triangles of a mesh and shade them once, with inputs chosen from one of them. Their paper says nothing about flat inputs, and no Apple documentation, talk or forum answer describes the M4 Pro's behaviour. The resemblance is a reading, not a source; a plausible explanation, which no source confirms, is that inputs interpolated across a triangle can be evaluated for a neighbour, while a flat input belongs to one primitive and cannot be shared.

What the code does

A pass that decides from which triangle a sample shows, and a pair of passes that must agree on it, read a flat input. The depth passes write each sample's surface normals that the shadow mask pass traces from, and the lit pass shades the same sample from its own fragment's triangle; the lit pass has always read a flat material_id, so its fragments never merged, and the depth passes read one too, to no effect:

struct DepthNormalsOutput {
    @builtin(position) @invariant clip_position: vec4<f32>,
    @location(0) camera_relative_position: vec3<f32>,
    @location(1) normal: vec3<f32>,
    @location(2) @interpolate(flat) material_id: u32,
}
    // Reads the flat input, so the stage has one the compiler cannot drop,
    // to no effect: Material IDs index the Material table, far below
    // NO_MATERIAL - 1.
    return select(encoded_normals, vec4<f32>(0.0), in.material_id == NO_MATERIAL - 1u);

main.wgsl, the depth passes' vertex output and the end of fs_surface_normals. An input the shader never reads can be dropped by the compiler, and then the stage reads no flat input after all; the comparison with NO_MATERIAL - 1, which is one below the largest u32, never holds for an ID that indexes the Material table, but the compiler cannot bound a value read from a vertex output, so it keeps the read (The depth pre-pass, MSAA).

Invariance could not do it. clip_position is @invariant in every main pass entry point, and wgpu turns on Metal's preserved invariance, but WGSL's attribute and Apple's option cover the position output alone: they make both passes compute the same depth, which they did. The disagreement was over which triangle owns a sample at that depth, and Vulkan's invariance appendix, the most explicit of the three specifications, promises identical fragments only for identical pipelines or across a listed set of state changes; a different fragment shader is not among them.

2 · dpdx · decode_surface

Derivatives are one difference per 2×2 quad

A fragment shader never runs alone: the GPU runs its invocations in 2×2 quads, so each can take a derivative by subtracting a neighbour's value. On the M4 Pro, dpdx and dpdy in the lit pass behave as one difference for the whole quad, from its top left pixel, not as each pixel's own difference.

Where a triangle covers only some of a quad's pixels, the GPU fills the rest with helper invocations, which compute values only so their neighbours can difference against them and whose outputs are discarded. A triangle about a pixel across can occupy a whole quad to shade one pixel, and a pixel on the edge between two triangles is shaded in two quads. WGSL leaves the form open: dpdx returns the same as either its fine form, which differences within each row and column of the quad, or its coarse form, which may use fewer unique positions.

Which form the M4 Pro takes was measured by a prototype that shaded town from per-sample triangle IDs in a compute pass, where no quad exists and the gradients have to be computed by hand. Differencing each pixel against its own right and lower neighbours left 132 to 2,054 pixels of 230,400 more than one 8-bit step from the lit pass's image, over the Goldens' eight frames; differencing from the quad's top left pixel, shared by the quad, left 5 to 617. The per-quad form cut the differences by a factor of 2 to 30, so the lit pass's derivatives are per quad, and a compute pass that must match it differences across the quad. The prototype's image, at its best, differed from the lit pass's at a few thousand pixels on the silhouettes of geometry under a pixel wide.

What relies on it on main is the lit pass's specular filter, which widens roughness by how fast the shading normal turns across the pixel:

    // The normal's change across a pixel widens roughness. The lit pass
    // shades once per pixel under 4x MSAA, not per sample, so these
    // derivatives are per pixel, the footprint the filter assumes.
    let surface = decode_surface(
        material,
        albedo,
        metallic_roughness,
        occlusion,
        emissive,
        dpdx(normal),
        dpdy(normal)
    );

main.wgsl, in fs_main. The same quad gives fs_surface_normals its triangle normal, from the cross product of the camera-relative position's two derivatives, a plane the quad's four invocations share (The lit pass).

3 · exclusive_scan · culling.wgsl

Which triangles precede others changes the image

On the M4 Pro, implicit derivatives at triangle edges depend on how the GPU batches a draw's triangles, so two draws of the same triangles in different orders give different images. The frame's draw is built in slot order within each culling phase, never in the order atomics land, so every run draws the same index stream.

The culling pass's first version appended each Instance's Meshlet records and packed indices through a shared atomic count, so an Instance's place in the draw depended on when its workgroup reached the count. Metal captures of the orrery then moved 64 to 97 pixels from run to run, and equal arguments no longer gave equal images. The geometry was the same in every run: each Meshlet triangle mapped back to the cooked index stream, 2,208 of 2,208, corners in order. With the mip level named explicitly, through a level-sampling call in place of the implicit one, the scene rendered bit-identical three runs out of three. What moved was the implicit derivatives at triangle edges, computed from neighbouring invocations in a quad, which on the M4 Pro depend on how the GPU batches the draw's triangles.

So the pass works each position out from the slots' order and counts alone, with a running sum over each block of slots and one more over the blocks:

// The culling pass's entry points, after the shared parts: they append the
// Meshlets of the Instances they draw to the frame's draw in slot order,
// which the main pass draws with one indirect call per phase and depth
// pipeline, and one of both phases for the lit pipeline (ADR 0019).
// The sum of `value` over the workgroup's invocations before this one, which
// they all call together: a Hillis and Steele scan
// [ref:hillis-steele-partial-sums], read one place back.
fn exclusive_scan(invocation: u32, value: vec2<u32>) -> vec2<u32> {
    scan[invocation] = value;
    for (var stride = 1u; stride < SCAN_BLOCK_SIZE; stride *= 2u) {
        workgroupBarrier();
        var before = vec2<u32>(0u);
        if invocation >= stride {
            before = scan[invocation - stride];
        }
        workgroupBarrier();
        scan[invocation] = saturating_add(scan[invocation], before);
    }

culling.wgsl, its opening comment and the head of exclusive_scan. Atomics remain where order cannot matter: the draw's index count is an atomicMax, its Instance counts atomicAdd, and phase two's visibility words atomicOr, each of which ends at the same value whatever order the invocations run in (The culling pass).

Slot order still moved one Golden once: with all five of the orrery's spheres in one draw, the M4 Pro batched their triangles differently than before, and 80 of the capture's 230,400 pixels moved by more than one step, at most 24, all on the grid texture's lines at triangle edges; software Vulkan's Goldens did not move. The owner accepted the rewritten Metal Golden and the rule, which the review checklist in CLAUDE.md carries: the GPU builds the frame's draw in slot order within each culling phase, never in the order atomics land.

4 · sinc · BEND_ROUNDING_SHARE

Fast math across entry points, and in sine

Metal compiles shaders with fast math by default, and wgpu-hal sets no math mode. The compiler may then reassociate sums and fuse a multiply and an add, so two entry points that test the same value can disagree at its boundary, and sine is accurate only to an absolute error, not to a share of its result.

The Metal Shading Language specification says of its math mode that the default is fast, which lets the compiler assume no NaNs or infinities and allow reassociation and fast floating-point contraction. In f32, (x + y) + z and x + (y + z) can round to different values, and a fused multiply-add rounds once where a multiply then an add round twice. Two entry points compiled separately can each choose. A Meshlet culling prototype met this: counting an Instance's kept indices in one dispatch and writing them in another, each testing the same cone against the same numbers, the count could say kept and the write say dropped for a Meshlet within a rounding step of its boundary, leaving a gap of indices nothing wrote, or an overrun. The prototype tested each Meshlet once and wrote the answer down; the culling pass on main tests each Instance once, in the dispatch that counts its records, and every later step reads its result.

Sine's bound is in the same specification's table of accuracy under fast math: for angles within ±π, the absolute error is at most 2−13, and larger outside. An absolute error divided by a small angle is magnified, so the bend pass's sin(x)/x, whose argument is half a figure's bend angle, takes its Taylor series where the angle is small:

// sin(angle) / angle, sinc, by its Taylor series below 0.5 radians, whose
// first term left out, angle⁸ / 9!, is under 1.1e-8 there: Metal compiles
// with fast math [ref:msl-4.1-fast-math], which leaves sin an absolute
// error [ref:msl-4.1-sin-fast-accuracy] that dividing by a small angle
// would magnify.
fn sinc(angle: f32) -> f32 {
    let squared = angle * angle;
    let series = 1.0 - squared / 6.0 * (1.0 - squared / 20.0 * (1.0 - squared / 42.0));
    return select(sin(angle) / angle, series, abs(angle) < 0.5);
}

bend.wgsl. The crowd never leaves the series: its largest half angle, half of CROWD_SWAY_CURVATURE times CROWD_FIGURE_HEIGHT, is 0.315 rad (The bend pass).

The error that remains reaches the dynamic TLAS. Each bent vertex is built from a few sines and cosines, so it lands off its exact shape by a few times 2−13 of its distance from the Mesh's origin, and the box that lets a shadow ray skip the dynamic TLAS has to hold the rounded vertex too:

/// The share of a Mesh's largest coordinate its box grows by before it is
/// placed, for the bend pass's rounding: under Metal's fast math, sine errs
/// by up to 2^-13 within ±π [ref:msl-4.1-sin-fast-accuracy], and a bent
/// vertex, built from a few sines and cosines over its height and its
/// distance from the middle, lands off its exact shape by a few times that
/// share of its distance from the Mesh's origin, by estimate, as no
/// specification bounds cosine or angles past ±π, which an azimuth can be.
/// Every Mesh grows, as which ones bend is not known here.
const BEND_ROUNDING_SHARE: f32 = 0.00390625; // 2^-8

acceleration_structures.rs (The dynamic TLAS).

5 · octahedral_decode · front_face

Unorm rounds to nearest, and a front face is what the shader reads

Metal rounds a Unorm store to the nearest step; Vulkan only recommends it and may round to either neighbour, which roughly doubles the error of a stored normal. Neither Metal's documented default winding nor naga settles which side of a triangle a ray query calls its front, so the shader reads the answer and a test decides it.

The depth passes store each sample's two normals as octahedral coordinates in an Rgba8Unorm target, 8 bits per coordinate, which hold a direction within 0.95° where the store rounds to nearest. The Metal Shading Language specification allows either round-to-nearest-even or round-toward-zero for single-precision operations, and Vulkan's Unorm conversion is a recommendation; so the shadow mask's margins are sized for both:

// The cosines, of a light's angle from a plane, past which a sample's normals
// face the light or turn from it: sin 2° for the first two, the stored
// normals' error, and sin 10° for the third. The surface normals'
// 8-bit octahedral coordinates hold each within 0.95° where the store rounds
// to the nearest step, as Metal's does, and about twice that where it may
// round to either (`octahedral_decode`).

shadow_mask.wgsl, above INTERPOLATED_TURN_MARGIN, AGREEING_TRIANGLE_TURN_MARGIN and TRIANGLE_TURN_MARGIN (The depth pre-pass).

A triangle's front face is the side its normal, taken from its vertices in index order, points toward, and a ray query reports whether the ray met it in front_face. The Vulkan specification decides facing in the BLAS's own space, so a mirrored Instance does not flip it. On Metal, the shading language documents a clockwise default winding and naga sets none, which would seem to invert it; the sources do not settle it. Culling back faces in the traversal was not an option either: naga's Metal backend ignores the cull-back-facing ray flag. So shadowed reads the face itself, and uses it to tell a ray leaving its own mesh from one that met an occluder:

    var flags = select(0u, RAY_FLAG_TERMINATE_ON_FIRST_HIT, leaves_surface);
    var start_distance = 0.0;
    var hidden = false;
    loop {
        let hit = first_intersection(flags, origin, direction, start_distance, distance);
        let found = hit.kind != RAY_QUERY_INTERSECTION_NONE;
        let any_hit = (flags & RAY_FLAG_TERMINATE_ON_FIRST_HIT) != 0u;
        if any_hit || !found || hit.front_face || hit.t + offset >= distance {
            hidden = found && (any_hit || hit.front_face);
            break;
        }
        flags = RAY_FLAG_TERMINATE_ON_FIRST_HIT;
        start_distance = hit.t + offset;
    }

shadow_mask.wgsl, the end of shadowed. A ray that starts inside the surface passes the first back face it meets, where it leaves its mesh, and traces on; a front face there is an occluder. An inverted front_face would hide the sun across every terminator band, and tests/shadows.rs would fail on Metal and on lavapipe alike (The shadow mask pass).

6 · compact_blases · Order

Tracking orders only what a command names

Metal orders a read after a write by itself, but only for tracked resources a command binds directly. A TLAS build names its BLASes by resource ID inside a buffer, so Metal never learns that the build reads them, and wgpu-hal records no barrier on Metal in their place. Praxis orders the pair itself: on the CPU at load, and with a shared event in the frame.

A queue is an order, not a timeline: the GPU starts each command buffer after the ones ahead of it have started, not finished, and work that does not depend on earlier work, as far as the GPU knows, runs alongside it. Vulkan and Direct3D 12 leave the read-after-write hazard to the application, which records a barrier. Metal tracks it for the resources made from the device, the default, and only where a command binds such a resource directly; a resource the work reaches any other way, such as through an ID stored in a buffer, is outside it.

wgpu-hal builds every TLAS on Metal in the indirect instance layout, where each entry holds its BLAS's acceleration structure ID and the descriptor names no BLAS, so a build after a BLAS write, or after the copy that compacts one, is ordered by nothing but chance. wgpu-core does know, and asks the backend for a barrier before and after the builds; on Metal the request arrives and no command is recorded. The residency set wgpu-hal makes per submission keeps the BLASes in memory and orders nothing, as Apple's documentation of residency sets says. The upstream report, 9215, is still open, with a fence-based fix in review.

At load, the Mesh pool waits on the CPU, once per frame that loads Meshes, for the compaction copies the static TLAS's build reads:

        // The copies wait in the queue's pending writes until a submit.
        queue.submit(std::iter::empty());
        if let Err(error) = self.device.poll(wgpu::PollType::wait_indefinitely()) {
            tracing::error!(%error, "waiting for BLAS compaction failed");
        }

pools.rs, the end of compact_blases. The empty submit is what makes the poll useful: the copies sit in wgpu-core's pending writes until something submits, and a poll waits only for submitted work (The BLAS, The static TLAS, Waiting on the GPU).

In the frame, a CPU wait would stall the main thread, which records and submits every frame, behind the GPU. The crowd's refit form, which updates each figure's BLAS every frame through wgpu-hal, orders the dynamic TLAS's build after the refits on the GPU instead: the submission that holds the refits signals a Metal shared event as it completes, and wgpu-hal's strict event sync holds every command buffer encoded after it, the build's among them, until the event reaches that value. Staging is queue-wide, as wgpu-hal's documentation warns: whichever submit runs next takes a staged signal or wait, and in Praxis only the main thread submits, presents or polls (ADR 0016), and the Renderer submits nothing between the refits and the build, nor calls what makes wgpu-core submit on its own, such as mapping a buffer with pending writes. Where Metal makes no shared event, the frame falls back to the CPU wait (The BLAS refit).

7 · dispatch_workgroups_indirect · shadow_mask_pass.rs

Queued frames stop passes overlapping, unless a pass dispatches indirectly

With the GPU idle at a frame's start, Metal runs the Froxel pass beside culling phase one and the lit pass's vertex work beside the shadow mask pass. Once the CPU outpaces the GPU and each frame queues behind the one running, the whole frame ran one pass after another, unless the shadow mask pass holds an indirect dispatch, even one of zero workgroups, ahead of its direct ones. The mechanism is the driver's, and Apple does not document it.

Hazard tracking promises that commands after a write wait for it, and Apple GPUs can make a pass's fragment stage wait while its vertex stage runs; neither says when Metal runs a command buffer's passes one after another. The loss was first seen when the TLASes left the lit pass's bind group: the CPU frame fell by more than half, the GPU became the bottleneck, and with two frames in flight the frame's passes spanned more than with one, the lit pass no longer starting beside the shadow mask pass nor the Froxel pass beside culling. The raw timestamps showed the whole queued frame running pass after pass, the lit pass starting 11 µs after the shadow mask pass ended, and the next frame's culling waiting for this frame's tonemapping.

Bisected, the overlap came back with the commit that gave the shadow mask pass its first indirect dispatch, and ablated on main, leaving both indirect dispatches out brings the loss back while an indirect dispatch of zero workgroups at the pass's start, launching nothing, removes it again. An empty shadow mask pass keeps the overlap and a doubled one loses it, so the pass's length is not the cause; nor is the per-submission residency set, since one set held for the queue's lifetime loses it too, nor the dynamic TLAS's build in its own submission. With shadow rays off there is no shadow mask pass, and queued frames keep the overlap.

On main the shadow mask pass records four dispatches: build_shadow_mask over the screen's tiles, trace_second_surfaces through dispatch_workgroups_indirect over the frame's list of edge pixels, list_shadow_edges over the tiles, and trace_shadow_edges indirectly over the list of shadow-edge pixels. What the span rule makes of the overlap, that a frame's GPU time runs from its passes' earliest start to their latest end rather than summing them, is the Frame stats page's matter.

The kernel's scheduling of bound Textures

One more Metal cost sits on the CPU, in the kernel, and at the commit above no code answers it. The roughly 11 ms of texture-wall's gate that no pass times is the time the kernel's GPU driver spends scheduling the Metal command buffer that holds the lit pass, between its commit and its start, which Apple's command buffer exposes as its kernel start and end times. The cost grows with the distinct Textures in the lit pass's material bind group, each of which wgpu-hal passes to Metal's residency call for the encoder, and grows faster than their count: with one distinct Texture bound, the gate reads about a twentieth of its Baseline. It does not depend on which Textures the quads sample, the depth passes, which bind the same group, add nothing, and the work grows with the machine's load, as CPU work in the kernel does. The bench reports the stretch as the lit pass's wait.

8 · pixel_minimum · final_depth_attachment

What the compiler does not do

Metal's shader compiler does not unroll a loop over a texture's four samples, a uniform branch around a term costs more than the term, a depth pass that stores writes the whole 4x target back, and ray-query code in a fragment shader costs even where no ray is traced. Each is answered where it was measured.

Loops over the samples. Both passes that read every sample of the depth target load the four by index:

// The minimum depth of the depth target's four samples at `pixel`, which
// Rust asserts it has (SAMPLE_COUNT), loaded together: Metal's compiler
// does not unroll a loop over them.
fn pixel_minimum(pixel: vec2<u32>) -> f32 {
    return min(
        min(textureLoad(depth, pixel, 0), textureLoad(depth, pixel, 1)),
        min(textureLoad(depth, pixel, 2), textureLoad(depth, pixel, 3))
    );
}
    // The four samples Rust asserts the depth target has (SAMPLE_COUNT),
    // loaded together: Metal's compiler does not unroll a loop over them.
    let depths = vec4<f32>(
        textureLoad(depth_target, pixel, 0),
        textureLoad(depth_target, pixel, 1),
        textureLoad(depth_target, pixel, 2),
        textureLoad(depth_target, pixel, 3)
    );

depth_pyramid.wgsl, level 0's reduction, and shadow_mask.wgsl, in build_shadow_mask; a Rust assertion holds SAMPLE_COUNT at four for both (The depth pyramid pass).

A branch around a light. A uniform branch around the first directional light's shading slowed the lit pass on the M4 Pro, so the light is shaded whether or not the light buffer holds one, with inputs selected to keep the term finite and zero:

        vec3<f32>(0.0, 1.0, 0.0),
        normalize(-first.offset),
        has_directional_light
    );

Storing depth. A pass that writes depth and stores it writes the whole 4x target back from tile memory, a measurable cost at 1440p, so the frame's last depth-writing pass discards it unless a later pass reads it, which only the light count pass does, behind a Render switch that ships off:

    /// The depth target as the attachment of the frame's last pass that
    /// draws depth: loaded, and discarded unless `kept` for a later pass to
    /// read. A pass that writes depth and stores it writes the whole target
    /// back, a measurable cost at 1440p on the M4 Pro (measured:
    /// `docs/performance.md`, Measurements behind the code).
    pub fn final_depth_attachment(&self, kept: bool) -> wgpu::RenderPassDepthStencilAttachment<'_> {
        wgpu::RenderPassDepthStencilAttachment {
            view: &self.depth,
            depth_ops: Some(wgpu::Operations {
                load: wgpu::LoadOp::Load,
                store: if kept {
                    wgpu::StoreOp::Store
                } else {
                    wgpu::StoreOp::Discard
                },
            }),
            stencil_ops: None,
        }
    }

targets.rs (The depth pre-pass).

Ray queries in a fragment shader. When shadow rays moved from the lit pass to the shadow mask pass, a first version kept an inline ray query in fs_main as a fallback for lights past the mask's bits, which no Reference scene reached. With that code present and never run, the lit pass took 1,362 to 4,611 µs against 429 to 754 µs without it, over two rounds on four scenes. The owner chose a fixed capacity of lights per pixel over the fallback, with the overflow counted and warned, and the lit pass holds no ray-query code (The shadow mask pass).

11 · ADRs 0016, 0019, 0020

Why this way

A flat read, over invariance or a visibility buffer. ADR 0019 records the rule: two passes that must agree on a sample's triangle both read a flat input. Invariance covers the position output alone, so it could not help. Writing the normals in one draw of both phases at depth equal would cost about one more geometry pass and would still rest on two different fragment shaders agreeing. Storing a triangle ID per sample and deriving the normals from it, as a visibility buffer does, is exact by construction and portable, and is the fallback if another GPU merges under other conditions; it is a larger change, and the prototype that built one did not move the main pass's gate.

Slot order, over atomics. Appending through an atomic count is simpler and the records land in any order; on the M4 Pro any order is a different image. The scan costs a dispatch over the blocks' totals and makes every run's draw identical, which the Goldens and the culled-against-unculled check both need; ADR 0019's draw is one indirect call per phase over that stream.

A series, over a math mode. wgpu-hal passes no math mode to Metal's compiler, and a safe mode would slow every shader for one function's sake. The Taylor series below 0.5 rad costs three multiplies and holds the bend within 1.1 × 10−8; the dynamic TLAS's box carries the rest of sine's error as a margin.

A shared event, over a CPU wait each frame. ADR 0016 keeps the main thread recording and submitting every frame, so a CPU wait on the refits each frame would stall it behind the GPU. A fence between acceleration-structure passes is upstream's fix and not in a release; wgpu-hal's events are available now, and strict event sync makes a staged wait an order rather than a hope. The CPU wait stays at load, where it costs a frame that loads Meshes about a third of a millisecond, and as the fallback where no shared event can be made (ADR 0020).

An indirect dispatch found, not a fix made. The queued-frame overlap was bisected to the commit that gave the shadow mask pass its indirect dispatch and confirmed by ablation on main; the mechanism is the driver's. The pass dispatches indirectly for its own reasons, the second surfaces and the shadow edges being minority pixels listed by the frame, so nothing was added for the overlap's sake, and a bench against the Baseline would show the loss if a change took the indirect dispatches away.

12

Limits

One GPU, one macOS. Everything here was measured on one Apple M4 Pro under macOS 27.0.1 and wgpu 30.0.1. Other Apple GPU families, other releases and the RTX 2070 SUPER's drivers may merge, batch, round or schedule otherwise; nobody has measured them.

No vendor documentation. Apple documents neither the merging, nor the loss of overlap behind queued frames, nor when a waiting core's clock falls. Each rule rests on its measurement, and the guards are the tests above: the merging test fails if the M4 Pro stops merging, and the Goldens if slot order stops being enough.

The kernel's scheduling. The time the kernel spends scheduling a command buffer with thousands of distinct Textures is measured and reported, not answered; texture-wall's gate carries it.

Unorm on Vulkan. Where a store may round to either neighbour, the stored normals' error doubles, and the shadow mask's margins are sized for that; a tighter margin would need Vulkan's rounding pinned.

Every new pass. A later pass that decides from which triangle a sample shows reads a flat input or keeps whole Meshlets; a later pass that writes a BLAS orders the TLAS build after it by event or by wait; a later compute pass in the frame may change which passes overlap once frames queue, and only a bench would show it.

History

The merging was found when a prototype's ID pass credited samples to a triangle's neighbour and the culled and unculled frames of town disagreed at a few edge pixels; the flat read followed, and the Goldens moved at single pixels. Slot order came when the orrery's capture moved from run to run under the first culling pass. The sine series and the box's margin came with the crowd's bend. The ordering gap was found at load, when a flaky test built a TLAS right after a compaction copy while eight devices loaded the GPU, and again with the crowd's per-frame refit, which took the event route. The loss of overlap behind queued frames appeared when the TLASes left the lit pass's bind group and the CPU outpaced the GPU, and its lever was found by bisection and ablation. The compiler's loops, the branch and the depth store were measured while the shadow mask and the depth pyramid were built, and the ray-query cost when the rays left the lit pass.
