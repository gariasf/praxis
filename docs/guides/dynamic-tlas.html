Praxis · the frame · src/render/acceleration_structures.rs

The dynamic TLAS

The TLAS of the frame's Moving Instances, at most 10,000 of them, rebuilt from scratch every frame in the static TLAS's frame, in a command buffer submitted ahead of the frame's commands, with a box that holds its triangles so that a shadow ray which misses the box never queries it.

Describes main at fbae12f4 (2026-11-04). A change to the dynamic TLAS rewrites this page and moves the commit; nothing is appended. Read first: The static TLAS for the frame both TLAS share, The BLAS for what each entry places, Instance Buffer Explained for slots, The shadow mask pass for the rays that query it.

Interface

Runs
Every frame, in three calls. Renderer::upload calls prepare_encoder before the frame's encoder is created and fill before the frame's uploads, since the fill returns the box the camera uniform carries; Renderer::render calls record after the bend pass and any BLAS update, and submits the build on its own just before the frame's command buffer. The GPU builds it in frames that list Moving Instances and once more, empty, in the frame the last one goes; DynamicTlas::new builds it empty once at creation.
Reads
Frame data's moving_instances and the instances they index; each Mesh's BLAS and bounds from the Mesh pool; the static TLAS's Anchor.
Writes
Its entries, up to DYNAMIC_TLAS_CAPACITY; the box that holds their triangles, which Renderer::upload writes into the camera uniform beside dynamic_tlas_entries.
Builds
One TLAS of 10,000 entries, created once with PREFER_FAST_TRACE and AccelerationStructureUpdateMode::Build and rebuilt in place, between two marker dispatches when the frame is timed.
Bind groups
The shadow mask pass's group 2, SHADOW_RAY_SCENE, beside the static TLAS; the markers' group 3, DYNAMIC_TLAS_MARKERS, with the buffer their query writes. No other pass binds it.
Shader
src/render/shaders/dynamic_tlas_marker.wgsl, the markers' mark_dynamic_tlas; the shadow mask pass's first_intersection queries it.
Counted
In Frame stats: dynamic_tlas_build in GPU time, counted from the end of the frame before's last pass; the CPU stages dynamic_tlas and dynamic_tlas_submit, which the bench sums with blas_refit into dynamic_tlas_cpu_microseconds; moving_instances_left_out; each built entry's backend record in uploaded_bytes; its capacity's estimate and the markers' buffer in GPU memory.

1 · src/render/renderer.rs

Where it sits in the frame

Its entries are filled on the CPU while the frame uploads, its build is recorded into a command buffer of its own once the bend pass is recorded, and that command buffer is submitted just before the frame's, so the GPU receives the build first, ahead of every pass that could read it.

What the GPU receives in a frame of the default crowd form, in order

  1. dynamic TLAS build
  2. bend pass
  3. culling, phase one
  4. Froxel pass
  5. depth pre-pass
  6. depth pyramid pass
  7. culling, phase two
  8. phase two's depth pass
  9. shadow mask pass
  10. lit pass
  11. tonemapping pass

The shadow mask pass is the one pass that reads it, through group 2. With the crowd's refit or rebuild form, a Render switch, a frame that bends Meshes is cut after its bend pass: the commands up to it are submitted first with the BLAS updates, and the build, recorded after them, follows, so its entries place the BLASes as the frame bent them (The BLAS refit). In the default form, the shadow proxies', nothing is cut.

Renderer::render: the build's own submit, then the frame's.

Only the main thread submits (ADR 0016), and nothing is submitted between the two, so the order the GPU receives is the order of these lines. record returns no command buffer in a frame with nothing to build, and the frame then submits its own alone.

2 · src/render/prepare.rs

The list it takes

Prepare hands it the list ready-made: every Moving Instance it wrote this frame, at most 10,000, those in the lowest slots, each a slot and an index into the frame's Instances. The dynamic TLAS takes the list as it is and decides nothing about which Instances it holds.

/// A Moving Instance the dynamic TLAS holds: its slot, and its Instance's
/// index in `FrameData::instances`.
pub struct MovingInstance {
    pub slot: u32,
    pub instance: usize,
}

MovingInstance, src/render/prepare.rs.

An Instance is a Moving Instance while its entity carries PreviousWorldTransform, which the fixed schedule keeps on every entity it moves so that frames draw it blended between Ticks (ADR 0022). Such an entity is drawn somewhere new every frame, so prepare writes its Instance every frame and lists the write as moving: a frame's Moving Instances are exactly its moving writes, and every one of them is among FrameData::instances. In the frame an entity loses the component, prepare writes its Instance once more, unlisted, so the static TLAS takes it in that frame.

Past DYNAMIC_TLAS_CAPACITY, prepare keeps the lowest slots with select_nth_unstable_by_key and drops the rest, counts them every frame as moving_instances_left_out, and warns once while it lasts. A slot changes only when its Renderable spawns or despawns, so which Moving Instances lose their shadow does not move from frame to frame with the ECS World's order. The fill, too, takes no more than its capacity from the list.

3 · DynamicTlas::new

Created once, at its capacity, and built empty

The TLAS is created once with room for 10,000 entries and rebuilt in place from then on, so the bind groups that hold it are built once. It is built empty at creation, so no marker ever queries a TLAS that was never built.

let tlas = device.create_tlas(&wgpu::CreateTlasDescriptor {
    label: Some("Dynamic TLAS"),
    max_instances: DYNAMIC_TLAS_CAPACITY,
    // Traced at every lit pixel, as the static TLAS is; ADR 0020's
    // per-frame cost was measured with this flag.
    flags: wgpu::AccelerationStructureFlags::PREFER_FAST_TRACE,
    update_mode: wgpu::AccelerationStructureUpdateMode::Build,
});
let mut encoder = create_encoder(device);
encoder.build_acceleration_structures(std::iter::empty(), std::iter::once(&tlas));
queue.submit(std::iter::once(encoder.finish()));

DynamicTlas::new, src/render/acceleration_structures.rs, its first lines; the rest creates the markers' buffer, bind group and pipeline, and picks each entry's upload size by backend.

Rebuilt in every frame that lists Moving Instances, it still asks for a tree that traces fast rather than one that builds fast: it is traced from every lit pixel, as the static TLAS is, and ADR 0020's per-frame cost was measured with that flag. The update mode is Build, a rebuild from scratch, as wgpu-core 30 implements no other for a TLAS.

The markers that time its build query it, so it must hold a build before the first of them runs. Built empty at once through the queue, it does before the first frame.

4 · fill · anchored_transform · tlas_instance

The fill: one entry per listed Moving Instance

Entry i takes the list's i-th Moving Instance: its Mesh's BLAS, placed by its transform from the corner of the static TLAS's Anchor, and tagged with its slot. Entries the previous fill filled past this one's count are cleared, and the fill returns the box that holds every triangle it placed.

pub fn fill(
    &mut self,
    frame: &FrameData,
    mesh_pool: &MeshPool,
    anchor: [i32; 3],
) -> [[f32; 3]; 2] {
    // Prepare lists no more than its capacity.
    let listed = frame
        .moving_instances
        .iter()
        .take(DYNAMIC_TLAS_CAPACITY as usize);
    let filled = listed.len();
    let previously_filled = std::mem::replace(&mut self.filled, filled);
    let mut uploaded_entries = 0;
    let mut bounds: Option<[glam::Vec3; 2]> = None;
    for (index, moving) in listed.enumerate() {
        let instance = &frame.instances[moving.instance];
        let handle = MeshHandle(instance.mesh);
        let mesh = mesh_pool.blas(handle).zip(mesh_pool.get(handle));
        self.tlas[index] = mesh.map(|(blas, mesh)| {
            let transform = anchored_transform(instance, anchor);
            let [lowest, highest] = placed_bounds(&transform, mesh.bounds);
            bounds = Some(
                bounds.map_or([lowest, highest], |[held_lowest, held_highest]| {
                    [held_lowest.min(lowest), held_highest.max(highest)]
                }),
            );
            uploaded_entries += 1;
            tlas_instance(blas, transform, moving.slot)
        });
    }
    for index in filled..previously_filled {
        self.tlas[index] = None;
    }
    self.unrecorded_upload_bytes = (filled > 0 || previously_filled > 0)
        .then_some(uploaded_entries * self.entry_upload_bytes);
    bounds.unwrap_or_default().map(<[f32; 3]>::from)
}

DynamicTlas::fill, src/render/acceleration_structures.rs.

An entry needs both the Mesh's BLAS and the Mesh itself, whose bounds the box takes; a Mesh missing either, its BLAS or its place in the pool, leaves its entry empty, and it casts no shadow. The clearing loop matters: a Moving Instance that despawns drops off the list, and without the loop its entry would keep its last transform and go on casting its shadow from there.

The fill records nothing. It leaves the bytes the build will upload for record, or none when this fill and the one before both held nothing, which is how an empty TLAS is built once more in the frame it empties and then not again.

fn anchored_transform(instance: &InstanceData, anchor: [i32; 3]) -> [f32; 12] {
    let [x_axis, y_axis, z_axis] = instance.rotation_scale;
    let row = |axis: usize| {
        let cells = i64::from(instance.anchor[axis]) - i64::from(anchor[axis]);
        let translation = cells as f64 * ANCHOR_CELL_SIZE + f64::from(instance.offset[axis]);
        [x_axis[axis], y_axis[axis], z_axis[axis], translation as f32]
    };
    bytemuck::cast([0, 1, 2].map(row))
}

anchored_transform, which the static TLAS uses too.

A ray is composed once and traced against both TLAS, so both place their Instances in one frame: the static TLAS's, whose origin is the corner of the camera's Anchor in the first Frame data, which Renderer::upload reads from the static TLAS and passes to the fill. Each translation is composed in f64 from whole 64 m cells plus the Instance's f32 offset, so only the f32 result rounds (ADR 0014). tlas_instance then makes the entry: the BLAS, those rows, the slot as the entry's custom data, and the cull mask 0xff that every ray carries.

wgpu-core converts each filled entry into the backend's own instance record on the CPU and stages it for the build: 72 bytes on Metal, a MTLIndirectAccelerationStructureInstanceDescriptor, and 64 on Vulkan and DX12, a VkAccelerationStructureInstanceKHR or D3D12_RAYTRACING_INSTANCE_DESC. record returns those bytes, which join the frame's uploaded_bytes.

5 · placed_bounds · first_intersection

The box that lets a ray skip it

A ray query starts at the TLAS's root however far the ray passes from its Instances, so the shadow mask pass tests each ray's segment against one box that holds every triangle of the dynamic TLAS first, and queries the TLAS only where the segment meets it.

The shadow mask pass's first_intersection traces the static TLAS, then skips the dynamic TLAS when it is empty, when a first hit was asked for and found, or when the ray's segment misses the box that holds the dynamic TLAS's triangles, grown by DYNAMIC_TLAS_BOUNDS_MARGIN_SCALE; DynamicTlas::fill returns that box from each entry's Mesh bounds placed by its transform (placed_bounds, grown by BEND_ROUNDING_SHARE), and Renderer::upload writes it into the camera uniform, which is 144 bytes. The queries themselves, their flags and the loop that calls them, are the shadow mask pass's (One ray).

fn placed_bounds(transform: &[f32; 12], bounds: [[f32; 3]; 2]) -> [glam::Vec3; 2] {
    let [lowest, highest] = bounds.map(glam::Vec3::from);
    let centre = 0.5 * (lowest + highest);
    let largest_coordinate = lowest.abs().max(highest.abs()).max_element();
    let half_extent = 0.5 * (highest - lowest) + BEND_ROUNDING_SHARE * largest_coordinate;
    let rows: [[f32; 4]; 3] = bytemuck::cast(*transform);
    let row = |axis: usize| glam::Vec4::from(rows[axis]).truncate();
    let placed_centre =
        glam::Vec3::from_array([0, 1, 2].map(|axis| row(axis).dot(centre) + rows[axis][3]));
    let reach = glam::Vec3::from_array([0, 1, 2].map(|axis| row(axis).abs().dot(half_extent)));
    [placed_centre - reach, placed_centre + reach]
}

placed_bounds, src/render/acceleration_structures.rs.

The Mesh's box grows first, by BEND_ROUNDING_SHARE, 2−8, of its largest coordinate, then is placed: its centre by the entry's rows, and its half-extent by the rows' absolute values, so the placed box holds the turned and scaled one. A Mesh's bounds hold every shape a bend gives it, and the margin covers how far the bend pass's fast-math sines may land a vertex off that shape; every Mesh grows, since which ones bend is not known here (The bend pass). The fill takes the union over its entries and returns a point at the origin when it placed none.

Renderer::upload, src/render/renderer.rs: the fill, and the camera uniform it feeds.

CameraUniform carries the TLAS's Anchor, the entry count and the box's two corners, each corner padded to 16 bytes, which brings the uniform to 144 bytes; the uniform's upload is counted at that size in every frame. The entry count is the list's length, which prepare has already capped.

first_intersection, src/render/shaders/shadow_mask.wgsl: its dynamic half's guard, between the static query and the dynamic one.

The segment runs from the ray's start to its end, or to the static hit where there is one, since only a nearer dynamic triangle could replace it. The box grows by 2−16 of the largest coordinate of its corners and the ray's origin, and of 1 m at least, the share a shadow ray's origin leaves its surface by; placing the box on the CPU, placing the entries' triangles and intersecting them on the GPU each round by a few times 2−24 of a coordinate, so a ray that meets a triangle of the dynamic TLAS meets the box. segment_meets_box, in the common part, is a separating-axis test: the box's three axes and the three crossings of them with the segment, with no divide, so a ray parallel to a pair of faces needs no case of its own, and the segment cut short first where it runs past the box, so a directional light's ray, which runs to f32's largest distance, keeps its products finite.

6 · record · mark · prepare_encoder

The build, between two markers

The build goes in a command buffer of its own, so its recording and its submit are timed apart from the frame's on the CPU. On the GPU an acceleration-structure build writes no timestamps, so two one-invocation compute passes that query the TLAS bracket it: the GPU must run the first before the build and the second after it.

pub fn record(
    &mut self,
    device: &wgpu::Device,
    timestamps: Option<[wgpu::ComputePassTimestampWrites<'_>; 2]>,
) -> Option<(wgpu::CommandBuffer, u64)> {
    let uploaded_bytes = self.unrecorded_upload_bytes.take()?;
    let mut encoder = self
        .encoder
        .take()
        .unwrap_or_else(|| create_encoder(device));
    let [before, after] = timestamps.map_or([None, None], |writes| writes.map(Some));
    self.mark(&mut encoder, before);
    encoder.build_acceleration_structures(std::iter::empty(), std::iter::once(&self.tlas));
    self.mark(&mut encoder, after);
    Some((encoder.finish(), uploaded_bytes))
}

DynamicTlas::record, src/render/acceleration_structures.rs.

@compute @workgroup_size(1)
fn mark_dynamic_tlas() {
    var query: ray_query;
    rayQueryInitialize(
        &query,
        dynamic_tlas,
        // Every instance's cull mask, and a ray too short to reach far.
        RayDesc(RAY_FLAG_NONE, 0xffu, 0.0, 1e-6, vec3<f32>(0.0), vec3<f32>(0.0, 1.0, 0.0))
    );
    rayQueryProceed(&query);
    marker_result = rayQueryGetCommittedIntersection(&query).kind;
}

mark_dynamic_tlas, src/render/shaders/dynamic_tlas_marker.wgsl: a ray too short to reach far, whose result is written so the query stays.

A marker must touch the TLAS. Metal runs a pass that does not alongside the build, so its timestamps would not bracket it, and a pass that does nothing writes no timestamp at all. A pass that queries the TLAS waits for the build that writes it, and the build waits for a pass still reading its old contents. The first marker writes its end, the second its start, and the build's GPU time runs from one to the other.

The markers run only when the frame is timed, and not with the crowd's rebuild form: wgpu-core checks the first marker's query against the BLASes of the last build, so a BLAS rebuilt through wgpu since would fail the whole command buffer, build included. A frame of that form reads its build as no time.

Where its GPU time starts

The first marker can run while the frame before still runs, and the build mostly runs beside it. So the readback counts the build from the later of the first marker's end and the end of the frame before's last pass, when that frame was the one read back just before; a build that ends before that frame's last pass ends reads 0. The GPU frame total is that build plus the span of the frame's own passes (Frame stats).

Where its CPU time is counted

The CPU stage dynamic_tlas sums three timings: prepare_encoder and the fill in Renderer::upload, which the upload stage leaves out, and record in Renderer::render. dynamic_tlas_submit times the build's own submit. Together they are ADR 0020's recording plus submit. At submit, wgpu-core walks a TLAS's dependencies, one BLAS per entry, for each pass whose bind group holds it, so the markers' and the build's walks are in that figure, and the shadow mask pass's walk is in the frame's own submit.

prepare_encoder creates the build's encoder before the frame creates its own. A new encoder reuses the one the GPU finished with last, and the build's command buffer is submitted first, so its encoder is released first; created in this order, the two swap roles every frame, and every encoder the frames reuse records the frame's passes within its first two frames, by which time the state Metal keeps per encoder, which grows to the largest pipeline and bindings it recorded and never shrinks, has grown. Created in the other order, the frame's passes could reuse the build's encoder in a frame the GPU's timing picks, and its state would grow then.

9 · ADRs 0003, 0013, 0014, 0016, 0020, 0022

Why this way

Two TLAS, split by how often they change. wgpu-core 30 can only rebuild a TLAS from scratch, and a rebuild's CPU time grows with the TLAS's capacity, filled or not. Most of an open world stands still and little of it moves in any one frame, so ADR 0020 splits the near field: a static TLAS rebuilt only when its static Instances change, and a dynamic TLAS of Moving Instances rebuilt every frame and capped at 10,000, a size whose recording plus submit the ADR records as measured on the M4 Pro. Shadow and probe rays query both.

A fixed capacity of 10,000. In wgpu a TLAS rebuild's CPU time grows with its capacity, filled or not, so the capacity is paid every frame; the Budgets on its CPU and GPU time were set at that capacity on town, which fills it (ADR 0013). The capacity is provisional until ADR 0013's split of the GPU memory Budget sizes it.

The lowest slots, not the first met. The ECS World's iteration order shifts whenever entities spawn, despawn or change components, even for an instant, as a teleport's marker does; an Instance's slot changes only when its Renderable spawns or despawns (ADR 0003). Keeping the lowest slots past the capacity holds which Instances lose their shadow still while nothing spawns.

Moving is carrying the previous World transform. ADR 0022's blend already marks every entity the fixed schedule moves, children included, and makes prepare write it every frame. Reading that component as the classification needs no component of its own and gives the list for free, from the writes prepare already makes.

The static TLAS's frame. Both TLAS place their entries from one Anchor's corner, composed in f64 (ADR 0014), so the shadow mask pass composes each ray once and traces it against both.

A box, not every ray. A query of the dynamic TLAS costs even where nothing it holds is near, because traversal starts at the root, and a ray can pass far from everything it holds. One box, the union of the entries' placed Mesh bounds, costs the CPU a few products per entry and the GPU one separating-axis test per ray, and sends only the rays that pass near the movers into the second query. Growing it for the bend's rounding keeps it a true bound for meshes the GPU bends.

Its own command buffer, submitted first. ADR 0020 caps the build's recording plus submit, so both are timed alone; submitted before the frame's command buffer, the build is in place before the shadow mask pass reads it, and only the main thread submits, so nothing comes between (ADR 0016). Markers that query the TLAS are the one kind of pass that brackets a build on Metal.

Limits

Ten thousand, then no shadow. Moving Instances past the capacity, those in the highest slots, are still drawn but cast no shadow; Frame stats count them every frame and a warning names them once.

Shadow proxies spend the cap. Each crowd figure casts its shadow through 16 shadow proxies, one per bone, so its 100 figures take 1,600 of the 10,000 entries (The Reference scenes).

Rebuilt whole every frame. Its cost grows with the Moving Instances it holds, and nothing of the last frame's tree is kept; wgpu-core has no TLAS refit to fall back on.

The capacity is paid empty. Its memory is its 10,000 entries' estimate in every scene, and each build walks every entry, filled or not.

One box for all of them. Moving Instances spread across a scene make one wide box, so where they spread, as town's flocks do over its square kilometre, a ray toward the sky from under them can cross the box and still query the TLAS.

Far from the load Anchor. The static TLAS's frame is never re-anchored in M3, so an entry far from the Anchor the first Frame data set is placed in f32 at that distance and rounds in proportion to it.

An entry with no BLAS. A Moving Instance whose Mesh has no BLAS or is not in the pool takes an empty entry and casts no shadow, though the entry count still includes it.

Hidden time. The build's GPU time counts only what runs past the frame before's last pass, so on the M4 Pro it reads 0 while the build itself takes longer; with the crowd's rebuild form it is not timed at all.

History

The dynamic TLAS took its form over the third milestone. It arrived on 2026-10-23 with the split from the static TLAS, the Moving Instances kept by lowest slot and a skip of its query while it is empty, its rays then traced in the lit pass, and its build moved into a command buffer of its own between two markers that time it; the rays moved into the shadow mask pass; the crowd's shadow proxies and its refit form made it carry deforming figures; on 2026-10-26 the owner had its build counted from the end of the frame before's last pass and set its CPU and GPU ceilings at 10,000 Moving Instances on town; on 2026-10-31 it gained the box that lets rays skip it; and on 2026-11-01 its encoder came to be created ahead of the frame's. The ordering gap its build shares with the static TLAS's is on Waiting on the GPU; The shadow mask pass holds the shadow rays' mechanism. This page describes the mechanism as it is.
