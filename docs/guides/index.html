Praxis · engine reference

How a frame runs

Praxis is a 3D engine in Rust for large open-world games. This is its frame in the order data flows through it, from the assets cooked before it to the stats read back after it, each step linking the page that describes its mechanism.

Describes main at 7b8009ee (2026-11-05). A page describes its mechanism as it is at the commit its own Describes line names; where a step has no page yet, it links the volumes that narrate how that mechanism was built, each kept until its page replaces it.

Before the frame

  1. The Reference scenes, each a Scene the engine generates or loads with a fixed camera path and injected time, so that every run produces the same frames: the Goldens, the Baselines and the galleries are all measured on them. Page: The Reference scenes
  2. praxis cook turns the manifest's sources and the Reference scenes into Blobs, among them each texture's mips, averaged in linear light, with a normal map's roughness widened by Toksvig's measure. Page: Texture cooking, and Box filtering for what a mean of texels lets through
  3. At load, each Mesh gets a BLAS, built and then, once the CPU has waited for the builds, compacted, and the static TLAS is built over the static Instances. Pages: The BLAS, The static TLAS, and Waiting on the GPU for why the CPU waits

On the CPU

  1. Prepare reads the ECS World into Frame data, and upload writes the frame's uniforms, lights and Instance writes into per-frame staging, recording their copies into GPU buffers at the head of the frame's commands, with the static TLAS's rebuild in a frame that writes or frees a static Instance. Pages: Prepare, Staging, The Instance buffer, and Camera-relative placement for the Anchor and offset each position is written as. Page: The static TLAS, for its rebuild

On the GPU

The GPU receives the steps below in this order, though on Metal a step can run beside the steps around it, or even start before an earlier one, where neither writes what the other binds (Metal quirks).

  1. The dynamic TLAS's build over the frame's Moving Instances, in frames that have any and once more, empty, when the last one goes, in a command buffer submitted ahead of the frame's commands. Page: The dynamic TLAS
  2. The bend pass, in frames that bend Meshes, which only the crowd scene does: each figure bent from its rest Mesh. With the crowd's refit form, chosen by a Render switch and available on Metal only, the frame's commands up to the bend pass are submitted first, with the refit of each figure's BLAS, and the dynamic TLAS's build follows them. Pages: The bend pass, The BLAS refit. Volume: Crowd Shadows Explained, for the crowd scene
  3. Phase one of the culling pass, which builds the draw of the Instances in view that were visible the frame before. Page: The culling pass, and Metal quirks for why the draw is built in slot order
  4. The Froxel pass, which lists for each Froxel the point lights that may reach it. Page: The Froxel pass, which opens with the light buffer it reads
  5. The depth pre-pass, which draws phase one's Instances into the 4x MSAA depth target, and with shadow rays on each sample's surface normals beside it. Page: The depth pre-pass, and Metal quirks for the flat input its fragments read
  6. The depth pyramid pass, which reduces that depth, level by level, to the farthest depth over each texel's share of the screen. Page: The depth pyramid pass
  7. Phase two of the culling pass, which builds the draw of the other Instances in view that the pyramid does not hide. Page: The culling pass
  8. With shadow rays on, as Praxis ships: phase two's depth pass, which draws phase two's Instances into depth and the surface normals (The depth pre-pass), then the shadow mask pass, which traces each pixel's shadow rays against both TLAS into the shadow mask, those of each edge pixel's second surface into its second layer, and a directional light's again from each sample of the pixels where its verdict differs from a neighbour's. Pages: The shadow mask pass, and The dynamic TLAS for the box that lets a ray skip its second query
  9. The lit pass, which shades both phases' Instances, reading each pixel's point lights from its Froxel's list and its shadows from the shadow mask, and resolves its 4x MSAA colour into the HDR target. Page: The lit pass, and Box filtering for what its samplers average
  10. The tonemapping pass, which maps the HDR target through GT7, encodes it as sRGB and dithers it into the 8-bit target. Pages: The HDR target, for what the lit pass resolves into and this pass reads; The tonemapping pass
  11. With the count_point_lights Render switch on, which ships off: the light count pass, which counts each lit pixel's point lights for the GPU stats. Page: The Froxel pass, its light count section

After the frame

  1. Each frame's GPU stats, its passes' timestamps and the counts the GPU wrote, come back through a ring of mapped buffers, a few frames late, and join the CPU's times, counters, heap allocations and GPU memory in Frame stats; with two frames in flight, the main thread waits each frame for the oldest one. Pages: Frame stats, and Waiting on the GPU for the frames in flight and where the main thread waits
  2. praxis bench measures each Reference scene along its camera path, and praxis compare judges the medians against the Baselines and Budgets. Page: The bench
  3. Each run is kept as Bench records on the bench-history branch, keyed by the source it measured; the quiet ones of main form the Series the Bench history page draws, a nightly sweep re-benches and bisects a Suspect among them, and a pinned Regression opens an issue. Page: The Bench history

What the pages lean on

Ideas several mechanisms share, each a page of its own.

  • The units every light value carries, glTF's photometric ones, and the EV100 exposure that brings the lit pass's luminance near display white. Page: Light units
  • How a pixel's samples and its fragments differ under 4x MSAA, how the samples resolve, and how Apple GPUs merge fragments. Page: MSAA
  • Why a box filter, as mips and anisotropic probes average texels, lets through detail finer than a pixel can show, and why a supersampled reference rewards blur on glints. Page: Box filtering
  • How a World position reaches the GPU as an Anchor plus an f32 offset, and how every shader composes it relative to the camera. Page: Camera-relative placement
  • Where the main thread waits for the GPU with two frames in flight, why a queue orders starts and not finishes, and why a blocked core clocks down. Page: Waiting on the GPU
  • What the reference machine's Metal backend does that no specification promises, from merging fragments to serialising queued frames, and the code that answers each. Page: Metal quirks
