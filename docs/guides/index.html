Praxis · engine reference

How a frame runs

Praxis is a 3D engine in Rust for large open-world games. This is its frame in the order data flows through it, from the assets cooked before it to the stats read back after it, each step linking the page that describes its mechanism.

Describes main at b3a8c555 (2026-11-04). A page describes its mechanism as it is at the commit its own Describes line names; where a step has no page yet, it links the volumes that narrate how that mechanism was built, each kept until its page replaces it.

Before the frame

  1. praxis cook turns the manifest's sources and the Reference scenes into Blobs, among them each texture's mips, averaged in linear light, with a normal map's roughness widened by Toksvig's measure. Volumes: Distant Textures Explained, Anisotropy Explained
  2. At load, each Mesh gets a BLAS, built and then, once the CPU has waited for the builds, compacted, and the static TLAS is built over the static Instances. Volumes: Acceleration Structures Explained, GPU Ordering Explained

On the CPU

  1. Prepare reads the ECS World into Frame data, and upload writes the frame's uniforms, lights and Instance writes into per-frame staging, recording their copies into GPU buffers at the head of the frame's commands, with the static TLAS's rebuild in a frame that writes or frees a static Instance. Volumes: Instance Buffer Explained, Acceleration Structures Explained, Lit Pass Explained, for the Environment prepare copies into Frame data

On the GPU

The GPU receives the steps below in this order, though on Metal a step can run beside the steps around it, or even start before an earlier one, where neither writes what the other binds.

  1. The dynamic TLAS's build over the frame's Moving Instances, in frames that have any and once more, empty, when the last one goes, in a command buffer submitted ahead of the frame's commands. Volume: Dynamic TLAS Explained
  2. The bend pass, in frames that bend Meshes, which only the crowd scene does: each figure bent from its rest Mesh. With the crowd's refit form, chosen by a Render switch and available on Metal only, the frame's commands up to the bend pass are submitted first, with the refit of each figure's BLAS, and the dynamic TLAS's build follows them. Volumes: Crowd Shadows Explained, BLAS Refit Explained
  3. Phase one of the culling pass, which builds the draw of the Instances in view that were visible the frame before. Page: The culling pass. Volumes it has not yet absorbed, for their Metal paragraphs: Instance Culling Explained, Meshlet Culling Explained
  4. The Froxel pass, which lists for each Froxel the point lights that may reach it. Volume: Froxel Lights Explained
  5. The depth pre-pass, which draws phase one's Instances into the 4x MSAA depth target, and with shadow rays on each sample's surface normals beside it. Page: The depth pre-pass
  6. The depth pyramid pass, which reduces that depth, level by level, to the farthest depth over each texel's share of the screen. Page: The depth pyramid pass
  7. Phase two of the culling pass, which builds the draw of the other Instances in view that the pyramid does not hide. Page: The culling pass
  8. With shadow rays on, as Praxis ships: phase two's depth pass, which draws phase two's Instances into depth and the surface normals (The depth pre-pass), then the shadow mask pass, which traces each pixel's shadow rays against both TLAS into the shadow mask, those of each edge pixel's second surface into its second layer, and a directional light's again from each sample of the pixels where its verdict differs from a neighbour's. Page: The shadow mask pass. Volumes it has not yet absorbed: Shadow Rays Explained, Edge Shadows Explained, Shadow Terminator Explained, and Dynamic TLAS Explained for its two queries
  9. The lit pass, which shades both phases' Instances, reading each pixel's point lights from its Froxel's list and its shadows from the shadow mask, and resolves its 4x MSAA colour into the HDR target. Page: The lit pass
  10. The tonemapping pass, which maps the HDR target through GT7, encodes it as sRGB and dithers it into the 8-bit target. Pages: The HDR target, for what the lit pass resolves into and this pass reads; The tonemapping pass. Volumes they have not yet absorbed: Tonemapping Pass Explained and HDR Pipeline Explained, for the light units and exposure
  11. With the count_point_lights Render switch on, which ships off: the light count pass, which counts each lit pixel's point lights for the GPU stats. Volume: Town Explained

After the frame

  1. Each frame's GPU stats come back through a ring of mapped buffers, a few frames late, and join the CPU's in Frame stats; with two frames in flight, the main thread waits each frame for the oldest one. Volumes: Frame Timing Explained, Waiting on the GPU Explained
  2. praxis bench measures each Reference scene along its camera path, and praxis compare judges the medians against the Baselines and Budgets; runs are kept as Bench records on the bench-history branch, whose Series the Bench history draws. Volume: Bench History Explained

What the pages lean on

Ideas several mechanisms share, each to become a page of its own, and two options the frame measured and did not take.

  • How a pixel's samples and its fragments differ under 4x MSAA, how the samples resolve, and how Apple GPUs merge fragments. Page: MSAA. Volume it has not yet absorbed: MSAA Fragment Merging Explained, for the merging
  • Why a box filter, as mips and anisotropic probes average texels, lets through detail finer than a pixel can show. Volume: Box Leakage Explained
  • A visibility pre-pass and a visibility buffer, ADR 0019's options B and D, against the depth pre-pass the frame keeps. Volumes: Visibility Pre-pass Explained, Visibility Buffer Explained
