Praxis · concept · src/capture/mod.rs

Waiting on the GPU

With two frames in flight, the main thread, which alone records, submits, polls and presents (ADR 0016), waits for the GPU in three places: for a swapchain texture, in the window; for the oldest frame in flight, in render_frames; and inside a frame wherever a GPU write must finish before the CPU or a later submission reads it. A queue orders when its command buffers start, not when they finish, so each such wait is explicit, and how the thread waits changes what its clock does next.

Describes main at 88941ee2 (2026-11-08). A concept the pages lean on; a change to how the main thread waits for the GPU, or to what a submission orders, rewrites this page and moves the commit. Pages that use it: Staging, The BLAS, The static TLAS, The BLAS refit, The dynamic TLAS, The shadow mask pass.

In the frame

Frames in flight
FRAMES_IN_FLIGHT, 2: "Frames submitted but not finished on the GPU when the next one starts, at most: the window's swapchain latency and capture's queue. Per-frame staging and the GPU stats readback are sized by it." The window asks the surface for the same, as desired_maximum_frame_latency.
The oldest frame
render_frames, which the bench, praxis capture and the Goldens render through, waits for it as its FrameWait says: Block, asleep until the GPU signals, or Spin, polling on its core. bench::run picks Spin on a hardware adapter and Block on a DeviceType::Cpu; capture and the Goldens pass Block. The window never goes through it: it waits in get_current_texture.
Inside a frame, on the CPU
compact_blases waits for the BLAS builds, then for the compaction copies, in a frame that loads Meshes; FrameStaging::write waits when every staging slot is still in flight; BlasRefit::submit waits for the refits where Metal makes no shared event (waits_on_cpu).
Inside a frame, on the GPU
The dynamic TLAS's build is submitted in a command buffer ahead of the frame's; the crowd's refits signal a shared event their submission completes, and the build's command buffer waits for it.
Frame stats
The CPU frame runs from FrameRecorder::begin, which State::update and update_settled call after the wait for the oldest frame, to FrameRecorder::end, after the frame's submit, so it counts the in-frame waits and not that one. heap_allocations counts the frame's allocations between the same two points, and the bench fails any increase.

1 · FRAMES_IN_FLIGHT · src/render/mod.rs

Two frames in flight

The CPU records frame N+1 while the GPU runs frame N, and may submit N+1 before N's last pass ends. Before it starts N+2, N must be done. Whatever the CPU writes for a frame has to outlive that frame on the GPU, so every per-frame ring is sized by the frames in flight.

The CPU records a frame's commands and hands them to the GPU, then starts the next frame. It may run ahead by a fixed number of frames; when the GPU is the slower of the two, the CPU reaches that limit in every frame and has to wait. Praxis lets two frames be in flight, and the window asks the surface for no more:

/// Frames submitted but not finished on the GPU when the next one starts, at
/// most: the window's swapchain latency and capture's queue. Per-frame
/// staging and the GPU stats readback are sized by it.
pub const FRAMES_IN_FLIGHT: usize = 2;

src/render/mod.rs. The window's surface configuration sets desired_maximum_frame_latency to the same constant (src/lib.rs), the balance wgpu's documentation recommends between latency and throughput, which ADR 0016 keeps at 2.

Three structures follow from it. Per-frame staging has SLOT_COUNT slots, FRAMES_IN_FLIGHT + 1: the two frames the GPU may still be copying from, plus the one the CPU is writing (Staging). The GPU stats readback is a ring of seven mapped buffers, sized by when a frame's timestamps can be copied and when their copy can be seen complete:

/// Frames after its own by which a frame's submission has completed: those
/// in flight and the one being recorded. Its timestamps resolve then.
const COMPLETION_LAG: u64 = FRAMES_IN_FLIGHT as u64 + 1;

/// Frames after the frame copying a slot's timestamps when its map is
/// requested at the earliest, once that copy completed. The bench has
/// waited for that frame by then, so each frame requests one map whatever
/// the GPU's timing, and the frame's first submission maps it
/// [ref:wgpu-30-submit-maintains]. A map requested with the copy maps in
/// whichever submission or poll first sees the copy complete
/// [ref:wgpu-30-map-after-submission], and wgpu allocates for it there
/// [ref:wgpu-30-handle-mapping]: inside a frame or between two, as the GPU's
/// timing falls.
const MAP_LAG: u64 = FRAMES_IN_FLIGHT as u64;

/// A slot's timestamps are copied `COMPLETION_LAG` frames after its frame.
/// A window polls only at a frame's start and through its submissions, so
/// the copy may be seen complete as late as `MAP_LAG` frames after it; its map is
/// then requested in the next frame and done by that frame's submissions,
/// and the slot is read, and reused, in the frame after.
const SLOT_COUNT: u64 = COMPLETION_LAG + MAP_LAG + 2;

src/render/readback.rs. Section 5 is about why the map is requested that late.

The third is the accounting. A stretch of GPU time can belong to two frames at once, since N+1's first submission may start before N's last pass ends, and the Frame stats have to give it to one of them: the GPU frame total takes, for each submission of a frame's passes, the span from its earliest start to its latest end, and counts the dynamic TLAS's build from the end of the frame before's last pass. That rule, and the one a render pass's own line follows, are the Frame stats page's; this page is about the waits.

2 · Queue::submit · device.poll

A queue is an order, not a timeline

The GPU starts each command buffer after the ones ahead of it in the queue have started, not finished. Work that reads what earlier work writes waits only where something tells the GPU so: a barrier the application records, or, on Metal, hazard tracking of a resource the work binds directly. Where neither reaches, the CPU has to wait, or order the pair itself.

The CPU records GPU work into command buffers and submits them to a queue. The queue keeps them in the order they were submitted, and that order is its whole promise. Apple's documentation says it in two places: a command queue "maintains an ordered list of command buffers", and of committing one, "The GPU starts the command buffer after it starts any command buffers that are ahead of it in the same command queue." Starts, not finishes. Its overview of resource synchronization opens with "By design, GPUs can run multiple commands in parallel", and wgpu's Metal backend says it as plainly in a doc comment: "Metal allows independent command buffers in a queue to overlap on the GPU".

In wgpu, a command buffer is what CommandEncoder::finish returns, and Queue::submit sends a batch of them as one submission. wgpu-core adds command buffers of its own: one of resource transitions ahead of each of yours, and one of copies that need no encoder, such as those of Queue::write_buffer and of a BLAS's compaction, which it keeps as its pending writes and puts ahead of them all in the next submission. The CPU learns that work has finished only by asking: device.poll with PollType::wait_indefinitely blocks the calling thread until the most recent submission has finished, and with a submission index, until that submission has.

Read after write

When one piece of GPU work writes memory that a later piece reads, the reader has to wait until the writer is done, or it may read old or half-written data. Vulkan and Direct3D 12 leave that to the application, which records a barrier between the two. Metal can handle it for you: for the resources it tracks, and that the work binds directly, it holds back work that reads what earlier work is still writing. Either way, something has to know that the second piece reads what the first one writes.

From Apple's Resource synchronization and wgpu-hal 30.0.1's acceleration-structure barrier in its Vulkan, Direct3D 12 and Metal command recorders.

Metal's tracking has an edge, and Praxis's two CPU waits for acceleration structures sit on it. A TLAS is built from its BLASes, so its build has to come after whatever writes them. On Metal, wgpu-hal builds every TLAS from a buffer of entries that name their BLASes by resource ID, the indirect instance layout; the build's descriptor names the buffer, not the BLASes, so Metal's tracking never learns that the build reads them. wgpu-core does know, and asks the backend for a barrier at that point; on Metal the function it calls records nothing. So nothing orders a TLAS build after a BLAS's compaction copy, or after its refit, beyond whatever the GPU happens to do (Metal quirks). The pair can be ordered three ways:

3 · render_frames · FrameWait · compact_blases

Where the main thread waits

Four waits are explicit in the code: the oldest frame in flight, every frame; a staging slot, only when the CPU has lapped the GPU; the compaction copies, in a frame that loads Meshes; and the refits, only where Metal makes no shared event. The window has a fifth, the swapchain's, that wgpu owns.

The bench, praxis capture and the Goldens render through render_frames, which keeps a queue of submission indices and, when two are in flight, waits for the oldest before it updates the next frame:

if in_flight.len() == FRAMES_IN_FLIGHT {
    let oldest = in_flight.pop_front();
    let timeout = match wait {
        FrameWait::Block => None,
        FrameWait::Spin => Some(Duration::ZERO),
    };
    loop {
        match context.device.poll(wgpu::PollType::Wait {
            submission_index: oldest.clone(),
            timeout,
        }) {
            Ok(_) => break,
            Err(wgpu::PollError::Timeout) => std::hint::spin_loop(),
            Err(error) => return Err(error.into()),
        }
    }
}
/// How `render_frames` waits for the oldest frame in flight.
#[derive(Clone, Copy)]
pub(crate) enum FrameWait {
    /// Blocks, as a window does in `get_current_texture`.
    Block,
    /// Polls until the frame is done. Behind a GPU-bound frame, the M4 Pro
    /// runs a main thread that blocks markedly slower for the whole next
    /// frame (measured: `docs/performance.md`, Measurements behind the
    /// code), so its CPU times would measure the clock, not the work. Apple
    /// asks games not to busy-wait, which holds a P-core and spends thermal
    /// headroom [ref:apple-tech-talk-110147-busy-waits], so only the bench
    /// spins, on a hardware adapter.
    Spin,
}

src/capture/mod.rs, render_frames and FrameWait. With Block, the poll's timeout is none: on Metal, wgpu-hal's fence wait is a condition variable that the command buffer's completion handler signals, so the thread sleeps until the frame is done and its core is free for other work, or to go idle. With Spin, each poll returns at once with PollError::Timeout until the frame is done, and the loop polls again with spin_loop between: the thread never leaves its core. Neither changes what the GPU does.

/// How a bench waits for the oldest frame in flight on `context`'s adapter:
/// a software rasterizer's threads would share the CPU with the spin.
fn frame_wait(context: &GpuContext) -> FrameWait {
    match context.adapter.get_info().device_type {
        wgpu::DeviceType::Cpu => FrameWait::Block,
        _ => FrameWait::Spin,
    }
}

src/bench/mod.rs, frame_wait, which render_run and traverse call. Capture and the Goldens pass FrameWait::Block. The window never goes through render_frames: it waits in the surface's get_current_texture for a swapchain texture to come free (src/lib.rs), and skips the frame when the surface reports a timeout.

Inside a frame

The compaction copies, at load. compact_blases waits twice, on every backend: once for the BLAS builds, so that each BLAS can say its compacted size, and once for the copies into the compacted BLASes, which wgpu-core keeps in its pending writes until something submits:

// The copies wait in the queue's pending writes until a submit.
queue.submit(std::iter::empty());
if let Err(error) = self.device.poll(wgpu::PollType::wait_indefinitely()) {
    tracing::error!(%error, "waiting for BLAS compaction failed");
}

src/assets/pools.rs, the end of compact_blases. The empty submit is what makes the poll useful: a poll waits only for work already submitted, so it sends the pending writes as a submission of their own, and the poll then waits for it. The wait is there because no barrier orders a TLAS build after the copies on Metal, and a static TLAS build that takes the new BLASes can be submitted in the same frame: a worker records it, and a frame that waits for that worker, as a capture's does, submits it right after the upload (The BLAS, The static TLAS). It runs only in frames that load Meshes: the first, and any frame whose streamed Chunks bring Meshes not loaded yet, which record the wait as their CPU stage blas_compaction.

A staging slot, when the CPU has lapped the GPU. Each frame writes its uploads into the next staging slot. If that slot is not mapped again yet, the GPU is still copying from it, two frames on, and the thread waits for every submission so far:

if !slot.is_mapped.load(Ordering::Acquire) {
    // Every slot is in flight: wait for the GPU to finish this one.
    slot.request_map();
    if let Err(error) = device.poll(wgpu::PollType::wait_indefinitely()) {
        tracing::error!(%error, "waiting for a frame staging slot failed");
    }

src/render/staging.rs, FrameStaging::write. Through render_frames it never happens, since the wait for the oldest frame comes first; a window could reach it if the surface let more frames in flight than the slots cover.

The refits, where there is no shared event. In the crowd's refit form, each frame's BLAS refits are submitted ahead of the dynamic TLAS's build, which reads them, and metal::Order orders the pair on the GPU: the refits' submission signals a shared event as it completes, and wgpu-hal's strict event sync holds every command buffer encoded after it, the build's among them, until the event reaches that value (The BLAS refit). Where Metal makes no shared event, BlasRefit::new logs it and every frame waits on the CPU instead:

if self.waits_on_cpu {
    let wait = wgpu::PollType::Wait {
        submission_index: Some(submission),
        timeout: None,
    };
    if let Err(error) = device.poll(wait) {
        tracing::error!(%error, "waiting for BLAS updates failed");
    }
}

src/render/blas_refit.rs, BlasRefit::submit. Correct and slow: the main thread stops in every frame until the refits are done. The refit form is behind a Render switch; the crowd ships with per-bone proxies, which refit nothing.

The dynamic TLAS's build itself needs no wait. The Renderer submits it in a command buffer of its own ahead of the frame's commands, in a frame that has Moving Instances and once more, empty, when the last one goes; the shadow mask pass that queries it binds it directly, so Metal's tracking orders the query after the build (The dynamic TLAS).

4 · FrameWait::Spin · Apple silicon

Blocking lowers the clock

Behind a GPU-bound frame, a main thread that blocks for the oldest frame ran its P-core about 30% slower for the whole next frame on the M4 Pro, and every CPU stage with it. The work did not grow; the clock fell. A CPU time measured behind a GPU-bound frame can measure the clock, not the work, which is why the bench spins and the window does not.

Apple's Tech Talk on CPU scheduling for Apple silicon games says that each cluster of cores "may be independently activated or have its frequency adjusted by the kernel's scheduler -- depending on the current workload, the current thermal pressure for that cluster, and other factors." A core's speed is not fixed, and how the scheduler weighs a thread that sleeps for most of each frame and runs for the rest is not published. What the measurement in docs/performance.md, "town's CPU stages slow because the P-core clocks down while the main thread waits", found is this:

The clock, not the work. Without root, the core's frequency cannot be read, so a measurement patch read it through work: a fixed chain of 2,000 dependent multiply-adds, timed on the main thread at three points of each frame. In the runs that blocked, the chain took 2.58 to 3.04 µs against 1.92 to 2.04 µs spin-waiting, and prepare_frame, which does the same work in every frame, 1,812 against 1,307 µs: the same ratio. Spin-waiting leaves the GPU as busy, with the GPU frame within 40 µs, so the load is not the cause; the wait's kind is.

Not migration, not priority. The thread never ran on an efficiency core and stayed on one performance cluster, whose cores share an L2, across the wait. A thread priority of 45 under the time-sharing policy took effect and left the stages as slow; a quality-of-service call left the thread at priority 31, which fits the ceiling xnu's task policy puts on an app-type task without an application role, though the patch did not read the role. The round-robin policy, which SDL gives a high-priority thread on Apple platforms, was not measured.

Not all of it. One blocking run kept a fast clock and still read its CPU frame about a millisecond over spin-waiting's, in its encode and submit stages. The measurements do not find what that is.

With one frame in flight the thread blocks for longer, about the whole GPU frame, and the chain is slow at the frame's start and fast again by the end of the frame's update: the frame then runs while the GPU is idle. With two in flight it runs beside the GPU and stays slow throughout. The clock also changes run to run with the same binary: one of four blocking runs kept it fast.

So the bench spins. Its CPU ceilings price the main thread's work when it is on the critical path, which is when the frame waits on the CPU; blocked behind a GPU-bound frame it is not, and its clock falls because it has the time. The window keeps blocking, as Apple asks: "Avoid busy waits. They potentially lock a P core, instead of doing something useful with it. They also prevents the scheduler from promoting a thread from and E to a P core. You are also wasting energy and producing unnecessary heat, eating away your thermal headroom." A GPU-bound game needs that headroom for its GPU, by this page's reading; the bench is not a game, runs for minutes, and must report the work. How the bench uses FrameWait, and what its spin may cost the GPU frame, is the bench page's.

5 · FrameStaging · MAP_LAG · prepare_encoder · Renderer::upload

Mapping late, so allocations never depend on the GPU's timing

wgpu maps a buffer, and allocates for the map, in the first submission or poll that finds the buffer's last submission finished: inside a frame or between two, as the GPU's timing falls. A map requested as soon as it could be done lands in a frame the GPU picks, and the frame's heap allocation count changes run to run. Three mechanisms request theirs a fixed number of frames later than they could, when the frame that copied from the buffer has certainly been waited for.

The bench holds heap_allocations, the main thread's allocations between a frame's begin and its end, to its Baseline and fails on any increase, as a counter that is the same on every run. For that to hold, nothing a frame allocates may depend on when the GPU finished the frames before it. wgpu's own bookkeeping is where it could: a map waits on the latest pending submission that uses the buffer, every submission ends by maintaining the device, which retires finished submissions and maps the buffers that waited on them, and each maintenance that finds buffers ready to map allocates the list of their callbacks. Per-frame staging requests each slot's map two writes after it was filled, when it is the next to be filled:

src/render/staging.rs. The GPU stats readback does the same with MAP_LAG (section 1): a slot's map is requested two frames after the frame that copied its timestamps, by which time render_frames has waited for that frame, so the requesting frame's first submission maps it. Each frame then requests exactly one map, which its own submission completes, and the allocation lands in the same frame on every run. The ring grew by one slot for it, to seven.

The dynamic TLAS's encoder is the third. A new command encoder reuses the encoder the GPU finished with last, and the state Metal keeps per encoder grows to the largest pipeline and bindings it recorded and never shrinks. The Renderer creates the build's encoder before the frame's, in DynamicTlas::prepare_encoder, so that the two swap roles every frame and each has recorded the frame's passes, and grown, within its first two frames; created in the other order, the passes would reuse the build's encoder in a frame the GPU's timing picks, and grow it there (The dynamic TLAS).

The swap needs both of a frame's encoders back in the pool, the build's first, before the next frame takes either. A submission retires whatever it finds finished, so if the main thread is held between the build's submit and the passes', as when the CPU runs other threads, the GPU finishes the build and the passes' own submission retires it. The build's encoder then waits in the pool alone. In a frame that starts with the frame before finished but not yet retired, the build takes that encoder again and the passes take an older one that has never recorded them, whose state grows in that frame: nine or ten more allocations on the M4 Pro, measured by holding the main thread there. So the upload retires the finished frames before the frame takes any encoder, and both come back in the order they were submitted:

// wgpu reuses the encoder retired last, so retire before taking any.
if let Err(error) = self.device.poll(wgpu::PollType::Poll) {
    tracing::error!(%error, "retiring finished frames failed");
}

Where nothing has finished, as when the frame before is still in flight, there is nothing to retire and the swap holds as before.

8 · ADR 0016

Why this way

The bench spins; the window blocks. The owner chose it over three others. CPU lines from a run with one frame in flight read close to spin-waiting's, but the clock's ramp after each wait stays in them, the frame runs while the GPU is idle, which is not how the engine runs, and each scene would run a third time. Spinning everywhere would read the window's CPU frame as the bench's, against Apple's advice, holding a P-core and spending the thermal headroom a GPU-bound frame needs. No change would keep the CPU lines reading the slowed clock whenever town is GPU-bound, over both of their ceilings, for a cost the frame does not pay. The chosen option costs no extra run and burns a P-core for the bench's few minutes only; it leaves the bench differing from the window in how it waits.

One thread submits, presents and polls. ADR 0016 keeps map and work-done callbacks at a known point of the frame, and wgpu-hal's Metal acquire sends a main-thread-only message on the calling thread, so a render thread would need a hand-off of the surface texture. One submitting thread is also what makes the event route safe: no worker can take a staged signal or wait between the refits' submission and the build's.

Two frames in flight. wgpu's documentation recommends 2 as the balance between latency and throughput, and ADR 0016 keeps it there; ADR 0013's Input latency budget of two frames leaves no room for more. Every per-frame ring is sized by the constant, so changing it changes staging's slots and the readback's ring with it.

A CPU wait at load, the GPU's order each frame. A wait suits work that happens once: the compaction copies cost it about a third of a millisecond at load, in three timed runs of their day, and no bench measures a load frame. Work in every frame could not pay that way, so the crowd's refits took the event route on the GPU, with the CPU wait as the fallback where no shared event can be made.

9

Limits

One machine measured. The clock's fall behind a blocking wait was measured on one M4 Pro; other Apple GPUs, other operating system releases and other vendors' machines may do otherwise, and the rule the scheduler follows is not published.

A remainder. The one blocking run that kept a fast clock still cost about a millisecond that the clock does not explain.

A CPU wait in every frame that loads Meshes. Meshes stream in with the Chunks that name them, so each frame that loads one stalls on the GPU twice, and the wait can go only when a wgpu release orders a TLAS build after compaction copies on every backend.

The event route is delicate. wgpu-hal's event staging is queue-wide: whichever submission comes next takes a staged signal or wait, and wgpu-core can submit on its own, as when it flushes pending writes to map a buffer. metal::Order relies on nothing submitting in between, which only one submitting thread can promise.

Seen, not reproduced, on the RTX 2070 SUPER. Under load, its Vulkan runs showed lone frames of five more allocations, then one, and once forty, which the encoder pool fits; only the M4 Pro was held between the two submits and measured, and the forty is not explained.

A software adapter blocks. lavapipe's rasterizer runs on the CPU, where a spinning main thread would take a core from it, so CI's CPU lines read the clock as a blocking thread's.

History

The wait for the compaction copies came from a test that flaked at load, a TLAS built right after a compaction copy missing its BLAS in a few of eighty iterations while other devices loaded the GPU; the eight-device test is its regression test. The crowd's refit, the same pair in every frame, took the event route on the GPU with the CPU wait as its fallback. The bench began spin-waiting when town's CPU stages read 20 to 40% slower once the GPU became the longer half of its frame, and the measurement found the clock. The late maps and the encoder swap came together, on 2026-11-01, when a frame's heap allocations were made independent of the GPU's timing; the retirement at the frame's start followed on 2026-11-08, when the allocation test still failed now and then on the RTX 2070 SUPER under load and a pause between the build's submit and the passes' reproduced it on the M4 Pro.
