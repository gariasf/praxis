The Froxel pass

A compute pass that cuts the view into 18,432 Froxels, 32 screen rectangles across, 18 down and 32 slices of depth each, and lists for every Froxel, in light order, the point lights of the light buffer whose range reaches into its bounds, so that the lit pass shades a pixel with its Froxel's point lights alone and a light left out would have added exactly zero.

Describes main at f097fd15 (2026-11-06). A change to the pass or the light buffer rewrites this page and moves the commit; nothing is appended. Read first: Light units for what a light's intensity holds, The shadow mask pass for the bits that follow each list, The lit pass for the shading that reads them.

Interface

Runs
Every frame, whatever the Render switches: recorded right after phase one of the culling pass, so that ADR 0019's gate counts it. With froxel_lights off the lists are still built; only the lit pass stops reading them.
Reads
The camera uniform; the light uniform, for how many directional and point lights the light buffer holds; the light buffer.
Writes
Each Froxel's list, a count and up to 127 indices into the light buffer, 9 MiB for all 18,432; the first field of the light counts, the lights the lists had no room for, which Frame stats read back.
Dispatches
One, build_froxel_lists: a workgroup per screen rectangle, 32 × 18, and an invocation per slice, 32, one per Froxel.
Bind groups
Group 3, Froxel lists: the camera, the light uniform, the light buffer, the lists and the light counts. Three passes read the lists, each through a group of its own: the lit pass through group 0, the frame; the shadow mask pass through its shadow mask build group; the light count pass through its input group.
Shader
src/render/shaders/froxel.wgsl, assembled with the common part and froxel_grid.wgsl, whose froxel_at the three readers share to find a pixel's Froxel.
Counted
froxel_pass in GPU time; froxel_lights_overflowed and, for the light buffer, lights_overflowed in counters; the lists and the light counts in GPU memory; with count_point_lights on, lit_pixels, listed_point_lights and reaching_point_lights.

The light buffer

Every light the frame draws is a 48-byte entry of one storage buffer of fixed capacity, the directional lights first and the point lights after them, a point light placed by an Anchor and an offset; a separate 32-byte uniform says how many of each it holds.

Prepare fills Frame data with every directional light, then every point light, each blended between its two newest Ticks, up to LIGHT_CAPACITY, 4,096, and the frame's upload writes them through its staging into the light buffer. The buffer is created at that capacity, 196,608 bytes, and never grows. Directional lights take their places first, so a full buffer leaves out point lights, farthest from the camera first, before any sun, and keeps the rest in the order it lists them under capacity; whatever it leaves out, prepare counts as lights_overflowed and warns of once, "Lights past the light buffer's capacity are not drawn", until a frame in which all fit.

let room = capacity - directional_light_count;
if point_light_count > room {
    point_light_distances.select_nth_unstable_by(room, |left, right| {
        left.0.total_cmp(&right.0).then(left.1.cmp(&right.1))
    });
    point_light_distances.truncate(room);
    point_light_distances.sort_unstable_by_key(|&(_, index)| index);
    for (kept, &(_, index)) in point_light_distances.iter().enumerate() {
        lights[directional_light_count + kept] = lights[directional_light_count + index];
    }
    lights.truncate(capacity);
}
*overflowed = (directional_lights_overflowed + point_light_count.saturating_sub(room)) as u32;
directional_light_count as u32

prepare_lights, src/render/prepare.rs.

A light is a LightData, with a WGSL twin in the common part that a test holds field for field to the Rust. A directional light has no position, so its offset carries the direction it shines along, its transform's forward axis; one scaled to nothing has no direction and is not drawn. Intensity is the light's colour times its intensity, in the units of Light units: candela for a point light, lux for a directional light.

The counts travel apart, in LightUniform: the scene's ambient illuminance, then directional_light_count and point_light_count. The Froxel pass reads both to find where the point lights start and end; every index a list holds is an index into the whole buffer, so it lands past the directional lights.

No World position reaches the GPU in f32 (ADR 0014). Prepare splits a point light's position into its Anchor and an f32 offset from the cell's corner, as it splits an Instance's, and each shader composes it relative to the camera with point_light_position:

position = (anchor − camera anchor) × 64 m + (offset − camera offset)

The integer difference is exact, so the composed position rounds in proportion to its distance from the camera, not from the World's origin. Prepare's test places a point light at (100,000.25, 2, −64.5) and expects the Anchor (1562, 0, −2) and the offset (32.25, 2, 63.5).

2 · src/render/renderer.rs

Where it sits in the frame

The pass reads nothing another pass writes, only the frame's uniforms and lights, so it can run as early as the lists are needed; it is recorded after the first culling dispatch so the gate, which starts there, counts the lights' culling.

The frame's passes with shadow rays on, in the order the GPU receives them

  1. dynamic TLAS build
  2. bend pass
  3. culling, phase one
  4. Froxel pass
  5. depth pre-pass
  6. depth pyramid pass
  7. culling, phase two
  8. phase two's depth pass
  9. shadow mask pass
  10. lit pass
  11. tonemapping pass
  12. light count pass

The passes ringed warm read the lists: the shadow mask pass, to give each listed point light its bit; the lit pass, to shade each pixel's point lights; and, with the count_point_lights switch on, which ships off, the light count pass after the frame's others. On Metal the Froxel pass can run beside phase one of the culling pass, and now and then start before it, since neither writes what the other binds.

pub fn record(
    &self,
    encoder: &mut wgpu::CommandEncoder,
    timestamp_writes: Option<wgpu::ComputePassTimestampWrites<'_>>,
) {
    encoder.clear_buffer(&self.light_counts, 0, None);
    let mut pass = encoder.begin_compute_pass(&wgpu::ComputePassDescriptor {
        label: Some(FROXEL_PASS),
        timestamp_writes,
    });
    pass.set_pipeline(&self.pipeline);
    pass.set_bind_group(FROXEL_LISTS.index, &self.bind_group, &[]);
    pass.dispatch_workgroups(FROXEL_COLUMNS, FROXEL_ROWS, 1);
}

3 · froxel_grid.wgsl

Froxels: rectangles on screen, slices in depth

The screen is cut into 32 × 18 rectangles of one size, and each rectangle's view into 32 slices of depth that grow three to each doubling, so every Froxel from 1 m to 1,024 m has the same shape, only larger with distance; the last slice reaches to infinity, as depth has no far plane.

ConstantValueWhat it fixes
FROXEL_COLUMNS32rectangles across the screen: 80 pixels at 2560 wide, 20 at the Goldens' 640
FROXEL_ROWS18rectangles down it: 80 pixels at 1440 high
FROXEL_SLICES32slices of view depth per rectangle, and the workgroup's size
FIRST_FROXEL_SLICE_DEPTH1.0metres: slice 0 takes everything nearer
FROXEL_SLICES_PER_OCTAVE3.0slices to each doubling of depth
FROXEL_LIGHT_CAPACITY127lights a list holds; with its count a list is 512 bytes
FROXEL_COUNT18,432lists in all, 9,437,184 bytes

From froxel_pass.rs at the commit above; Rust declares them into the WGSL when each module is assembled.

Depth here is the distance along the view axis, which a point's clip w holds. Slice 0 runs from the camera to 1 m; slices 1 to 30 follow at three to each doubling, 1 to 1.26 m, 1.26 to 1.59 m, and on to 812.7 to 1,024 m; slice 31 runs from 1,024 m to infinity.

fn froxel_slice_start(slice: u32) -> f32 {
    let octaves = (f32(slice) - 1.0) / FROXEL_SLICES_PER_OCTAVE;
    return select(FIRST_FROXEL_SLICE_DEPTH * exp2(octaves), 0.0, slice == 0u);
}

fn froxel_slice(depth: f32) -> u32 {
    let slice = floor(log2(depth / FIRST_FROXEL_SLICE_DEPTH) * FROXEL_SLICES_PER_OCTAVE) + 1.0;
    return u32(clamp(slice, 0.0, f32(FROXEL_SLICES - 1u)));
}

froxel_grid.wgsl.

A rectangle's height grows in proportion to its distance: at the camera's 45° vertical field of view a row of rectangles is about 4.6% of the distance tall. A slice spans the same ratio of depths wherever it lies, 21/3 ≈ 1.26, so its depth is about 26% of the distance where it starts. Each Froxel is therefore about five times as deep as it is wide, at every distance. Exponential slices shrink without end towards the camera, so slice 0 takes everything nearer than 1 m; depth is reversed with no far plane (ADR 0015), so the last slice runs to infinity and every visible point has a Froxel.

A Froxel's index puts the slices of one rectangle side by side, the rectangles counted from the lowest normalised device coordinates, as clip space counts them:

index = (row × 32 + column) × 32 + slice
4 · build_froxel_lists

The sphere test

A point light's range is a sphere. The pass drops a light from a Froxel only when the sphere lies wholly outside one of the six planes that bound it, so it never drops a light that reaches the Froxel and sometimes keeps one that does not.

The camera sits at the origin of every position the shaders see, and view_proj holds no translation (ADR 0014), so each rectangle side is a plane through the camera. A side at normalised x = a is where clip x − a · clip w = 0; with row0 to row3 the rows of view_proj, its normal is row0 − a · row3, and clip x − a · clip w over that normal's length is a point's signed distance from it. A sphere lies wholly outside the side only when its centre is farther outside than its range. Each invocation computes its rectangle's four normal lengths once; a slice's two planes stand square to the view axis, where clip w is already the distance.

let froxel = froxel_index(rectangle.xy, slice);
var count = 0u;
let end = light.directional_light_count + light.point_light_count;
for (var index = light.directional_light_count; index < end; index++) {
    let point = lights[index];
    let centre = point_light_position(point, camera.anchor, camera.offset);
    let clip_x = dot(rows[0].xyz, centre);
    let clip_y = dot(rows[1].xyz, centre);
    let depth = dot(rows[3].xyz, centre);
    let inside_sides = vec4<f32>(
        clip_x - lowest.x * depth,
        highest.x * depth - clip_x,
        clip_y - lowest.y * depth,
        highest.y * depth - clip_y
    );
    // Its range reaches into the Froxel unless it lies wholly outside a
    // side or beyond the slice: conservative, as a sphere may miss a
    // corner that it reaches past both sides of.
    if all(inside_sides >= -point.range * normal_lengths)
        && depth + point.range >= nearest
        && (last_slice || depth - point.range <= farthest) {
        if count < FROXEL_LIGHT_CAPACITY {
            froxel_lists[froxel].lights[count] = index;
        }
        count++;
    }
}

build_froxel_lists, froxel.wgsl; rows is view_proj transposed, lowest and highest the rectangle's corners in normalised device coordinates, nearest and farthest its slice's depths.

Each plane test is exact; together they are not. A sphere near a Froxel's corner can reach past two sides' planes and still miss the edge where they meet, and the light is listed though its range never enters the Froxel. A plane through the camera shows on screen as a rectangle edge, so the rectangles that list a light are those under its outline's bounding box, and the false positives are the box's corners the outline misses; the outline of a sphere in front of the camera is an ellipse, stretched towards the screen's edges. A false positive costs the lit pass one light evaluated to zero at each pixel of that Froxel, and the image nothing, unless a list or a pixel's shadow mask runs out of room (Limits).

Why a skipped light changes nothing: a point light falls off with the square of the distance inside KHR_lights_punctual's range window, which reaches 0 at the range and stays there.

attenuation = clamp(1 − (distance / range)4, 0, 1) / distance2

5 · FroxelList

The lists: one writer each, in light order

Each invocation owns one list and walks the point lights in buffer order, so the lists need no atomics and each comes out in light order: the lit pass then adds a pixel's nonzero terms in the order brute force adds them, and the image does not depend on which thread ran first.

The dispatch launches 576 workgroups of 32 invocations: an invocation's slice is its index in its workgroup, its rectangle the workgroup's position. Its list sits at its Froxel's index in one buffer of FroxelList entries, a count and 127 indices into the light buffer each.

FroxelList, 128 × u32: light_count, then lights[0] … lights[126] for example: 3, 1, 3, 4, … the sun is light 0; this Froxel lists point lights 1, 3 and 4

Light order matters because the lit pass sums luminance in f32, which rounds after every addition: (1 + 3×10−8) + 3×10−8 is 1 in f32, while 1 + (3×10−8 + 3×10−8) is 1.00000012, and a last-bit difference can tip a pixel to the next 8-bit code. Gathering a tile's lights with atomics, as Forward+ does, would make a list's order depend on which thread gets in first.

An invocation keeps counting past 127, stores the smaller of its count and 127, and only if its list overflowed adds the rest to froxel_lights_overflowed with one atomic add; integer addition gives the same total in any order, so the count is exact. A full list keeps its first 127 lights in light order; the others light nothing in that Froxel.

froxel_lists[froxel].light_count = min(count, FROXEL_LIGHT_CAPACITY);
if count > FROXEL_LIGHT_CAPACITY {
    atomicAdd(&light_counts.froxel_lights_overflowed, count - FROXEL_LIGHT_CAPACITY);
}

froxel.wgsl.

A few frames later the CPU reads the counter back with the frame's other GPU stats. It becomes Frame stats' froxel_lights_overflowed, and the first frame read back with an overflow warns, once until a frame has room for all: "The Froxel lists are full: lights past a list's capacity do not light its Froxel".

6 · froxel_at · main.wgsl

Who reads the lists

A reader finds a pixel's Froxel from the pixel itself, its place on the target for the rectangle and its view depth for the slice, through one shared function; the lit pass shades every directional light, then that Froxel's point lights in list order.

fn froxel_at(point: vec2<f32>, size: vec2<f32>, view_depth: f32) -> u32 {
    let rectangle = clamp(
        floor(vec2<f32>(point.x / size.x, 1.0 - point.y / size.y) * FROXEL_GRID_SIZE),
        vec2<f32>(0.0),
        FROXEL_GRID_SIZE - 1.0
    );
    return froxel_index(vec2<u32>(rectangle), froxel_slice(view_depth));
}

froxel_grid.wgsl; point is in pixels from the target's top left corner, so the row is flipped to count from the bottom, as normalised device coordinates do.

The lit pass takes the view depth as clip w of its fragment's camera-relative position and the target's size from the shadow mask, a target of the same size. A Render switch, froxel_lights, which ships on, sets the WGSL override FROXEL_LIGHTS when the pipeline is created; off, the loop runs over every point light in buffer order, brute force, the reference the lists must match.

The shadow mask pass gives each pixel's word a bit per light in the order the lit pass sums them: the directional lights, then its Froxel's list, entry by entry, with the Froxel's slice in the word's top bits so the lit pass can tell whose list the bits follow (The shadow mask pass). The light count pass

With the count_point_lights Render switch on, which ships off, a compute pass after the frame's others counts how tight the lists are. An invocation per pixel of the depth target, in 8 × 8 tiles, takes the pixel's first sample; where the frame drew a surface there, it rebuilds the sample's position relative to the camera, finds its Froxel with froxel_at, and counts the point lights the Froxel lists and, of those, the ones whose range reaches the position. Each workgroup sums its pixels in workgroup memory, and one invocation adds the sums to the light counts, which Frame stats read back as lit_pixels, listed_point_lights and reaching_point_lights; Frame stats print the last two per lit pixel.

fn camera_relative_point(clip: vec4<f32>) -> vec3<f32> {
    let rows = transpose(camera.view_proj);
    let x_row = rows[0].xyz;
    let y_row = rows[1].xyz;
    let w_row = rows[3].xyz;
    let y_cross_w = cross(y_row, w_row);
    return (clip.x * y_cross_w + clip.y * cross(w_row, x_row) + clip.w * cross(x_row, y_row))
        / dot(x_row, y_cross_w);
}

light_count.wgsl: the point is the solution of view_proj's x, y and w rows, which hold no translation, by Cramer's rule in cross products. The view depth is the near plane's distance over the stored depth, under reverse Z with no far plane.

Listed against reaching is a measure of the sphere test's false positives at the surfaces the frame shows. The pass reads the depth the main pass keeps at the frame's end instead of counting in the lit pass: a fragment shader with side effects, such as atomic adds, makes the GPU run it before the depth test, for fragments it then rejects, which would slow the lit pass and count hidden surfaces.

9 · ADRs 0014, 0015, 0019, 0023

Why this way

Lists per Froxel, not per tile or per depth bin. ADR 0019 weighed two other ways to cut light lists. Tiled culling, as in Forward+, lists each screen tile's lights between the nearest and farthest opaque depth in it, so a tile across a depth discontinuity takes in the gap, and transparent surfaces in front of the opaque depth need lists of their own. Z-binning keeps a bit mask of lights per tile and a table of the lowest and highest light index in each depth bin, intersected per pixel when it shades. A Froxel's list is built once against bounds fixed in advance, independent of the depth buffer, so one set of lists serves the opaque pass and the transparent pass to come.

Exponential slices, not equal ones. Slices equal in normalised depth come out very thin near the camera and very long far away; slices equal in view depth, the reverse. Exponential spacing keeps the Froxels self-similar. Cubical cells would take about fifteen slices to each doubling at this rectangle size, five times as many lists; three keep the lists at 9 MiB.

Sphere against six planes, kept simple. Tighter tests exist: one shrinks the sphere, slice by slice and row by row, to each plane it crosses, and culls better than a test against each cell's box at a similar cost. The simple test is exact on every plane and errs only towards keeping a light, which costs time and never the image, and the light count pass measures how much it keeps.

On the GPU, one writer per list. Building the lists in a compute pass keeps the CPU's frame free of a per-light, per-cell loop; giving each invocation its own list keeps them in light order without atomics, so the lists and brute force sum the same terms in the same order and can be compared pixel for pixel.

A fixed capacity, counted. Neither the light buffer nor the lists grow at runtime (ADR 0003); a light past either is left out and counted in Frame stats, so a scene that reaches a capacity shows it. Both capacities are provisional until ADR 0013's split of the 8 GB Budget sizes them.

Anchors and reverse Z throughout. A light's position composes relative to the camera from its Anchor, as ADR 0014 requires of every World position; the last slice reaches to infinity because ADR 0015's projection has no far plane.

10

Limits

False positives take places. A light listed where its range never enters takes one of a list's 127 places: where more than 127 lights pass a Froxel's test, it can push a later light that does reach the Froxel off the end, and that light lights nothing there. With shadow rays on it also takes a bit: a pixel's word gives the directional lights their bits first, then the entries of its Froxel's list in order, up to 59, whether or not each entry's light reaches the pixel, so a false positive can push a later light past the bits, and that light casts no shadow there. Both are counted.

Point lights only. Directional lights are never culled; every pixel shades all of them. Spot lights do not exist yet; a cone would be listed by its bounding sphere unless the test learns its shape.

One list per Froxel, whatever the surface. A Froxel deep enough to hold a wall and the street behind it lists the lights of both; nothing narrows a list to the depths the frame shows.

Every invocation tests every point light. The work grows with the lights and not with what they reach: 18,432 tests for each, before any is listed.

Fixed capacities. 4,096 lights and 127 a list, both provisional.

History

The pass took its form in one step of the third milestone, in three parts: the light buffer replaced a uniform that held one directional and four point lights; the Froxel pass built the lists; the lit pass looked each pixel's Froxel up, with brute force kept as the reference. Since then the town scene's 1,024 lamps gave the lists the load they were built for, the light count pass came to measure their false positives, and the shadow mask pass came to give each listed light its bit. A light's place in the buffer once also depended on whether it cast a shadow; that distinction is gone, and every point light now casts one. The volume that narrated each part, with its measurements, is retired; this page describes the mechanism as it is.
