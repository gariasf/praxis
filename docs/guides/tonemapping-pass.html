The tonemapping pass

The frame's last timed pass: one triangle over the target that reads each pixel's exposed colour from the HDR target, undoes the resolve's weighting, maps it through GT7's tone curve to display colour, encodes it as sRGB in the shader and adds two steps of triangular blue-noise dither before the 8-bit target rounds it.

Describes main at fbae12f4 (2026-11-04). A change to the pass rewrites this page and moves the commit; nothing is appended. Read first: The HDR target for what the pass reads, HDR Pipeline Explained for the light units and the EV100 exposure that set where mid-grey lands.

Interface

Runs
Every frame, after the lit pass, as its own render pass into the frame's target: the window's surface or a capture's texture.
Reads
The HDR target, one texel per pixel; the dither mask, a 64×64 R8Unorm texture loaded once at creation.
Writes
Every pixel of the target, an 8-bit UNORM format that is not sRGB: Bgra8Unorm or Rgba8Unorm for the surface, Rgba8Unorm for a capture.
Draws
One triangle of three vertices from vs_full_screen, with no vertex buffer, shaded by fs_tonemap.
Bind groups
Group 3, tonemapping input: the HDR target and the dither mask, rebuilt by bind_render_targets after every resize.
Shader
src/render/shaders/tonemapping.wgsl, assembled after the HDR, GT7 and display parts: hdr.wgsl, gt7.wgsl, display.wgsl.
Counted
tonemapping_pass in GPU time; the dither mask's 4,096 bytes in GPU memory.

1 · TonemappingPass::record · fs_tonemap

One triangle over the target

The pass draws a single triangle that covers the target and computes each pixel's display colour from that pixel's texel alone: no filter, no neighbours, no history.

The frame's passes with shadow rays on, in the order the GPU receives them

  1. dynamic TLAS build
  2. bend pass
  3. culling, phase one
  4. Froxel pass
  5. depth pre-pass
  6. depth pyramid pass
  7. culling, phase two
  8. phase two's depth pass
  9. shadow mask pass
  10. lit pass
  11. tonemapping pass

The vertex shader places its three vertices at (−1, −1), (3, −1) and (−1, 3) from the vertex index, a triangle whose part inside clip space is the whole target. The render pass clears the target first, since the triangle covers every pixel and a clear spares the load, and stores what the fragment shader writes.

@fragment
fn fs_tonemap(@builtin(position) position: vec4<f32>) -> @location(0) vec4<f32> {
    let pixel = vec2<u32>(position.xy);
    let weighted = textureLoad(hdr_target, pixel, 0).rgb;
    let encoded = srgb_encode(tonemap(resolve_unweighted(weighted)));
    // DITHER_MASK_SIDE, a power of two declared from Rust's
    // (src/render/shaders/mod.rs), tiles the mask with a bit mask.
    let noise = dither_noise(textureLoad(dither_mask, pixel % DITHER_MASK_SIDE, 0).r);
    return vec4<f32>(encoded + noise / 255.0, 1.0);
}

tonemapping.wgsl.

The four steps follow in order: resolve_unweighted turns the resolved texel back into exposed colour (The HDR target); tonemap maps exposed colour to display-linear colour in [0, 1]; srgb_encode turns that into the encoded values a display expects; and the dither adds noise of up to one 8-bit step either way, which the target's rounding to 8 bits then resolves.

TonemappingPass::new checks, in debug builds, that the target format is not sRGB, since the shader encodes and an sRGB view would encode again. It creates the pipeline, the dither mask and the bind group that reads the HDR target; bind_render_targets builds that group again whenever a resize creates the targets again.

2 · tonemap, display.wgsl

Exposed 1 as paper white

GT7 works in its own frame-buffer units, 100 cd/m² each, and in Rec. 2020's primaries. Praxis reads exposed 1 as GT7's SDR paper white, 2.5 units, and converts the scene's Rec. 709 colour into Rec. 2020 and back around it, so GT7's linear section keeps exposed mid-tones as the exposure set them.

fn tonemap(exposed: vec3<f32>) -> vec3<f32> {
    let display = gt7_tonemap(REC709_TO_REC2020 * exposed * GT7_PAPER_WHITE);
    return clamp(REC2020_TO_REC709 * display, vec3<f32>(0.0), vec3<f32>(1.0));
}

display.wgsl. REC709_TO_REC2020 is ITU-R BT.2087-0's matrix; its inverse is derived from the two recommendations' primaries and D65, to seven places.

With the paper white at exposed 1, GT7's linear section, frame-buffer 0.538 to 1.11, falls at exposed 0.2152 to 0.444, and there a grey maps to itself. Exposed 1 shows at 0.835, on the shoulder. Clipping back into Rec. 709 after the conversion is what keeps an output channel from going negative where a saturated Rec. 2020 colour lies outside Rec. 709.

3 · gt7_curve, gt7.wgsl

The curve: a toe, the identity, a shoulder

GT7's tone curve, at its published parameters, darkens the darks along a power toe, is the identity through the mid-tones, and rolls the brights over an exponential shoulder that meets the identity with the same value and slope.

fn gt7_curve(frame_buffer: f32) -> f32 {
    let peak = GT7_PAPER_WHITE;
    let alpha = 0.25;
    let mid_point = 0.538;
    let linear_section = 0.444;
    let toe_strength = 1.28;
    // The shoulder's rise past the linear section's end, over the peak: the
    // sample's k.
    let shoulder_rise = (linear_section - 1.0) / (alpha - 1.0);
    let shoulder_limit = peak * linear_section + peak * shoulder_rise;
    let shoulder_scale = -peak * shoulder_rise * exp(linear_section / shoulder_rise);
    let shoulder_rate = -1.0 / (shoulder_rise * peak);
    if frame_buffer < 0.0 {
        return 0.0;
    }
    if frame_buffer < linear_section * peak {
        let linear_weight = smoothstep(0.0, mid_point, frame_buffer);
        let toe = mid_point * pow(frame_buffer / mid_point, toe_strength);
        return (1.0 - linear_weight) * toe + linear_weight * frame_buffer;
    }
    return shoulder_limit + shoulder_scale * exp(frame_buffer * shoulder_rate);
}

gt7.wgsl, ported from Polyphony Digital's sample implementation under its MIT licence, which the file carries.

x < 1.11: (1 − s) · 0.538 · (x / 0.538)^1.28 + s · x, s = smoothstep(0, 0.538, x) x ≥ 1.11: k_A + k_B · e^(k_C · x) k = (0.444 − 1) / (0.25 − 1) = 0.7413 k_A = 2.5 · 0.444 + 2.5 · k = 2.963, 1.19 times the peak

The linear section ends at 0.444 of the peak, frame-buffer 1.11. Below the mid point the toe blends into the identity by a smoothstep; from 0.538 to 1.11 the curve is the identity; past 1.11 it rises towards 2.963, and gt7_tonemap clamps the result to the peak, 2.5, before dividing by it.

4 · gt7_tonemap

Colour and the path to white

The curve applied to each channel alone shifts a bright colour's hue. GT7 blends that result 40/60 with one that keeps the input's chroma in ICtCp at the curve's intensity, and fades that chroma to white as the input's intensity passes the paper white's.

fn gt7_tonemap(rgb: vec3<f32>) -> vec3<f32> {
    let ictcp = rec2020_to_ictcp(rgb);
    let skewed = vec3<f32>(gt7_curve(rgb.r), gt7_curve(rgb.g), gt7_curve(rgb.b));
    let skewed_intensity = rec2020_to_ictcp(skewed).x;
    let paper_white_intensity = rec2020_to_ictcp(vec3<f32>(GT7_PAPER_WHITE)).x;
    let chroma_scale = 1.0 - smoothstep(0.98, 1.16, ictcp.x / paper_white_intensity);
    let scaled = ictcp_to_rec2020(vec3<f32>(skewed_intensity, ictcp.yz * chroma_scale));
    let blended = 0.4 * skewed + 0.6 * scaled;
    return min(blended, vec3<f32>(GT7_PAPER_WHITE)) / GT7_PAPER_WHITE;
}

gt7.wgsl.

ICtCp, from ITU-R BT.2100, separates intensity from chroma through SMPTE ST 2084's PQ curve, which pq_encode and pq_decode implement with BT.2100's constants. The forward matrices are BT.2100's Table 7; the inverse ones are the sample's, to six digits. Red and blue hold their hue to about exposed 1.4, while green picks up some red from about exposed 0.5; brighter, red whitens through orange, green through yellow and blue, with the least luminance of the three, through violet, last.

5 · srgb_encode

Encoded once, in the shader

The pass encodes sRGB itself and writes an 8-bit UNORM target that stores the encoded value as it is, so the dither it adds after the encoding lands on the target's 8-bit steps. No target in the engine is an sRGB format.

fn srgb_encode(display: vec3<f32>) -> vec3<f32> {
    let clamped = clamp(display, vec3<f32>(0.0), vec3<f32>(1.0));
    return select(
        1.055 * pow(clamped, vec3<f32>(1.0 / 2.4)) - 0.055,
        12.92 * clamped,
        clamped <= vec3<f32>(0.0031308)
    );
}

display.wgsl: IEC 61966-2-1's encoding, as the Khronos Data Format Specification restates it.

The window takes the 8-bit UNORM format its surface offers, Bgra8Unorm or Rgba8Unorm, and refuses a surface that offers neither; a capture renders into Rgba8Unorm. An sRGB format would encode again what the shader encoded, so a convention test finds any sRGB format named outside the sampled textures the assets and the cooker make.

6 · dither_noise · DITHER_MASK

The dither: two steps of triangular blue noise

A dim gradient spans few 8-bit codes and bands. The pass adds noise of triangular density over two steps peak to peak, the least that makes the rounding error's power independent of the signal, drawn from a fixed blue-noise mask so the grain is fine, even and the same in every frame.

fn dither_noise(mask_value: f32) -> f32 {
    let uniform = (round(mask_value * 255.0) + 0.5) / 256.0;
    let centred = 2.0 * uniform - 1.0;
    return sign(centred) * (1.0 - sqrt(1.0 - abs(centred)));
}

display.wgsl.

The mask is Christoph Peters's 64×64 blue-noise texture LDR_LLL1_0.png, CC0, committed under assets/BlueNoise/ and compiled into the binary as its red channel, dither_mask.bin, since a build without the cook feature links no PNG decoder and the cook would store it lossy. It holds each of its 256 levels 16 times, so its values are uniform. dither_noise reads each level at the centre of its bin and turns it by the inverse of the triangular distribution's CDF, as Peters remaps a mask for dithering, which keeps the mask's arrangement: over the 256 levels the noise's mean is 0, its variance 1/6 and its extremes ±0.9375 steps.

pub(crate) const DITHER_MASK_SIDE: u32 = 64;
const _: () = assert!(DITHER_MASK_SIDE.is_power_of_two());

const DITHER_MASK: &[u8; (DITHER_MASK_SIDE * DITHER_MASK_SIDE) as usize] =
    include_bytes!("dither_mask.bin");

tonemapping_pass.rs.

The noise goes on after the encoding because that is where the rounding happens; in linear light near black, where the encoding multiplies by 12.92, the same noise would be 12.92 times too large. The same value goes to all three channels, and the mask tiles the screen by a bit mask on the pixel's coordinates, which the side being a power of two allows. Nothing animates it.

9 · ADRs 0008, 0018, 0021, 0023

Why this way

GT7 over the other operators. Of the operators that take saturated light to white, analytic and permissively licensed, GT7 is the only one built for both SDR and any HDR peak, so it would carry over to HDR output; its linear section keeps the mid-tones the scenes' exposure sets; and its sample implementation is MIT, so the shader can be ported and checked against it. AgX, Blender's default, gives a softer, desaturated look, and PBR Neutral, Khronos's operator for product rendering, keeps base colours most faithfully; both are SDR only. Reinhard and Hable never take saturated colours to white, the ACES 1 fits shift blue through magenta or over-saturate brights, and Tony McMapface is a lookup table with no HDR form. There is no operator switch: grading, when it comes, would bake the operator into a lookup table.

A path to white, between per-channel and luminance-only. A curve per channel shifts hue as the brightest channel tops out; a curve on luminance alone holds hue but leaves saturated highlights outside the display's range. Film and cameras desaturate very bright colour toward white, which GT7's ICtCp blend does.

Encoding in the shader into an 8-bit UNORM target. The dither must land on the target's steps, so the shader must write encoded values that the target stores as they are. A non-sRGB view of an sRGB surface would allow that too, but it needs a wgpu downlevel flag outside the Capability floor of ADR 0021, which Vulkan reports only with an extension; writing a UNORM surface needs nothing.

Triangular noise, two steps, after the encoding. Rectangular noise of one step leaves the error's power varying with the signal; triangular noise of two steps peak to peak is the least that makes it constant, so the grain does not itself band. It goes in the encoded domain, where the rounding is.

Blue noise, fixed to the screen. Blue noise has no low frequencies, so it reads as finer grain than white noise, and unlike an ordered Bayer pattern it shows no grid. Fixed and never animated, it keeps Goldens exact and needs no history, which ADR 0008 keeps out of the frame.

A bit mask, not a modulo. Tiling the mask by its texture's size with a modulo cost about 38 µs more at 1440p on the Apple M4 Pro than a bit mask on a constant power of two, so the side is a constant the build asserts is one.

The mask compiled in. A shipping build without the cook feature links no PNG decoder, and ADR 0018's cook would store the mask with lossy compression, so its 4,096 bytes are in the binary, with a test that holds them to the committed asset.

10

Limits

SDR output only. HDR displays take values above SDR white: EDR on Apple's platforms, scRGB on Windows, PQ for HDR10. wgpu can configure each, and GT7 has a path to any display peak, but the pass writes SDR alone; an HDR path would be a second output with its own tests.

No bloom. Nothing scatters light brighter than white into its surroundings.

A fixed exposure. Each Reference scene sets its EV100 by hand; histogram adaptation and local tone mapping wait for a scene that joins an interior and sunlight or changes the time of day.

One noise for three channels. The channels tend to move together, so a colour's grain is luminance grain, never chroma.

No grading. GT7 is the only operator and nothing adjusts it per scene.

History

The pass came with the move to photometric light in the third milestone, in steps measured against each other: a clamp-only pass over a new fp16 target, then the weighted resolve, GT7, the shader's own sRGB encoding and the dither, after a survey of operators, targets, dithers, displays and bloom chose each. The development narrative, with each step's measurements, the operator sweep and the live demos, is in the notebook's volumes until the pages absorb them: Tonemapping Pass Explained and HDR Pipeline Explained. This page describes the pass as it is; the volumes describe how it got here.
