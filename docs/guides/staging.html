Staging

How the frame's bytes reach GPU buffers: FrameStaging writes each frame's uploads, the camera and light uniforms, the lights, the bends and the changed Instances, into the next of three mapped staging buffers in a fixed turn and records their copies into the frame's encoder ahead of its passes, while LoadStaging carries a Scene's loads through a StagingBelt that is dropped with the submission that copies them.

Describes main at b3d764b4 (2026-11-04). A change to the frame's staging, the uniforms, what Renderer::upload writes or the load path's staging rewrites this page and moves the commit; nothing is appended. Read first: Prepare for the Frame data this step uploads, The Instance buffer for the slots the Instance copies land in, Waiting on the GPU Explained for frames in flight and what the CPU waits on.

Interface

Called
Renderer::upload, once a frame, after prepare and before Renderer::render, which records the frame's passes into the same encoder and submits it. LoadStaging while a Scene loads; its copies are submitted at the head of the next upload.
Reads
Frame data: the camera, the light uniform, the lights, the bends, the Instances with their writes, and the Instance slot count; the static TLAS's Anchor and the dynamic TLAS's box, which upload folds into the camera uniform.
Writes
Six GPU buffers, by copies from a staging slot: the camera buffer, the light uniform buffer, the light buffer, the bend buffer, the Instance buffer and the Instance slot count buffer. At load: the Mesh pool's Arenas and tables, the Material buffer and each Texture's mips, and the BLAS builds that read them.
Buffers
SLOT_COUNT slots, FRAMES_IN_FLIGHT plus one, three, each MAP_WRITE and COPY_SRC, all of one size that grows on demand up to the bound. The load path's belt allocates in chunks of LOAD_CHUNK_BYTES, 1 MiB.
Counted
In Frame stats: uploaded_bytes, the bytes the frame's slot carried plus the dynamic TLAS's instance records; instances_written; the slots in gpu_memory_bytes, the load path's belt not; the CPU stage upload.
Where in the code
src/render/staging.rs, src/render/uniforms.rs, Renderer::new and Renderer::upload in src/render/renderer.rs.

1 · Renderer::upload

One upload a frame, at the head of its commands

Every byte the CPU writes into the frame's GPU buffers goes through one call, all but the TLAS instance records, which wgpu stages itself: upload gathers the frame's writes into one iterator, FrameStaging::write copies them into one staging slot and records a copy per write into the frame's encoder, and render then records the passes after those copies, so every pass reads this frame's data.

What upload does, in order

  1. submit the loads staged since the last frame
  2. compact their BLASes
  3. prepare the dynamic TLAS's encoder
  4. create the frame's encoder
  5. static TLAS rebuild, if the frame changes it
  6. fill the dynamic TLAS
  7. staging copies
  8. then render's passes

The loads go first, in a submission of their own, so a Mesh or Texture loaded since the last frame is on the GPU before any copy or draw of this one. The frame's encoder then takes the static TLAS's rebuild, when the frame's Instance writes change a static Instance, and after it the copies. The dynamic TLAS is filled before the copies because its fill returns the box that holds its entries, which the camera uniform carries; its build goes in a command buffer of its own, which render records and submits ahead of the frame's.

The two uniforms are written every frame. The light buffer is written whenever the frame has lights, which every Reference scene does, since each has a sun; the bends whenever any Mesh is bent; the Instances only for the slots prepare wrote, a copy per run of consecutive slots; and the slot count only when it changed, which in a scene that spawns and despawns nothing is on its first frame alone. A frame where only the camera moves therefore writes no Instance at all (ADR 0003).

2 · src/render/uniforms.rs

What a frame writes

Two small uniforms are rewritten whole every frame, the camera's 144 bytes and the lights' 32; everything else is an array written as far as the frame fills it: 48 bytes a light, 20 a bend, 128 an Instance.

LightUniform and CameraUniform, src/render/uniforms.rs.

CameraUniform is 144 bytes: the 64-byte view-projection matrix, then five rows of 16 bytes, each a 12-byte vector followed by a 4-byte value (exposure, dynamic_tlas_entries) or padding. Prepare fills the matrix, the camera's Anchor and offset and the exposure; upload fills the rest from the two TLAS, as quoted above. LightUniform is 32 bytes: the ambient illuminance as a 16-byte vector, the two light counts and 8 bytes of padding. The Rust-only padding fields start with _, and a test holds both structs field by field against their WGSL twins.

3 · FrameStaging::new

The bound: every buffer upload writes, in full

A slot grows on demand to the next power of two of what a frame needs, and never past the most one frame can upload, which is the six target buffers' sizes summed: 67,387,572 bytes. A frame that asks for more is a bug, and the write asserts.

// The most a frame uploads: every buffer `upload` writes, in full.
let frame_staging = FrameStaging::new(
    [
        &camera_buffer,
        &light_uniform_buffer,
        &light_buffer,
        &instance_buffer,
        culling_pass.instance_slot_count(),
        bend_pass.bends(),
    ]
    .iter()
    .map(|buffer| buffer.size())
    .sum(),
);

Growth replaces all three slots at once with new ones of the new size, created mapped; a replaced slot still in flight lives until the GPU is done with it, and dropping one whose map is pending fails that map, which mark_mapped leaves unset. Slots never shrink. pbr-sweep's first frame uploads 1,700 bytes, its ten Instances, the slot count and the frame's usual 416, so in a capture of it the slots grow once, to 2,048 bytes each, 6,144 bytes of gpu_memory_bytes, and every later frame fits. The largest power of two under the bound is 226, 67,108,864 bytes, so a frame that needs more than that, such as one that writes every slot of the Instance buffer, gets slots of exactly the bound rather than of 227.

4 · FrameStaging::write · StagingSlot::request_map

The turn and the late map

Each write fills slot N and requests the map of slot N+1, the one written FRAMES_IN_FLIGHT writes ago, so, once the caller has waited for that frame, as the bench does, the map's completion lands in a frame's own submission and the frame's heap allocations do not depend on the GPU's timing. A slot not yet mapped when its turn comes is waited for: if the CPU laps the GPU, it waits.

/// Slots the per-frame uploads cycle through: the frames in flight, plus the
/// one being written. A fixed count keeps `gpu_memory_bytes` the same on
/// every run.
const SLOT_COUNT: usize = FRAMES_IN_FLIGHT + 1;

/// Staging memory for the per-frame uploads, reused every frame, where
/// `Queue::write_buffer` creates a fresh staging buffer on every call. Its
/// slots grow on demand, never past the most one frame uploads. Each frame
/// fills the next slot in turn, copies it into its targets, and requests the
/// map of the slot it fills next, last filled `FRAMES_IN_FLIGHT` writes
/// before. The fixed turn keeps the frame's heap allocations the same on
/// every run: wgpu grows an encoder's tracking by each buffer's tracker
/// index, so which slot a frame takes changes its allocation count. So does
/// the late map, for the reason the GPU stats readback maps late: the bench
/// has waited for the frame that copied from the slot, so the frame's own
/// submission maps it, whatever the GPU's timing
/// [ref:wgpu-30-handle-mapping].
pub struct FrameStaging {
    slots: Vec<StagingSlot>,
    slot_size: u64,
    /// The most one frame uploads, which no slot grows past.
    max_slot_size: u64,
    next_slot: usize,
}

struct StagingSlot {
    buffer: wgpu::Buffer,
    /// Set by the map callback once `buffer` is mapped for writing again.
    is_mapped: Arc<AtomicBool>,
    /// Whether its map was requested since it was last written.
    map_requested: bool,
}

SLOT_COUNT, FrameStaging and StagingSlot, src/render/staging.rs.

With FRAMES_IN_FLIGHT at 2 there are three slots, and the frames take them in a fixed turn, 0, 1, 2, 0 and so on, never whichever happens to be mapped. The turn is fixed because wgpu grows an encoder's tracking by each buffer's tracker index: a frame that took a different slot would allocate a different number of times.

let index = self.next_slot;
self.next_slot = (self.next_slot + 1) % SLOT_COUNT;
self.slots[self.next_slot].request_map();
let slot = &mut self.slots[index];
if !slot.is_mapped.load(Ordering::Acquire) {
    // Every slot is in flight: wait for the GPU to finish this one.
    slot.request_map();
    if let Err(error) = device.poll(wgpu::PollType::wait_indefinitely()) {
        tracing::error!(%error, "waiting for a frame staging slot failed");
    }
    if !slot.is_mapped.load(Ordering::Acquire) {
        // Its map failed, so the buffer is unmapped: map it again.
        tracing::error!("frame staging slot not mapped; skipping the frame's uploads");
        slot.map_requested = false;
        slot.request_map();
        return 0;
    }
}

A slot is not asked to map again as soon as it is unmapped. Its map is requested one write before its turn, two writes after the frame that copied from it. By then the bench has waited for that frame, so the buffer is ready to map when the request is made, and wgpu-core maps it in the next maintenance, which is this frame's own first submission: in a frame with Moving Instances, the dynamic TLAS build's. wgpu-core allocates the list of map callbacks in each maintenance that finds buffers ready to map. Were the map requested early, the GPU's finishing time would decide which submission or poll found it ready, in this frame or between two, and so which frame paid that allocation. The GPU stats readback maps late for the same reason.

The wait is the rare case. When the slot whose turn it is has not mapped, the write requests its map, if that was not done, and blocks in device.poll until the GPU finishes. If the slot is still unmapped after that, its map failed: the write logs an error, requests the map again for a later turn, and returns 0 bytes, skipping the frame's uploads. map_requested keeps a slot from being asked twice between two writes, since wgpu refuses a second map of a buffer whose map is pending.

impl StagingSlot {
    /// Requests the map of its buffer for writing, unless it is mapped or
    /// its map was requested since it was last written.
    fn request_map(&mut self) {
        if !self.map_requested && !self.is_mapped.load(Ordering::Acquire) {
            self.map_requested = true;
            self.buffer
                .map_async(wgpu::MapMode::Write, .., mark_mapped(&self.is_mapped));
        }
    }
}

/// A map callback that sets `is_mapped` on success. A failure leaves it unset
/// for `write` to report; dropping a slot whose map is pending, as `resize`
/// does, fails it too.
fn mark_mapped(
    is_mapped: &Arc<AtomicBool>,
) -> impl FnOnce(Result<(), wgpu::BufferAsyncError>) + use<> {
    let is_mapped = is_mapped.clone();
    move |result| {
        if result.is_ok() {
            is_mapped.store(true, Ordering::Release);
        }
    }
}

5 · FrameStaging::write

Filling a slot and recording the copies

The writes are packed end to end from the slot's start, each followed by its copy into its target, then the slot is unmapped and handed to the GPU. An empty transition_resources first sizes the encoder's buffer tracking to every buffer at once.

{
    let Ok(mut mapped) = slot.buffer.slice(..).get_mapped_range_mut() else {
        tracing::error!("frame staging slot not mapped; skipping the frame's uploads");
        return 0;
    };
    // An empty transition sizes the encoder's buffer tracking to
    // every buffer at once. The copies alone grow it buffer by buffer
    // in tracker-index order, which depends on what earlier States
    // created and dropped, so the frame's heap allocations would too.
    encoder.transition_resources(std::iter::empty(), std::iter::empty());
    let mut offset = 0;
    for (target, target_offset, bytes) in uploads {
        let size = bytes.len() as u64;
        debug_assert!(size.is_multiple_of(wgpu::COPY_BUFFER_ALIGNMENT));
        mapped
            .slice(offset as usize..(offset + size) as usize)
            .copy_from_slice(bytes);
        encoder.copy_buffer_to_buffer(&slot.buffer, offset, target, target_offset, size);
        offset += size;
    }
}
slot.buffer.unmap();
slot.is_mapped.store(false, Ordering::Release);
slot.map_requested = false;
needed

FrameStaging::write, src/render/staging.rs.

The empty transition is the companion of the fixed turn. Each copy_buffer_to_buffer makes the encoder track its two buffers, and copies alone grow that tracking buffer by buffer in tracker-index order. Which indices a frame's buffers hold depends on what earlier states of the engine created and dropped, so the tracking would grow in a different number of steps from one run to the next, and the frame's heap allocation count with it. A transition of no buffers and no textures sizes the tracking to every buffer at once, before any copy.

Every write's length is a multiple of COPY_BUFFER_ALIGNMENT, 4 bytes, as the debug assertion checks: each struct the frame uploads is a whole number of 4-byte fields. The copies are recorded before any pass, and the slot is unmapped before the frame is submitted, since wgpu refuses to submit work that uses a mapped buffer.

6 · uploaded_bytes

Counting the bytes

uploaded_bytes is what the frame's slot carried plus what the dynamic TLAS's build uploads, its instance records. A write that returns 0 means the frame's uploads were lost, and the next prepare writes every Instance again.

FrameStaging::write returns the bytes it packed, which upload adds to the frame's counters. render adds a second term: when the dynamic TLAS records a build, it returns the bytes that build uploads, one backend instance record per entry its fill placed, which wgpu-core converts each entry to and stages itself. On Metal a record is a MTLIndirectAccelerationStructureInstanceDescriptor, 72 bytes; on Vulkan and DX12 it is 64. So a frame's count is, exactly:

144 + 32 the two uniforms + 48 × lights where the frame has lights + 20 × bends where it has bends + 128 × Instances written a copy per run of slots + 4 when the slot count changed + 72 × dynamic TLAS entries on Metal; 64 elsewhere
/// Bytes the frame's uploads wrote to GPU buffers: the camera and light
/// uniforms, the light buffer, the bends, the Instances it wrote, the
/// Instance slot count when it changed, and the dynamic TLAS's instances
/// its build uploads. Pools upload only while a Scene loads.
pub uploaded_bytes: u64,

FrameStats, src/stats/mod.rs.

When the write returns 0 with Instances queued, those writes never landed, and the slots on the GPU hold what an earlier frame wrote. upload then sets lost_instance_writes; the next frame's update takes it through take_lost_instance_writes and calls rewrite_all_instances before prepare, so that frame writes every slot once. Only a frame whose write succeeded adds its Instances to instances_written and records the slot count as uploaded.

7 · LoadStaging

The load path

Loads use a StagingBelt and one encoder that live only until submit: the belt goes with the submission, so load staging never stays resident and never counts in gpu_memory_bytes. Its bound is in time, not in bytes.

/// The `StagingBelt`'s allocation unit at load: a larger write gets a chunk
/// of its own.
const LOAD_CHUNK_BYTES: u64 = 1 << 20;

/// Staging for load-time uploads (ADR 0017): each write goes through a
/// `StagingBelt` into a copy on one encoder, with the BLAS builds that read
/// them, which `submit` sends ahead of the next frame's. The belt goes with
/// it, so its staging buffers live only until the GPU has run the copies and
/// never count in `gpu_memory_bytes`.
pub struct LoadStaging {
    device: wgpu::Device,
    pending: Option<(wgpu::util::StagingBelt, wgpu::CommandEncoder)>,
}

impl LoadStaging {
    pub fn new(device: wgpu::Device) -> Self {
        Self {
            device,
            pending: None,
        }
    }

    /// Records a copy of `bytes` to `target` at `offset`; the length and the
    /// offset are multiples of `wgpu::COPY_BUFFER_ALIGNMENT`.
    pub fn write(&mut self, target: &wgpu::Buffer, offset: wgpu::BufferAddress, bytes: &[u8]) {
        let Some(size) = wgpu::BufferSize::new(bytes.len() as u64) else {
            return;
        };
        let (belt, encoder) = self.pending();
        belt.write_buffer(encoder, target, offset, size)
            .copy_from_slice(bytes);
    }

LoadStaging, src/render/staging.rs.

The Mesh pool writes each Mesh's vertices, indices, Meshlets and table entry through write into its Arenas, and records the BLAS build of a traced Mesh through build_blas, after the copies it reads. The Material pool and the tonemapping pass write their buffers and Textures the same way. write_texture copies a mip's rows of blocks into the belt at a pitch of COPY_BYTES_PER_ROW_ALIGNMENT, 256 bytes, which a buffer-to-texture copy requires, so the cooked mip needs no padding of its own; a mip smaller than a block copies one whole block.

/// Submits the copies recorded since the last call, if any.
pub fn submit(&mut self, queue: &wgpu::Queue) {
    if let Some((mut belt, encoder)) = self.pending.take() {
        belt.finish();
        queue.submit(std::iter::once(encoder.finish()));
    }
}

LoadStaging::submit, src/render/staging.rs.

The belt's chunk size, LOAD_CHUNK_BYTES, 1 MiB, is only its allocation unit: a write larger than every free chunk gets a chunk of its own. Nothing caps the bytes one load stages, so a Scene's whole load can sit in the belt until upload submits it at the head of the next frame, after which the belt is dropped and its buffers are freed once the GPU has run the copies. upload then compacts the new BLASes before the static TLAS takes them.

10 · ADRs 0003, 0013, 0016, 0017

Why this way

Owned slots, not Queue::write_buffer. wgpu's own documentation says that on native platforms each write_buffer stages through a new allocation released after the next submission, and suggests a belt or buffers created, mapped and unmapped by hand to avoid short-lived allocations. ADR 0017 sends uploads through staging the engine owns; for the per-frame uploads the engine takes the second suggestion, so a frame allocates no staging memory once its slots have grown.

A fixed count of fixed-size slots, not a belt, for the frame. A belt allocates more chunks on demand, so its memory would vary with what frames happened to need. Three slots of one size keep gpu_memory_bytes the same on every run, and ADR 0013 counts that sum against the GPU memory Budget.

Three slots for two frames in flight. ADR 0016 keeps the surface's frame latency at 2 and has the main thread alone submit, so two frames may be on the GPU while the CPU fills the third slot; wgpu completes a map only after the last submission using the buffer finishes, so the ring decides whether the CPU waits, never whether a write is safe.

A fixed turn and a late map. The bench's heap_allocations counter fails on any increase over its Baseline, so it has to repeat run to run. Taking whichever slot is mapped, or requesting a map as soon as a slot is unmapped, would tie the count to the GPU's timing; the turn and the late map tie it to the frame number alone.

Bounded by what a frame can write. The Instance buffer has a fixed capacity and never grows (ADR 0003), and so do the light and bend buffers, so the most a frame can upload is known at creation. Bounding the slots there keeps growth from rounding a full Instance upload up to the next power of two, three times over.

Only what changed. ADR 0003 has prepare write only the slots of new Renderables and of those whose World transform, Mesh or Material changed, plus every Moving Instance, so camera motion writes no Instance and a static scene's frame carries only its uniforms and lights.

A belt for loads. Loads are large, rare and of no fixed size, the case a belt is for; dropping it with each submission keeps load staging out of resident memory. ADR 0017 also has streaming uploads go through a belt, never Queue::write_texture, which stages each call afresh.

11

Limits

The slots never shrink. One frame that writes every Instance slot leaves three slots of 67,387,572 bytes, 202,162,716 bytes of staging, for the rest of the run.

One frame's uploads succeed or fail together. A failed map skips every write of the frame, the uniforms included, so that frame draws with the last frame's camera and lights, and the next writes every Instance again.

The wait blocks the main thread. When the CPU laps the GPU the write polls until the GPU has finished all the work submitted to it, the frame that held the slot among it; nothing else runs meanwhile.

No cap on a load. ADR 0017 caps the bytes streaming writes into the belt each frame at the staging Budget, so an upload past the cap waits for a later frame; streaming is not built, and LoadStaging stages a whole load at once, however large.

What uploaded_bytes leaves out. The static TLAS's instance records, which wgpu-core stages when a frame rebuilds it, and the load path's bytes are not counted; the counter is the frame's slot and the dynamic TLAS's build.

History

The per-frame uploads left Queue::write_buffer for reused staging slots in the engine's first weeks, and soon after went to the Instance buffer as one copy per run of written slots, while Meshes and then Textures began loading through the belt. The slots were bounded at the most a frame can write when the Instance buffer took its fixed capacity, and the load encoder took the BLAS builds when every Mesh gained one. The light buffer, the bends, the slot count and the dynamic TLAS's records joined the uploads as their mechanisms landed. Last came the fixed turn, the late map and the empty transition, which made a frame's heap allocations independent of the GPU's timing. Instance Buffer Explained narrates the slots and their bound, and Dynamic TLAS Explained the records the TLAS uploads. This page describes the mechanism as it is; the volumes describe how it got here.
