Frame stats

Frame stats are what one frame cost, measured by the engine itself: on the CPU, a clock around each ECS system and each renderer stage, the thread's allocation count and the counters the frame's own code keeps; on the GPU, a timestamp at each end of every timed pass and the counts the passes wrote, which come back through a ring of mapped buffers seven frames later and are turned into a time per pass, a GPU frame total that is a span rather than a sum, ADR 0019's gate and the lit pass's wait.

Describes main at 7d8f0a57 (2026-11-06). A change to what a frame measures, when it reads it back or how its timestamps become times rewrites this page and moves the commit; nothing is appended. Read first: The dynamic TLAS and the BLAS refit for the markers that time work no pass brackets, The bench for what reduces these stats into Baselines, Waiting on the GPU Explained for the frames in flight the ring is sized by and where the main thread waits.

Interface

Recorded
The CPU side from FrameRecorder::begin, the first line of State::update, to FrameRecorder::end, the last of State::render. The GPU side as the passes run: GpuStatsReadback::begin_frame hands the frame's passes their timestamp queries, which mark each pass run in the frame's log as it takes them, end_frame copies the counts the GPU wrote into the frame's slot, and the slot is read seven frames later by begin_frame, or by flush at the end of a run. State::frame_stats returns the last frame's.
Reads
On the CPU, the clock around each stage, the spans bevy_ecs enters around each system, the thread's allocation count, the preparer's refusals and the GPU memory ledger's totals by kind. On the GPU, the query set's timestamps, the culling pass's FrameDraw, the Froxel pass's LightCounts and the shadow mask pass's overflow count.
Writes
One FrameStats per frame, whose gpu is None until that frame's GpuFrameStats come back, and for good if their readback was skipped.
Buffers
One query set of 168 timestamps, 24 per slot; a 192-byte resolve buffer, since queries resolve only into a buffer the CPU cannot map; and seven slots of 288 bytes each, MAP_READ and COPY_DST, holding a frame's draw, its light counts, its overflow count and then its timestamps. ADR 0013 leaves all of them out of gpu_memory_bytes, since they measure the frame rather than hold it.
Counted
Of itself, only gpu_readbacks_skipped, the slots that were still copying or mapping when their frame came round. Every other field is another mechanism's cost; praxis capture writes the last frame's to standard output, and praxis bench reduces every measured frame's into a Baseline's form (The bench). The window shell reads none of them.

What a frame's stats are

A frame's stats are two structs: what the CPU measured while it ran the frame, complete when the frame is submitted, and what the GPU measured of it, which arrives a few frames later and is slotted in by frame number.

FrameStats holds the CPU's times and every counter. Its cpu_times list the ECS systems and renderer stages in run order, each with its wall-clock time; cpu_frame_time runs from the start of State::update to the end of State::render. The counters are what each mechanism refused or left out, which the preparer, the upload and the acceleration structures write into the recorder as they go.

GpuFrameStats is what the GPU measured of one frame, tagged with that frame's number. Its pass_log says which of the twelve Timed passes the frame ran, how each was timed and the submission it was recorded into (section 3). Its pass_times hold a time for each of them in the order they ran; a pass that did not run in the frame, as the dynamic TLAS's build in a frame that had nothing to build, or with the crowd's rebuild form, which never brackets it, reads as taking no time. Three spans stand beside them, each defined in section 5, and the counts the GPU wrote: the Instances and triangles the frame's draw held, phase two's share of those triangles, and the overflows of the draw, the Froxel lists and the shadow mask. With the count_point_lights Render switch on, the lit pixels and the point lights their Froxels list and whose range reaches them join; they read 0 with it off.

Where they go

FrameStats prints as four lines, each a label and then key=value pairs: the CPU times, the GPU times when they are there, the counts and the GPU memory. praxis capture renders its 60 frames, waits for the last readbacks with flush_gpu_frame_stats, slots each GpuFrameStats into the frame it names, and writes the last frame's four lines to standard output under the image. praxis bench keeps every frame's and reduces the measured ones into medians and p95s, the Measurements a Baseline is a copy of; The bench says how. The window shell asks for none of them.

The CPU side

One recorder lives in the State and is reset at the start of every frame. Stages are timed by whoever runs them, with a clock they start and hand back; systems are timed by a tracing subscriber that sees the span bevy_ecs enters around every system run; allocations are counted by the global allocator, per thread, and read twice.

Stages

FrameRecorder::begin clears the systems' runs and the stages, resets the counters, reads the thread's allocation count and starts the clock. A stage is recorded by the code that ran it: it takes an Instant before the work and calls stage after it with the stage's name, and a stage recorded twice in one frame, as the dynamic TLAS's recording is, adds its times. end closes the frame and takes the allocation count again. The lists are sized by the first frames and never allocate after.

FrameRecorder, src/stats/mod.rs
    /// Starts measuring a frame.
    pub(crate) fn begin(&mut self) {
        self.systems.reset();
        self.stages.clear();
        self.counters = FrameStats::default();
        self.allocations_at_start = thread_allocations();
        self.started = Instant::now();
    }

    /// Records the CPU time of `stage`, which began at `started`, added to
    /// what the frame already recorded of it, and returns the time this call
    /// recorded.
    pub(crate) fn stage(&mut self, stage: &'static str, started: Instant) -> Duration {
        let time = started.elapsed();
        match self.stages.iter_mut().find(|(name, _)| *name == stage) {
            Some((_, recorded)) => *recorded += time,
            None => self.stages.push((stage, time)),
        }
        time
    }

    /// Ends the frame `begin` started.
    pub(crate) fn end(&mut self) {
        self.counters.cpu_frame_time = self.started.elapsed();
        self.counters.heap_allocations = thread_allocations() - self.allocations_at_start;
    }

Systems

bevy_ecs's trace feature enters a tracing span named system around every system run. A span reports to the subscriber that was the default when it was created, whatever the global subscriber filters, so State::new builds its schedules inside SystemTimer::scope, which makes the timer the default subscriber for that closure and nothing else. The timer accepts only spans named system from a bevy_ecs target, keeps each system's name without its module path or generic arguments, and on every exit pushes the run's time in run order. Events logged inside the scope are dropped.

Heap allocations

The crate's global allocator is CountingAllocator, the system allocator with a thread-local counter in front of it. Every alloc, alloc_zeroed and realloc adds one; dealloc adds nothing. The counter is read through try_with, since an allocator may not panic, and the cell has no destructor, so it outlives everything its thread allocates. A frame's count is the difference between the two readings on the thread that ran it: whatever the compute pool's workers allocate is not in it.

Bytes uploaded

uploaded_bytes is what the frame's writes cost the GPU in bytes. Renderer::upload hands the frame's camera and light uniforms, its light buffer, its bends, the Instances it writes and, when it changed, the Instance slot count to the per-frame staging ring (Staging), which returns the bytes it copied; 0 means the slot failed to map and the frame's Instance writes are lost, to be written again. The dynamic TLAS's build adds the bytes of the entries it uploads. Loads stage outside the ring, and of them only the copies that move a Texture from its Resident tail's Texture class to its whole chain's count here, in the frame whose upload submits them.

GPU memory

gpu_memory_bytes is the engine's own ledger, kept the same way on every backend, because wgpu-hal's default allocator report is None and Metal keeps the default (ADR 0013). Renderer::new makes one GpuMemory for its adapter and hands it to every owner it creates: the render targets, the passes, the Mesh and Material Pools, both TLAS, the BLAS refit and the per-frame staging. Each creates its buffers and textures through it, under one of ADR 0017's kinds of GPU memory, and keeps the Counted resource it gets back in place of wgpu's. The ledger holds a running total per kind, so State::frame_stats reads seven numbers and adds them, walking no resource and no mip chain.

impl Charge {
    pub fn set(&mut self, kind: GpuMemoryKind, bytes: u64) {
        let total = &self.totals[kind as usize];
        total.fetch_add(bytes, Ordering::Relaxed);
        total.fetch_sub(self.bytes[kind as usize], Ordering::Relaxed);
        self.bytes[kind as usize] = bytes;

impl Drop for Charge {
    fn drop(&mut self) {
        for kind in GpuMemoryKind::ALL {
            self.set(kind, 0);
        }
    }
}

A Charge adds its bytes to its kinds' totals when made and takes them back when dropped, so a resize's new render targets replace the old ones' bytes as the old ones go. A Texture class's array of Material Textures is charged in two kinds, every slice whether it holds a Texture or not: each mip of RESIDENT_TAIL_LEVEL_BYTES, 64 KiB, or less per slice is part of its slices' Resident tail, the rest the texture pool's. A buffer counts its size. A texture counts through texture_bytes, once, at creation: the theoretical footprint of each level of its mip chain, summed and multiplied by its sample count, except a transient attachment on an adapter that keeps one in tile memory, which counts 0; the lit pass's 4x colour attachment is memoryless on Apple GPUs. Acceleration structures have no size wgpu exposes, so each TLAS is charged the estimate for its capacity, from bytes measured once per adapter, and the Mesh pool keeps one Charge for its BLASes, set again from its compacted and uncompacted triangles at each load and compaction (ADR 0017).

texture_bytes and level_bytes, src/stats/gpu_memory.rs
fn texture_bytes(texture: &wgpu::Texture, transient_saves_memory: bool) -> u64 {
    if transient_saves_memory
        && texture
            .usage()
            .contains(wgpu::TextureUsages::TRANSIENT_ATTACHMENT)
    {
        return 0;
    }
    level_bytes(texture).sum::<u64>() * u64::from(texture.sample_count())
}

/// Bytes of each level of `texture`'s mip chain at one sample.
fn level_bytes(texture: &wgpu::Texture) -> impl Iterator<Item = u64> + '_ {
    (0..texture.mip_level_count()).map(|level| {
        let size = texture.size().mip_level_size(level, texture.dimension());
        texture.format().theoretical_memory_footprint(size)
    })
}

Three things the engine creates stay out of the sum, each for a reason ADR 0013 records. The GPU stats readback's query set, resolve buffer and slots measure the frame rather than hold it. The target the frame is presented into is the caller's: a window's surface textures are the surface's, not the engine's, and capture's stand-in for them is left out so that a capture counts what a windowed run counts. Capture's read-back buffer is the caller's for the same reason. The load staging belt lives only until its copies have run and never counts. arena_bytes_in_use is the Mesh pool's Arenas' occupied bytes, kept beside the total because the total counts each Arena whole whatever it holds. allocator_report_bytes is wgpu's own report where a backend has one, a diagnostic that the bench records nowhere.

Dropped time

State::update runs the Ticks the frame's delta completes, under a cap, and simulate returns the simulated time past the cap it skipped; the recorder keeps it as dropped_time, the amount the game slowed by (ADR 0022).

The timestamp queries

Twelve timed passes, two queries each: a frame owns 24 consecutive queries of one query set, and each pass is handed the pair at its position, as a compute pass's or a render pass's timestamp writes, or as the markers that bracket work no pass can time.

The timed passes, in TIMED_PASSES' order

  1. dynamic TLAS build
  2. bend pass
  3. BLAS refit
  4. culling, phase one
  5. Froxel pass
  6. depth pre-pass
  7. depth pyramid pass
  8. culling, phase two
  9. phase two's depth pass
  10. shadow mask pass
  11. lit pass
  12. tonemapping pass

The three marked passes run in some frames only: the dynamic TLAS's build where the frame has Moving Instances or the fill before held some, so an emptied TLAS is rebuilt once, the bend pass where it bends Meshes, the BLAS refit where it bent them with the crowd's refit form. Phase two's depth pass and the shadow mask pass run only with the shadow_rays switch on; with it off they are never recorded, so never marked, and read as taking no time. Timestamp queries are in the Capability floor (ADR 0021), so every frame on every adapter is timed.

begin_frame returns a FrameTimestamps: the query set, the frame's first query and the frame's pass log. Renderer::render asks it for each pass's PassQueries, the pair of queries at the pass's position, and the pass turns it into the timestamp writes it takes as it is recorded. A compute pass and a render pass take wgpu's timestamp writes at their start and end. The dynamic TLAS's build is not a pass, so it is bracketed: the end timestamp of a marker before it and the start timestamp of a marker after it, both compute passes that query the TLAS so that Metal orders them around the build (The dynamic TLAS). With the crowd's rebuild form the build is never bracketed, since its rebuilds through wgpu would fail the first marker's query, and reads as taking no time. The BLAS refit is recorded through wgpu-hal with no pass of its own, so it gets only a marker after it, which writes the refit's end query at its start; the refit's time runs from the bend pass's end (The BLAS refit).

Turning a PassQueries into its writes marks the pass in the frame's PassLog, a fixed array in the frame's slot with an entry per timed pass, so marking allocates nothing. Each entry holds the kind of writes the pass took, which is the method called, compute, render, bracket or marker, and the submission it was recorded into. A pass handed queries it does not use stays unmarked: the bend pass with nothing to bend, the dynamic TLAS with nothing to build, the refit when no marker was recorded. Submissions are counted by render, which calls split_submission once the bend pass and the BLAS updates are submitted ahead of the frame's other passes; the build, a command buffer of its own, is submitted just ahead of the submission it was marked in. Debug builds assert that each submission's passes are marked in TIMED_PASSES' order.

The log decides which queries the readback trusts: a pass not marked leaves the stale timestamps of the frame that last used its slot. It travels with the frame's GpuFrameStats, where the bench reads which of the gate's passes its run without shadow rays ran.

4 · GpuStatsReadback · src/render/readback.rs

The readback ring

A frame's slot is filled in three steps on three later frames: its counts are copied in as it is recorded, its timestamps are resolved and copied once its submission has completed, and its buffer is mapped once that copy has completed and a fixed number of frames have passed. The main thread never waits for any of it; a slot that is not ready when its frame comes round is skipped and counted.

Only the main thread submits and polls (ADR 0016), and a window polls only through its submissions, so each step is seen done only at a later frame's submit. Three constants fix the lags, and the ring's size follows from them, so from the frames in flight.

src/render/readback.rs
/// Frames after its own by which a frame's submission has completed: those
/// in flight and the one being recorded. Its timestamps resolve then.
const COMPLETION_LAG: u64 = FRAMES_IN_FLIGHT as u64 + 1;

/// Frames after the frame copying a slot's timestamps when its map is
/// requested at the earliest, once that copy completed. The bench has
/// waited for that frame by then, so each frame requests one map whatever
/// the GPU's timing, and the frame's first submission maps it
/// [ref:wgpu-30-submit-maintains]. A map requested with the copy maps in
/// whichever submission or poll first sees the copy complete
/// [ref:wgpu-30-map-after-submission], and wgpu allocates for it there
/// [ref:wgpu-30-handle-mapping]: inside a frame or between two, as the GPU's
/// timing falls.
const MAP_LAG: u64 = FRAMES_IN_FLIGHT as u64;

/// A slot's timestamps are copied `COMPLETION_LAG` frames after its frame.
/// A window polls only through its submissions, so the copy may be seen
/// complete as late as the submissions `MAP_LAG` frames after it; its map is
/// then requested in the next frame and done by that frame's submissions,
/// and the slot is read, and reused, in the frame after.
const SLOT_COUNT: u64 = COMPLETION_LAG + MAP_LAG + 2;

/// A timestamp at the start and one at the end of each timed pass.
const QUERIES_PER_FRAME: usize = 2 * TIMED_PASSES.len();

const TIMESTAMP_BYTES: u64 = QUERIES_PER_FRAME as u64 * wgpu::QUERY_SIZE as u64;

FrameWhat happens to frame N's slotState after
Nbegin_frame reads the slot's last occupant and takes it; end_frame records the copies of the draw, the light counts and the overflow count into it, and a work-done callback that raises frames_completed past NRecorded
N + 3begin_frame sees N's submission completed, resolves its 24 queries into the resolve buffer and copies them into the slot; N + 3's work-done callback marks the copy doneCopying
N + 5 or N + 6begin_frame requests the map once the copy is done and was recorded at least MAP_LAG frames back: at N + 5 where N + 4's submissions saw it done, else at N + 6, since a window sees it only through N + 5's submissions; that frame's submissions map itMapping
N + 7begin_frame reads the slot, pushes N's GpuFrameStats, unmaps the buffer and takes the slot for frame N + 7Recorded

Two skips are possible, both counted in gpu_readbacks_skipped. At N + 3, if N's submission has not completed, N's timestamps are not resolved at all and its slot is freed: Metal reads a timestamp resolved before its pass's submission completed as 0 or stale, so a late resolve would be worse than none. At N + 7, if the slot is still copying or mapping, frame N + 7 goes untimed and its passes get no queries; the slot is read when its map lands and the ring next comes round. A frame that resolved nothing also pushes nothing: its FrameStats keep gpu as None.

GpuStatsReadback::begin_frame, src/render/readback.rs

            self.request_maps(latest_copy);

end_frame copies the three counters the GPU wrote during the frame into the slot's head, in front of the timestamps' place: the culling pass's FrameDraw, whose indirect arguments carry the draw's index count and whose two counts are the Instances drawn and overflowed; the Froxel pass's LightCounts; and the shadow mask pass's 4-byte count of the lights it had no bit for. Each is read on the CPU with pod_read_unaligned at its offset. A frame whose draw, lists or mask overflowed is warned about once, until a frame read back has room for all.

GpuStatsReadback::end_frame, src/render/readback.rs
        let (frame, frames_completed) = (self.frame, self.frames_completed.clone());
        // At most the one slot `begin_frame` resolved.
        let copying = self.copying_in(frame).next();
        encoder.on_submitted_work_done(move || {
            frames_completed.fetch_max(frame + 1, Ordering::Release);
            if let Some(progress) = copying {
                progress.store(COPY_DONE, Ordering::Release);
            }

flush is the end of a run: it waits for the GPU with wait_indefinitely, resolves every recorded slot in one encoder, oldest frame first, submits it, waits again, requests every map, waits a third time and reads every slot. Capture calls it after its last frame, so each frame's GpuFrameStats can be slotted into the frame it names before the stats are returned.

All 168 queries live in one query set because Apple GPUs allow 32 counter sample buffers and on Metal each query set is one. The slot's map is requested a fixed number of frames after its copy, not as soon as the copy is seen done, so that the frame in which wgpu maps the buffer, and allocates the list of its callbacks, does not depend on how the GPU's timing happened to fall: a frame's heap_allocations are then the same whether the GPU finished the frame before between frames or inside the next one.

5 · frame_times · src/render/readback.rs

From timestamps to times

A frame's GPU time is a span, not a sum. Metal runs neighbouring passes side by side wherever neither writes what the other binds, so adding the passes' times would count the shared stretches twice; the frame is timed from its passes' earliest start to their latest end, submission by submission, with the dynamic TLAS's build counted only where it sticks out past the frame before.

frame_times is a pure function of the 24 ticks, the frame's pass log, a floor for the build and the tick period. Every time it returns is end.saturating_sub(begin) scaled by the period, so a stale or missing timestamp reads as no time rather than as a huge one. Its helper bounds takes a range of passes and returns the earliest start and latest end among those that wrote both timestamps: the compute and render passes the log marks, so never the refit, whose marker writes only its end, nor a pass the frame did not run.

frame_times, src/render/readback.rs
    let ran = |pass: usize| log.get(pass).is_some();
    let (bend_pass, blas_refit) = (pass_position(BEND_PASS), pass_position(BLAS_REFIT_PASS));
    let refitted = ran(blas_refit);
    // An untimed refit leaves the build inside the span from the bend pass.
    let build_spanned = !refitted
        && log
            .get(bend_pass)
            .zip(log.get(0))
            .is_some_and(|(bend, build)| bend.submission < build.submission);
    let build = if ran(0) && !build_spanned {
        time(ticks[0].max(build_floor), ticks[1])
    } else {
        Duration::ZERO
    };
    // From the earliest start to the latest end of `passes` that write both
    // timestamps: Metal can run a pass alongside those recorded around it
    // when it reads none of their output, so the Froxel pass can start
    // before culling phase one, and a pass can end after the last.
    let bounds = |passes: std::ops::Range<usize>| {
        passes
            .filter(|&pass| log.wrote_both(pass))
            .fold((u64::MAX, 0), |(begin, end), pass| {
                (begin.min(ticks[2 * pass]), end.max(ticks[2 * pass + 1]))
            })
    };
    let span = |passes| {
        let (begin, end) = bounds(passes);
        time(begin, end)
    };
    // The refit runs from the end of the bend pass, and the frame's other
    // passes in a later submission. A frame that bends nothing records no
    // bend pass, whose timestamps are then an earlier frame's.
    let frame_time = if refitted {
        build
            + time(ticks[2 * bend_pass], ticks[2 * blas_refit + 1])
            + span(blas_refit + 1..TIMED_PASSES.len())
    } else {
        build + span(bend_pass..TIMED_PASSES.len())
    };

The GPU frame total

The frame's passes reach the GPU in up to three submissions: the bend pass with the BLAS refits and their marker, the dynamic TLAS's build between its markers, and the rest. frame_time is the build, plus the span of each submission of passes: with a timed refit, from the bend pass's start to the refit marker's start and then the span of the passes after the refit; without one, the span from the bend pass or, in a frame that bent nothing, from culling phase one. Neither the GPU's idle time between submissions nor what a submission records before its first pass counts. A frame whose bend pass was submitted ahead of the build's submission with no marker to end it, the refit having gone untimed, spans the build's submission from the bend pass, so its build is not counted apart.

The build's time starts at the later of its first marker's end and the floor, and the floor is the tick at which the frame before's last pass ended, which the readback keeps from the last frame it read and hands on only to the frame that directly follows. The build is submitted before the frame's passes and, with two frames in flight, runs beside the frame before's lit and tonemapping passes, which bind no TLAS; counted from its own marker, that overlap would sit in the frame before's span and again in this frame's build. Where the build starts on the GPU, and what its two markers are, is on The dynamic TLAS; the refit's marker on The BLAS refit.

The gate and the lit pass's wait

ADR 0019's gate is the span its reopen clause names: from the start of culling phase one, not from the earliest start among the gate's passes, to the latest end of the passes up to and including the lit pass. The build and the tonemapping pass are outside it. The lit pass's wait is how long after the latest end of the passes from culling phase one up to it the lit pass started, and none where it started beside them; with the span of the passes before it and the lit pass's own time it makes up the gate, which is how praxis report prints the gate as a table that sums.

A pass's own time

Apple GPUs can run a render pass's vertex stage while its fragment stage waits for the passes before it, and the M4 Pro writes the pass's start timestamp as the vertex stage starts: the lit pass's beside the shadow mask pass in some frames, the tonemapping pass's beside the lit pass in every frame. A time read from its own two timestamps would then hold the wait. So a render pass, a pass its log marks as one, counts from the latest end of the passes before it that it waits on, if later than its own start: its time is what it adds past them. The depth pre-pass and phase two's depth pass do not count from the Froxel pass's end, which only the lit pass and later read; Metal can run them beside the Froxel pass and end them first, and a floor at its end would read them as 0. A compute pass keeps its own time, as the Froxel pass runs beside culling phase one and outlasts it. counted_begin models no other dependency: a render pass's floor is the latest end of every pass that ran before it, from the bend pass on, with the Froxel pass left out for the passes before the lit pass, whether or not the pass waited on each of them; a pass that did not run in the frame bounds nothing, since its end timestamp is stale.

frame_times, src/render/readback.rs
    let (froxel_pass, lit_pass) = (pass_position(FROXEL_PASS), pass_position(LIT_PASS));
    let counted_begin = |pass: usize| {
        let begin = ticks[2 * pass];
        if log
            .get(pass)
            .is_none_or(|logged| logged.kind != PassKind::Render)
        {
            return begin;
        }

            .filter(|&earlier| ran(earlier) && (earlier != froxel_pass || pass >= lit_pass))
            .map(|earlier| ticks[2 * earlier + 1])

        let taken = match pass {
            0 => build,

                time(ticks[2 * bend_pass + 1], ticks[2 * blas_refit + 1])
            }
            _ if !ran(pass) => Duration::ZERO,
            _ => time(counted_begin(pass), ticks[2 * pass + 1]),
        };
        (TIMED_PASSES[pass], taken)
    });

Overlap on Metal

Metal orders passes by hazard tracking: a pass waits for an earlier pass only where it binds a resource that pass wrote, or writes one it read (Metal quirks). Any two neighbouring passes with no such hazard can run side by side, and a pass's two timestamps then share time with its neighbours': the Froxel pass starts before culling phase one, the lit pass's vertex stage starts beside the shadow mask pass, the tonemapping pass's beside the lit pass. A single pass's time is therefore a reading of that pass under its neighbours, not a cost that could be added to theirs; the spans, the GPU frame total and the gate, count each shared stretch once. How much Metal overlaps also depends on whether frames queue on the GPU: when the CPU frame is shorter than the GPU frame, passes that overlap on an idle GPU stop overlapping. Only a span, or a difference of two whole frames, compares two changes fairly.

Shadow-ray time

No pass is only the rays: they add phase two's depth pass and the shadow mask pass and change the lit pass. So the bench renders each scene twice, the second time with shadow_rays: false, and shadow_ray_microseconds in src/bench/mod.rs is, for each measured frame, the frame's GPU total with rays on less the same frame's with them off; both runs draw the same frames from the same camera path, so the frames pair. The gate is taken from the rays-off run, as ADR 0019 asks. Each total carries its own noise, so where the rays cost almost nothing the difference is centred near zero and its median can read below it; check_regression therefore passes anything at or below its Baseline, and from a Baseline at or below zero treats any growth as past every ratio and fails it only past the noise floor.

Why this way

The engine sums its own memory. ADR 0013 counts GPU memory as the bytes of the buffers and textures the engine created, summed by the engine on every backend, because wgpu has no allocator report on Metal and unified memory has no separate pool to ask. The readback's buffers are left out since they measure the frame rather than hold it; the presented target and capture's read-back buffer are left out so a capture counts what a windowed run counts. The Budget it is judged against is one number today, to split by kind of memory later.

A ring of mapped buffers, never a wait. ADR 0016 keeps every submit, present and poll on the main thread, so map and work-done callbacks land at known points of the frame, and has the GPU stats come back through a ring of mapped readback buffers on the per-frame staging ring's rule (ADR 0017): a slot is reused only after its callback fired. The ring decides whether the CPU waits, not whether a read is safe; wgpu completes a map only after the last submission using the buffer and refuses to submit work on a mapped one. The alternative, blocking on each frame's map, would stall the frame that reads it; the ring costs seven slots and a few frames of lag instead.

Timestamps, not CPU clocks, for the GPU. A CPU clock around a submit measures the driver, not the GPU; the GPU's own clock, written into a query set at each end of a pass, is what the Capability floor requires of every adapter (ADR 0021). Where the floor's timestamps cannot bracket the work, the dynamic TLAS's build and the BLAS refit, a marker pass that Metal must order after it writes one.

A span against a sum. Summing the passes' times double-counts whatever Metal overlaps, and the overlap changes with the scene and with whether frames queue, so a sum of passes is a number that moves when nothing in the engine changes. The span from earliest start to latest end counts each stretch of GPU time once; the build is counted only past the frame before, since it is submitted first and runs beside that frame's last passes. ADR 0019's gate is a span for the same reason, cut to the passes the main pass's design decides and taken with shadow rays off, since every option traces the same rays.

A render pass counts from what it waits on. Apple's per-stage fences let a render pass's vertex stage start, and its start timestamp be written, before the passes it depends on have ended. Counting from the latest end of those passes reads the pass as what it adds; counting from its own timestamp reads its wait. The floor is every earlier pass's end, not a dependency graph; the one dependency it models is the depth passes against the Froxel pass, whose lists they do not read and which Metal lets them finish before.

A fixed map lag. wgpu maps a buffer, and allocates the list of its callbacks, in whichever submission or poll first finds its copy complete. Requesting the map as soon as the copy was seen done would put that allocation in a frame that depends on the GPU's timing, and the bench's allocation counts would then differ between a quiet run and a loaded one. Requesting it a fixed number of frames after the copy, by which the bench has waited for that frame, pins the allocation to one frame whatever the GPU did.

Wall-clock times per system and stage. ADR 0013's CPU Budget bounds the wall time of each stage's critical path, waits on workers included; CPU time summed across threads is neither measured nor budgeted, so the recorder times stages on the main thread and the allocator counts that thread alone. Dropped time is ADR 0022's: the fixed schedule reads no wall clock, so what the Tick cap skipped is reported, not hidden.

Limits

Seven frames late, or never. A frame's GPU stats arrive seven frames after it at the earliest. A frame whose submission had not completed three frames on never gets them. A slot still copying or mapping when its frame comes round is read when the ring next comes round, so that frame's stats arrive fourteen frames late, and the frame that found the slot busy goes untimed. The count of skips is all that records either.

One thread's allocations. The counter is per thread and the frame reads the main thread's; what the compute pool's workers allocate inside the frame is not counted.

A pass's time is a reading under its neighbours. Where Metal overlaps passes, a pass's own time depends on what ran beside it and on whether frames queued on the GPU, and a render pass's floor is at the latest end of the passes before it whether or not it waited on all of them. Only the spans compare two changes fairly.

The build's cost is not separated. Counted past the frame before, the build reads what sticks out, not what it took from the passes it ran beside; that cost shows in their times.

Estimated acceleration structures. wgpu exposes no acceleration-structure size, so their bytes are an estimate from figures measured once per adapter: NVIDIA's on an NVIDIA GPU on any backend, lavapipe's on any other Vulkan adapter, the M4 Pro's on any other.

No cost across frames. Loads stage outside the per-frame ring and count no upload; the stats say what a frame cost, not what a Scene's load did.

Timestamps inside a pass. wgpu's timestamps inside encoders and passes are reported by the capability printout and never requested, so no finer division than a pass is measured.

History

The stats began as the CPU recorder, the counting allocator and the engine's own memory ledger, written when the Instance buffer stopped growing and every Baseline's memory had to add up to the byte. GPU time came as two timestamps per pass summed into a frame, then the dynamic TLAS's build bracketed by two markers that query the TLAS, since a build is no pass, and the BLAS refit ended by a marker that reads its scratch (The dynamic TLAS, The BLAS refit). The frame became a span per submission once the Froxel pass was seen starting before culling, and the build was counted from the frame before's last pass after it was found running beside that frame and counted twice; the main pass prototypes were judged by spans for the same reason (Metal quirks). A render pass came to count from the passes before it when the M4 Pro was seen writing its start timestamp as the vertex stage started, the depth passes were then freed from the Froxel pass's end, and the lit pass's wait was added when a scene spent most of its gate before the lit pass began. The ring took its map lag when a frame's allocations were found to depend on when the GPU finished, and the readback's, the presented target's and capture's buffers left the memory sum. Which passes a frame ran was first told to the ring after the frame was recorded, as three flags beside lists of passes never run and of render passes; it became the log the passes mark as they take their queries, so the list of timed passes is written once. The volumes that narrated those steps are absorbed into this page; it describes the mechanism as it is.
